## 一、用户报告的缺陷与实测复现

用户反馈：「我用增强，给出的增强后提示词没有参考标签。」

上一轮（`34f05953`）已经解决了「素材要传进增强请求」，但**增强后的提示词里仍然没有参考编号** —— 模型只是「描述了图片」，却没「标注哪张图」。下游 H3 工作流拿到的是一段没有引用的文字，无法知道哪句话对应哪张素材。

**本轮现场复验又挖出第二个、更隐蔽的缺陷**（见第二节）：上一轮把参考标签一律写成 H3 官方的 `<Picture N>`，结果**参考生图（Qwen-Image 2.1 图片编辑）被自己修坏了**。

---

## 二、根因：不同模型族的官方参考标记语法**不是同一套**

这是本轮最关键的发现 —— 官方规范本身是分模型族的：

| 面板 | 模型族 | 官方参考标记语法 | 官方依据 |
|---|---|---|---|
| `flf` / `r2v` / `t2v` / `longfilm` | MiniMax H3 视频 | `<Picture N>` / `<Video N>` / `<Audio N>` | 官方 skill `h3-prompt-writing/references/ref-en.txt` |
| `i2i_qwen`（参考生图） | Qwen-Image 2.1 | `<imageN>`（小写、**无空格**） | 官方 PE-I2I system prompt 原文：*"the rewritten instruction MUST use `<image1>`, `<image2>`, ..."* |
| `i2i_h3image` | MiniMax-H3-Image | `<Picture N>` | `h3studio/h3image.py` 的 `H3_IMAGE_PLACEHOLDER`，该模块明确写了「官方占位标记是 `<Picture N>`（**不是** Qwen 的 `<imageN>`）」，且两套语义必须隔离 |

### 线上实测复现（修复前，8190）

```
POST /api/enhance   mode_ctx=i2i_qwen, 2 张参考图
  -> HTTP 200
     reference_labels.found = ["<Picture 1>", "<Picture 2>"]     <-- 用了 H3 语法

POST /api/jobs      mode=i2i_qwen, prompt 含 <Picture 1>/<Picture 2>
  -> HTTP 400  code=ref_invalid
     "参考图校验未通过：有 2 张参考图，提示词里必须有 <image1>..<image2>
      占位标记（官方 PE-I2I 多图模板要求用 <imageN> 引用每张图）"
```

用户的表现是：**「我点了增强，增强出来的提示词提交不了。」**

### 修复后（8190，线上实测）

```
POST /api/enhance   mode_ctx=i2i_qwen, 2 张参考图
  -> HTTP 200

     assets.labels    = ["<image1>", "<image2>"]
     reference_labels = {"expected": ["<image1>","<image2>"],
                         "found":    ["<image1>","<image2>"]}

POST /api/jobs      mode=i2i_qwen, prompt 含 <image1>
  -> HTTP 200  {"id": "614c003550fc", "status": "queued"}      <-- 提交通了
```


## 三、改动清单

### 3.1 `h3studio/enhance_assets.py` —— 引入「标签方言」

- 新增 `LABEL_DIALECT_H3` / `LABEL_DIALECT_QWEN` 两个方言常量。
- `label_for(category, index, dialect)` 按方言产出标签：
  - H3 → `<Picture 1>` / `<Video 1>` / `<Audio 1>`
  - Qwen → `<image1>`（图片）；视频/音频仍走 H3 写法（Qwen 没有这两种参考槽位，不编造不存在的语法）。
- `label_pattern(dialect)` / `has_reference_label(...)` / `extract_reference_labels(...)` **按方言收紧匹配**：
  - Qwen 方言**只认** `<imageN>`。放宽会让模型写错方言被判「通过」，而真正提交时仍被 400 拒掉 —— 变成**静默假通过**，比报错更糟。
  - H3 方言**不认** `<imageN>`。
- 新增 `normalize_label()` / `missing_labels()`：比较前归一化空白。模型写 `<image 1>`（带空格）而我们分配 `<image1>` 时，不再误报「缺标签」。
- `resolve_assets(refs, work_dir, dialect)` 接受方言，返回值带出 `dialect`。
- `describe()` 在 Qwen 方言下**显式讲清标签写法**（小写 image + 数字、中间无空格），避免模型按模板里的旧写法输出。
- `summary()` 回显 `dialect`。

### 3.2 `server.py` —— 按面板选方言

- 新增 `_label_dialect_for_mode(mode_ctx)`：`i2i_qwen` → qwen，其余 → h3。逐条对应第二节的官方依据。
- `_resolve_enhance_assets(asset_refs, dialect)` 把方言传到解析层。
- 素材解析与**输出标签校验**都传方言。
- 响应回显 `reference_labels.found` 也传方言（**这条是浏览器取证实测踩出来的**，见第五节）。

## 五、取证过程中实测踩出的第三个缺陷（已修）

浏览器取证第一次跑 `i2i_qwen` 时，`reference_labels.found` 是 `[]`，但 `enhanced` 原文里明明写着「将`<image1>`作为起始帧、`<image2>`作为结束帧…」，meta 行还显示「模型未写出：`<image1>`、`<image2>`」。

**根因**：校验那一处传了方言，**响应回显**那一处（`reference_labels.found`）漏传 —— 走了默认 H3 方言，只认 `<Picture N>`，于是 `<image1>` 一个都匹配不上。

**危害**：回显写「模型未写出」= **假消息**。模型其实写了。用户会以为增强没带参考编号，进而放弃用增强 —— 比「不显示」更糟。

**修法**：`server.py` 的 `reference_labels.found` 改为 `extract_reference_labels(enhanced, label_dialect)`。

**回归防护**：
- `test_server_response_found_field_uses_dialect` —— 源码级断言：响应字典里的 `found` 必须带方言参数。
- `test_response_found_field_matches_validation_gate` —— 一致性断言：校验与回显算出的标签集合必须一致（并反证：同一段文本在 H3 方言下确实匹配不到 `<imageN>`）。
- 变异脚本新增第 10 个变异（响应回显不传方言），**已验证被杀死**。

| 判定项 | 结果 |
