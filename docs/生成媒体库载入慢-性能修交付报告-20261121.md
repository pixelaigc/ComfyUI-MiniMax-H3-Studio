# 生成媒体库「卡片载入慢」性能缺陷 —— 实测定位与修复交付报告

**项目**：ComfyUI-MiniMax-H3-Studio 多模型创作工作台
**用户反馈**：生成媒体库的卡片**有时候载入很慢很慢**（偶发，不是每次都慢）
**线上服务**：systemd `h3-studio.service` → `http://127.0.0.1:8190`
**修复分支**：`local/feature/favorites-v2-20261120`（隔离 worktree `/root/projects/h3s-favorites`）
**上线 merge commit**：`461c9e584004ec0ba2ee3ef2124383c0abc83190`

---

## 0. 一句话结论

**「慢」不在生成媒体库自己的接口上，而在同一条 aiohttp 事件循环上**：
首屏并发拉面板清单时，`/api/video-options` 的**同步扫盘**（264 次 `find_weight`，
135 次落 USB 盘的 `rglob`）把事件循环占住 ~600ms，
导致**同一时刻所有请求排队** —— 包括 `/api/jobs`（它自己只要 4.7ms）。

外加一处**恒定成本**：卡片直接引用原始产物（一页 12 张卡实测 **29.6MB**）。

| 指标 | 修前 | 修后 |
|---|---|---|
| `/api/jobs` 在面板接口并发下的 p50 | **1279ms**（劣化 220 倍） | **6.5ms**（劣化 1.3 倍） |
| 一页 12 张卡的媒体传输字节（翻到第 2 页） | **28,184 KB** | **489.5 KB**（-98.3%） |
| 首屏打开生成库的媒体字节 | 8,203 KB | 167.9 KB（-98.0%） |
| 生成完成刷新后的媒体字节 | 4,954 KB | 167.9 KB（-96.6%） |
| `/files` 原始产物请求数（三场景全部） | 10 / 37 / 9 | **0 / 0 / 0** |
| `/api/video-options` 自身 p50 | 607ms | 1.5ms |
| 浏览器首屏并发时 `/api/jobs` 耗时 | 707ms | 12~36ms |

**上线 merge commit**：`d593bf4`（线上 8190，systemd `h3-studio.service` active）

## 2. 修复（按实测瓶颈选，不是凭猜）

### 2.1 主因：`/api/video-options` 不再占住事件循环

**A. `h3studio/video_models.py` —— `find_weight` 记忆化缓存**

```python
_FIND_WEIGHT_CACHE: dict = {}
_FIND_WEIGHT_TTL = 60.0

def find_weight(name, kind="diffusion_models"):
    ...
    key = (name, kind)
    if key in _FIND_WEIGHT_CACHE:
        return _FIND_WEIGHT_CACHE[key]
    ...
```

* 264 次扫盘 → 1 次
* **正确性**：返回的是**路径**（路径没变，返回值就仍正确）；
  内容变化由 `_read_header` 的 `(path, mtime, size)` 缓存自己判失效；
  文件被删时下游 `is_file()` / `open()` 各自判出来。
  ⇒ **只影响性能，不影响正确性**。
* 失效入口：`invalidate_find_weight_cache()`（装完权重调用）+ 60s TTL 兜底。

**B. `h3studio/video_models.py` —— 兼容性矩阵缓存**

```python
_ACCEL_COMPAT_MATRIX_CACHE: dict = {}
_ACCEL_COMPAT_MATRIX_TTL = 60.0
```

84 组（7 底模 × 12 LoRA）兼容性不再每次重算。

**C. `server.py` —— payload 构建挪出事件循环**

```python
payload = await asyncio.to_thread(
    video_models.options_payload,
    node_available=node_available,
    snapshot=snapshot,
)
matrix = await asyncio.to_thread(
    video_models.accel_lora_compat_matrix, model_key)
```

底下是 `open()` / `Path.stat()` / `rglob()` —— **同步阻塞 IO**，
改成 async 只是换个写法，不能让它不占线程。
线程化解决「不阻塞别人」，缓存解决「自己别那么慢」—— **两层都要**：
缓存后单次 ~25ms；线程化保证即使缓存未命中（冷启动 / TTL 过期）也不冻结全站。

### 2.2 恒定成本：卡片媒体走受限尺寸缩略图

**D. 新增 `h3studio/thumbnails.py`**

| 类型 | 做法 | 实测耗时 | 产物大小 |
|---|---|---|---|
| 图片 | PIL 解码 → 缩到最长边 ≤640 → JPEG q82 | ~30ms | 14~43KB（原 1.1~9.5MB） |
| 视频 | ffmpeg 取第 0 秒一帧 → 宽 640 → JPEG | ~140ms | 14~43KB（原 1.8~7.2MB） |

* **缓存键** = `sha1(路径 + mtime_ns + size)`：源文件换了内容 → 键变 → 旧缩略图自动失效
* **URL 带 `k=<键>`** → 浏览器也不会拿旧缓存（这是 `immutable` 缓存的前提）
* **每键锁 + 全局并发闸(4)**：同一张缩略图只生成一次
* 生成失败**不缓存** → 下次重试
* 写在 `data/thumbs/`，**不碰用户产物**

**E. `server.py` —— 列表接口只算键，缩略图接口才生成**

```python
# GET /api/jobs：只 stat 一次算键（亚毫秒）-> 下发 URL
out["thumb"] = f"/api/thumb/{key}.jpg"

# GET /api/thumb/{key}.jpg：被浏览器请求时才生成（走线程 + 并发闸）
```

> **踩坑**：第一版把「生成缩略图」放进 `GET /api/jobs`，
> 结果**列表接口自己**被拖到 **1546~2897ms**（12 张卡 = 11 次 ffmpeg）——
> 那是「为了媒体字节少，把列表接口搞慢」，正好是反的。
> 改成「列表只算键、缩略图接口才生成」后，列表接口回到 **4.5ms**。

**F. `web/app.js` —— 卡片渲染**

```js
// 图片卡片：缩略图 + 懒加载（点开大图仍用原图）
preview = `<img src="${src}" loading="lazy" decoding="async" data-orig-src="${outputUrl(job, image)}">`

// 视频卡片：缩略图当 poster，preload="none"（实测只有 none 才真的 0 字节）
preview = `<video src="${outputUrl(job, video)}"${posterAttr} controls preload="none"></video>`

// 批次缩略图：同样走缩略图 + lazy
```

**G. `web/index.html`** —— `app.js?v=` 从 `fav20261120c` 升到 `mediaperm20261121a`
（`tests/test_frontend_assets_hygiene.py` 的期望表同步更新）
