## 1. C 组根因分析（用户 2026-11-13 11:24 报的 BUG）

### 1.1 用户报告的现象

媒体库「文生视频」卡片：

| 现象 | 原文 |
|---|---|
| LoRA 行显示错 | 显示 `integrated_multimodal_description`（这是**提示词/描述类字段**，根本不是 LoRA），而实际任务并未使用该 LoRA |
| 参数不显示 | 卡片完全不显示步数/调度器等生成参数 |
| 提示词行有噪声 | 「提示词」行混入工作流节点名等噪声 |

### 1.2 根因链（三环，逐环实测核实）

**第 1 环：落库端没有白名单校验**

`params["lora"]` 这条路径**完全没有取值校验**：

| 入口 | 是否校验 lora | 证据 |
|---|---|---|
| `server.prepare_job_params` | ❌ 不校验 | `server.py:2002+` 只按 `lora` 决定采样档位（`params.get("lora") != "none"`），不校验值本身 |
| `h3studio.agent._validate_create_job_args` | ✅ 校验，但**只守 Agent 工具入口** | `agent.py:2470+` → `agent_schema.validate_params` |
| 面板提交 / 内置 Agent 批量 / 直接调 API | ❌ 不经过上面那个校验 | — |

实测验证（`agent_schema.validate_params`）：

```
t2v    hard=1  HARD lora LoRA「integrated_multimodal_description」不是 t2v 的合法取值
flf    hard=1  HARD lora LoRA「integrated_multimodal_description」不是 flf 的合法取值
r2v    hard=1  HARD lora LoRA「integrated_multimodal_description」不是 r2v 的合法取值
```

→ **任意字符串**都能落进 `params["lora"]` 并被原样存进 `jobs` 表。

**第 2 环：摘要层原样透传**

`h3studio/job_meta.py` 的 `_legacy_video_summary` 把 `params["lora"]` **原样**塞进 `lora_label`（不查表、不校验）。

实测复现（修复前）：

```python
job_meta.summarize("t2v", {"model":"lora","lora":"integrated_multimodal_description"})
# -> {"lora_label": "integrated_multimodal_description", "lora_strength": 1.0, ...}
```

**第 3 环：前端直接渲染**

`web/app.js` 的 `loraLabel()` 读 `info.lora_label` 就渲染 → 提示词字段名被当成 LoRA 名显示。

### 1.3 为什么 `integrated_multimodal_description` 会跑进 `lora`

那是 **H3 三段式提示词的字段名**（H3 官方提示词规范的第一段）：

- `integrated_multimodal_description` — 画面+声音描述
- `overall_soundscape` — 环境音
- `non_diegetic_music` — 非叙事音乐

出处：`h3studio/enhancer.py:229-230`（`"dimensions": ["integrated_multimodal_description", "overall_soundscape", "non_diegetic_music", ...]`）。

本机 155 条历史任务里，有 **19 条**的 `params.prompt` 以 `integrated_multimodal_description:` 开头（实测统计），而这些提示词经过某些提交路径时，字段名被当成参数值写进了 `lora`。

### 1.4 修复（两道闸互补）

| 闸 | 位置 | 作用 |
|---|---|---|
| **闸 1（落库前）** | `server.py` `prepare_job_params` | 白名单外的 `lora` **直接丢弃**（视为「没传」，由工作流走默认档）。不报错 —— 历史任务里已经躺着这类脏值，报错会让老任务无法复用 |
| **闸 2（显示层）** | `h3studio/job_meta.py` `_is_valid_legacy_lora_key` | 已落库的脏值**当「没有 LoRA」**（`lora_label` 置空），并把原值记进 `lora_rejected` 留证据 |

白名单的真源 = `workflows.LORAS`（工作流里真正会挂上去的那张表）。

**实测修复效果**（往测试库插一条脏值任务，浏览器实测）：

```
API:  lora_label    = ''
      lora_rejected = 'integrated_multimodal_description'
      lora_name     = ''

UI:   LoRA = 无        ← 修复前显示 integrated_multimodal_description
```

## 2. 字段映射表（C1 / C2）

### 2.1 参数取值口径

**唯一真源 = 服务端算好的 `job.model_info`**（`h3studio/job_meta.py` `summarize()`）。
前端**不再从 `params` 里猜** —— 那正是 BUG 的根因。

服务端按**字段语义白名单**取参（`job_meta.GENERATION_PARAM_FIELDS`）：

```python
GENERATION_PARAM_FIELDS = (
    "steps", "sampler", "scheduler", "cfg",
    "shift_video", "shift_audio",
    "width", "height", "aspect", "resolution",
    "duration", "seed",
    "twopass",
)
```

**白名单里没有** `prompt` / `negative_prompt` / `description` / `lora` —— 所以提示词、描述、工作流节点名**永远不可能**被当成参数显示。

前端副本：`web/job-meta.js` 的 `PARAM_FIELDS`（与服务端一一对应）。

### 2.2 卡片字段映射表

| 卡片显示行 | 数据来源（key） | 取不到时 | 备注 |
|---|---|---|---|
| 模式 | `job.mode` → `MODE_INFO.name` | — | |
| 分辨率 | `job.resolution_info.label`（服务端按**产物实际像素**算） | 「—」 | 不用 `params.resolution`（遗留默认值会撒谎） |
| 时长 | `model_info.duration` | 「—」 | **不再**用 `p.duration \|\| 5`（老任务没记录时会显示假的 5s） |
| 模型 | `model_info.model_label` | 「—」 | 服务端摘要，与面板下拉逐字一致 |
| **LoRA** | `model_info.lora_label` + `model_info.fixed_lora_label` | **「无」** | **只来自真实使用的 LoRA 列表**（含强度）；工作流固定那枚单独标明 |
| 采样 | `model_info.sampler` · `model_info.scheduler` | 「— · —」 | 不再用 `p.sampler`（遗留字段常为空） |
| 步数/CFG | `model_info.steps` · `model_info.cfg` | 「— · —」 | |
| 注意力 | `model_info.attention_label` | **整行不渲染** | 老任务没记录 → 不编造 |
| 种子 | `model_info.seed` | 「随机」 | |
| 耗时 | `job.elapsed` | 「—」 | |
| 提示词 | `params.prompt`（截断 80 字，点击看全文） | — | 节点名噪声来自**提交时**混入，不是渲染层 |

### 2.3 复用参数一致性（C4）

`reuseConfigFromJob()` 改为**先读权威摘要、再退回 `params`**：

| 字段 | 修复前 | 修复后 |
|---|---|---|
| steps / sampler / scheduler | `p.steps` 等（遗留，常为空） | `model_info.steps` 等 → `p.*` 兜底 |
| shift_video / shift_audio | `p.shift_*` | `model_info.shift_*` → `p.*` |
| 宽高 / 比例 | `p.width` / `resolution_info` | `model_info.width` → `p.width` → `resolution_info` |
| **LoRA 强度** | ❌ 只带 key | ✅ `accel_lora` + `accel_lora_strength` |
| attention | `p.attention` | `model_info.attention_key` → `p.attention` |
| cfg / seed | ❌ 没带 | ✅ `model_info.cfg` / `model_info.seed` |

> **为什么 LoRA 强度必须单独处理**：面板是**单选**模型（`accel_lora` + `accel_lora_strength`），
> 旧实现只传 `accel_loras` 数组 -> 走兼容分支 -> 强度取的是数组项的 `strength`，
> 跟面板当前档位不一定一致。

## 4. 媒体库注意力机制标注（需求 3）

- **真值来源**：任务元数据 `params["attention"]`（面板真实提交的字段）。
- **显示名**：服务端 `job_meta._attention_label()` 查 `video_models.VIDEO_ATTENTION_MODES` 算出，
  **与面板下拉逐字一致**（不会出现「面板写 Sol-Attn、卡片写 sol」）。
- **已下线的机制**：返回「<label>（已下线）」并附 `attention_available=false` + 下线原因
  （实测 `sol_scheduled` -> 「Sol-Attn 渐进调度（已下线）」）。

### 5.3 借鉴项 #1 的落地细节

**节点链路（开启 sigma 精修时）**

```
9  BasicScheduler(scheduler, steps)        -> sigmas
346 H3SigmaRefiner(sigmas=["9",0], extra_steps, start_at_sigma, end_at_sigma, spacing)
                                              -> sigmas（低噪段加密）
171 SelfLiftH3Sampler(sigmas=["346",0], transition_step, ...)
```

**transition_step 必须重标定**（这是本轮最容易踩的坑）

SelfLift 把 sigma 表切成两段：

```python
sigmas[:transition_step + 1]   # 低分辨率一采
sigmas[transition_step:]       # 高分辨率二采
```

`transition_step` 是**索引**。精修后表长 `+extra_steps`，索引语义会变 ->
上下限必须按**精修后**的表长算，不能按 `steps-1`。

实测（`h3studio/video_workflow.py` + `server.py` 两处**同一份公式**）：

| 场景 | refined_len | max_transition | ts_in=3 | ts_in=18 | ts_in=19 | ts_in=99 |
|---|---|---|---|---|---|---|
| 无精修，steps=4 | 5 | 3 | 3 | — | — | 3 |
| 精修 extra=15 | 20 | 18 | 3 | 18 | 18 | 18 |

**默认关闭** —— 节点不在本机时服务端强制关（`"H3SigmaRefiner" not in _COMFY_NODE_NAMES`），
面板控件也置灰，避免「能开但跑不了」的假控件。

## 8.5 本轮**自造**的回归与修法（如实记录）

> 这一节记的是**我自己在实现过程中引入、又被浏览器实测抓出来**的缺陷。
> 记下来是因为它们都体现了同一个教训：**只看代码不看渲染，就会自造 bug**。

### 8.5.1 卡片「种子」行渲染两次

- **现象**：图像 / 音频卡片上「种子」出现两行。
- **根因**：需求 C2 补齐生成参数时，在**图像分支**和**音频分支**里各加了一行「种子」，
  但模板末尾本来就有一行**共享**的「种子」（在三种分支之外）。
- **修法**：删掉分支内两行，保留末尾共享那行。

### 8.5.2 骨架卡与真实卡片不等高（网格抖动 68px）

- **现象**：`test_grid_flash` 的「骨架 → 真实卡片网格高度不得变」挂了：
  网格高度从骨架 **1784px** 变成真实卡片 **1852px**（差 68px）。
- **定位**（不是猜 —— 复刻测试流程的诊断脚本逐帧采样）：

  | 观测项 | 骨架 | 真实 | 结论 |
  |---|---|---|---|
  | 卡片高度 | 436px | 453px | 差 17px × 4 行 = 68px |
  | 逐行高度 | `[27×8, 20]` | `[27×8, 20]` | **完全一致** |
  | 预览区高度 | 189px | 189px | 一致 |
  | 动作行高度 | **36px** | **53px** | ← **差异在这** |
  | 动作按钮数 | **3** | **5** | ← 差异在这 |

  真实卡片有「下载 / 新窗口打开」（因为**有产物**），骨架没有（`outputs` 为空）
  -> 动作行从 2 行缩到 1 行 -> 每张卡矮 17px。
- **修法**：
  1. 骨架 job 加 `is_skeleton` 标志，`jobCard` 按骨架形态补上**同形**的
     「下载 / 新窗口打开」两个占位按钮。
     **不给假 outputs** —— 给了会真的渲染 `<img>`，骨架就变成真实卡片，
     测试直接判「整个切换过程没出现骨架占位」（踩过这个坑）。
  2. 骨架的 `model_info` 补齐成与真实卡片**同形**（LoRA 显示「无」、采样/步数占位），
     保证元信息区行数一致。
  3. **骨架刚铺过时，真实卡片的写入推迟一帧** —— 原来骨架与真实卡片在**同一帧**内替换，
     服务端响应快时（约 10ms）骨架等于没出现过（用户看不到加载态，
     测试判「没出现骨架占位」）。这条是连跑 3 次才稳定下来的。

- **验证**：`test_grid_flash` 连跑 3 次全绿；与本次改动相关的 10 个测试文件
  **197 passed + 276 subtests passed**。

> 实质错误** —— 而且性质比「自造 bug」更值得记：

#### 错误 1：LightX2V 三枚的 shift 被统一标成 12/3（实为 6/3 与 12/3 两档）

第一版把三枚 LightX2V 的 shift 都标成「ComfyUI 内生值 12/3」，步数/采样器
一律标「作者未提供」。回查上游作者规格表后发现**作者明确给了**：

```
https://github.com/ModelTC/Minimax-H3-Turbo#1-model-specs
| Model                        | Training resolution | shifts (video/audio) | NFE | 推荐 NFE |
| FL2VA Turbo 4-step v0.1      | 544p mixed          | 12 / 3               |  4  |    4     |
| FL2VA Turbo 8-step v1.0      | 544p mixed          | 12 / 3               |  8  |  8 / 4   |
| FL2VA Turbo 4-step v1.0 768p | 768p (1344×768)     |  6 / 3               |  4  |    4     |
| FL2VA Turbo 8-step v1.0 768p | 768p (1344×768)     |  6 / 3               |  8  |    8     |
| Ref2VA Turbo 4-step v0.1     | 544p mixed          | 12 / 3               |  4  |    4     |
```

`COMFYUI_SETUP_AND_INFERENCE.md`：「set `lora_name`, `steps`, `shift_video`, and
`shift_audio` together to match the model table. **Sampler defaults to `euler`.**」

SLA 变体（HF `lightx2v/Minimax-h3-Turbo-SLA` 模型卡）：
`"video_flow_shift": 6.0, "audio_flow_shift": 3.0, "h3_step_update": "training_euler"`

**→ 768p 系列的 shift 是 6/3，544p 系列才是 12/3。**

```
lightx2v_8step         推荐步数：8（作者提供）  推荐采样器：euler（作者提供）  推荐视频 shift：12（作者提供）
```

#### 错误 2：主模型「无加速 LoRA」档位的采样器写成 euler（实为 res_multistep）

第一版给 5 个 fl2va 底模写的无 LoRA 档位是 `20 步 / simple / euler`。
但**本项目自己的工作流**写的是：

```python

default_steps     = 4  if lora != "none" else 20
default_scheduler = "beta"   if lora != "none" else "simple"
```

**euler 是「挂了加速 LoRA」时的档位；无 LoRA 档位是 res_multistep。**
第一版把两档混了 —— 用户照注释设采样器，会与工作流默认不一致。

**修正后**：`推荐采样器：res_multistep`，来源标注为「本项目工作流档位
（`workflows.py:347-350`）」，并加了一条断言把这条锁死
（用正则匹配工作流**源码里的常量**，不是硬编期望值）。

### 11.3 【上线前实测发现并修掉的真实缺陷】C1 白名单只覆盖视频模式

#### 11.3.1 缺陷现象

上线前的复核实测发现：合并树里的 LoRA 白名单闸门**只对视频模式生效**。

| 模式 | `validate_params` | `prepare_job_params` 落库后的 `params.lora` |
|---|---|---|
| `t2v` | ✅ 报 `invalid_lora` | ✅ 清空 |
| `t2i` | ❌ **返回 0 个问题** | ❌ **原样保留** `"integrated_multimodal_description: [Shot 1] ..."` |
| `t2i_qwen` | ❌ 0 个问题 | ❌ 原样保留 |
| `t2i_moss` | ❌ 0 个问题 | ❌ 原样保留 |
| `t2a` | ❌ 0 个问题 | ❌ 原样保留 |

另外 `params["loras"][].name`（图像模式的**真正** LoRA 入口）同样无校验；
素材库入库把 `params.lora` / `params.loras` **原文**写进 `source_meta`，
前端素材抽屉把每个键原样印出来 → 提示词被印在「lora」那一行。

#### 11.3.2 根因（三处各写一套判定，且都只覆盖视频）

1. **校验端** `agent_schema.validate_params`：
   `if allowed and str(lora) not in allowed` —— 而 `mode_loras()` 对图像/音乐模式
   返回**空列表** → `allowed` 为空 → **整个校验分支被跳过** → 任何字符串都能过。
2. **落库端** `server.prepare_job_params`：
   `if mode in ("t2v", "flf", "r2v", "longfilm")` —— 图像/音乐模式直接跳过。
3. **入库端** `asset_service.add_from_media_output`：
   `params.get("lora")` 原文照抄。

**「各写一套」必然漂移 —— 这正是缺陷的成因。**

#### 11.3.3 修法：单一判定 + 全部模式共用

`h3studio/job_meta.py` 新增**唯一判定入口**：

| 函数 | 职责 |
|---|---|
| `is_real_lora_key(value)` | 是不是本机真实 LoRA 标识符 |
| `sanitize_legacy_lora_value(value)` | 归一成可安全落库的值（`""` = 丢弃） |
| `resolve_job_lora(mode, params)` | 算出「这个任务真实用到的 LoRA」（固定形状） |

四道闸门全部基于**同一份**判定：

- **落库端** `server.prepare_job_params`：改成**按模式语义**统一处理 ——
  该模式工作流真的读 `params["lora"]`（视频旧路径）→ 值必须过白名单；
  该模式不读（图像/音乐）→ 传了就是误填 → 一律丢弃。
  `params["loras"]` 数组同样逐项过白名单。
- **校验端** `agent_schema.validate_params`：图像/音乐模式传 `lora` → 报
  `invalid_lora`；`loras[].name` 不在清单 → 报 `invalid_loras`。
- **显示端** `job_meta._image_summary` / `_music_summary`：
  `loras[].name` 也要过白名单 —— 这是**本分支原有**的一个显示层泄漏
  （`t2i` / `t2i_qwen` 的 `lora_label` 会显示整段提示词）。
- **入库端** `asset_service.add_from_media_output`：

#### 11.3.4 一个反直觉的关键点：判定顺序必须「清单优先」

本机真实 LoRA 里有 **23 个文件名带空格**：

```
z-image-effects/CYBORG FACTORY 🦾 BY STX_epoch_13.safetensors
moss-effects/moss Hsin2.safetensors
moss-effects/lucia elowen.safetensors
...
```

若把「不含空白」这条粗判排在「查清单」**前面**，这 23 个真 LoRA 会被**全部误杀**
—— 用户的图像任务会突然「没有 LoRA 了」，而闸门看起来还在正常工作
（脏值确实被挡住了，**只有真值被误杀**）。

所以判定顺序必须是：

1. **在真实清单里** → 直接认（清单是权威，形状不参与）；
2. 不在清单里 → 才用形状判据兜底：长度 ≤ 120 **且** 不含冒号/换行
   （提示词正文必带冒号 `"integrated_multimodal_description: ..."`，文件名不带）。

> **注**：并行分支 `local/feature/media-card-detail` 的 `is_real_lora_key`
> 采用的是「先判空白、再查清单」的顺序 —— 若直接采用，会误杀这 23 个真 LoRA。
> 本轮**未直接采用**该实现，而是沿用并修正了本分支的白名单入口。

**白名单范围 = 面板可选清单**（实测核实）：
`LORA_CATALOG`（407 条）经实测是图像面板下拉清单的**超集**
（面板 407 条全部在 catalog 里；磁盘上另有 256 个权重不在 catalog ——
那些不是用户可选项）。工作流侧同样以 `lora_registry.resolve_lora()` 为准，
解析不到就抛「本机不存在该 LoRA 文件」。**白名单与真实执行语义一致。**
