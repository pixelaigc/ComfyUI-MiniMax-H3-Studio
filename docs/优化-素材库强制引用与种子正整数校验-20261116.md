## 一、需求与落地位置

### 目标 1：所有媒体引用必须先进入素材库

用户要求：首尾帧 / 参考生等功能的图片 / 音频 / 视频引用，与「图片编辑」保持一致 ——
外部素材必须先进入素材库，界面只能从素材库挑选并引用，**不允许功能直接引用外部文件路径**。

**现场核实结论**：改动前 `flf`（首尾帧）/ `r2v`（参考生视频）面板
仍然存在「本地文件直传」入口 —— 槽位渲染器创建 `<input type="file">`，
提交体用 multipart 的 `file_first` / `file_last` / `file_ref` / `file_refvid` /
`file_refaud` 直接把本地文件路径交给服务端。`i2i_qwen` / `i2i_h3image`
（「图片编辑」）**早已**有这条约束（`code="ref_must_come_from_library"`），
本轮把前两者对齐。

### 目标 2：种子仅允许正整数

用户实测：非数字种子 → 用户只看到
`✕ 生成失败（服务端未能给出具体原因）。请稍后重试；若反复失败，请查看服务端日志，或改用「复用参数」重新生成一段。`

**根因**（现场核实）：种子**一路不校验**地流到 worker ——
`workflows.py:339` 取 `params.get("seed")`，`workflows.py:380` 执行 `int(seed)`，
ValueError 被 worker 捕获后只剩一句兜底文案（`server.py:1003` `_GENERIC_FAILURE_REASON`）。

本轮把校验提前到「提交前」与「服务端入口」，非法种子**明确拦截并给中文原因**。

| 场景 | 修复前 | 修复后 |

## 六、部署期间由线上探针发现的两个真实缺陷（已修）

> 这两个是**部署脚本自带的线上功能探针**发现的 —— 单元测试全绿，
> 但线上真实请求打穿了它们。两个都已修 + 补回归 + 重新部署。

### 缺陷 A：视频归一层把非法种子吞成「随机」

- **现象**：`POST /api/jobs (mode=t2v, seed="abc")` → **200**，
  任务照建、照跑（用户填了非法种子，却跑出一个随机结果，且无任何提示）。
- **根因**：`normalize_t2v_params` 在 `prepare_job_params` **之前**跑
  （`api_create` 里的顺序），而它原来只做 `int()` 转换、失败就置 `None`
  —— 归一后 `prepare_job_params` 看到的是「随机」，种子校验**根本没机会生效**。
- **修法**（`server.py`）：
  1. 归一层改走 `seed_guard.parse_seed`，非法即**报错**；
  2. 种子校验挪到函数**最前面** —— 后面还有宽高 / 模型 / 加速 LoRA /
     注意力 / 二采一长串校验，种子排在它们后面的话，用户填错种子 +
     模型不兼容 → 报的是模型那条，用户不知道自己**还**填错了种子。
     一次只说一件事；
  3. `h3studio/music_yue2._seed` 同样不再静默回落成随机（原 `except`
     分支直接 `return random.randint(...)`）。
- **回归**：新增 4 例（`tests/test_assetlib_and_seed_guard.py`）。

### 缺陷 B：素材引用不查库 —— 伪造的 asset_id 放行

- **现象**：`POST /api/jobs (mode=flf,
  asset_refs=[{"asset_id":"asset_000000000000","slot":"first_frame"}])`
  → **200**，建了任务（worker 才去报「素材不存在」）。
- **根因**：`asset_ref_guard.check_asset_refs` 写好了，但**没接进**
  `prepare_job_params` —— 素材引用只查了「槽位在不在」，没查
  「这个 id 在素材库里到底存不存在」。
- **修法**：`prepare_job_params` 里接上 `check_asset_refs` —— 查库确认
  条目存在、未删除、类型与槽位匹配，否则返回可读中文原因。
- **连带**：新增 `tests/assetlib_fixture.py`（临时素材库夹具 ——
  真的 `register_asset` 入库拿到真 `asset_id`），把 5 个测试文件里
  编造的 `asset_id`（`"a"` / `"b"` / `"x"`）换成**库里真有的**素材。
  **不是放宽断言** —— 原来那些用例的**意图**（音轨来源不被改掉 /
  尺寸归一生效 / 采样参数回落 / 参考图上限）全部保留，只是素材 id 换成真的。

## 七、已知遗留

1. **素材库不可用时**：素材库挂载点（`/mnt/usb2t/asset_library`）掉线时，
   `asset_ref_guard.lookup_asset()` 查不到素材 → 引用**被拒**（返回
   「尚未入库素材库」）。这是**有意的**：放行等于「没有素材库也能引用外部路径」，
   正好违反需求。代价是素材库掉线期间无法用素材引用功能。
2. **媒体库结果不能直接拖进槽位**：必须先「入库素材库」再拖。用户要求是
   「媒体必须先入素材库」，这是该要求的**直接后果**，不是缺陷；但操作路径
   变长了（媒体库卡片右键「添加到素材库」→ 素材库拖到槽位）。
3. **历史任务不受影响**：老任务的 `params` 里仍躺着 `first_frame: "img-xxx.png"`
   这类直传路径（现场统计 flf/r2v 共 104 条历史任务，其中 18 条 flf 是纯直传）。
   本轮只拦**新建任务**，老任务的**重放**路径（worker 里读 `params["first_frame"]`
   去 UPLOAD_DIR 找文件）**没有**改 —— 改了会让老任务永久无法复用。
   若需要清理，需另开一轮（涉及 worker 侧的历史任务重放兼容）。
4. **`prepare_job_params` 里的 `file_*` 接收分支保留未删**：multipart 解析那几行
   仍在（`server.py` 的 `api_create`），只是 flf/r2v 分支现在会**明确报错**。
   保留是为了让老客户端收到**中文原因**而不是 aiohttp 的 415/400 裸错误。
   `i2i_qwen` / `i2i_h3image` 的直传拒绝逻辑**原样保留**（既有约束，未弱化）。
5. **`state.files` 字段已从前端 state 移除**，但 `web/app.js` 里
   `resetSlotsForMode` 的测试替身（`tests/test_slot_state_reset.py`）仍注入该字段
   —— 那是测试夹具的历史包袱，已在测试里注明，产品代码不再触碰它。
6. **素材引用查库是硬依赖**：素材库挂载点（`/mnt/usb2t/asset_library`）
   掉线时，`check_asset_refs` 查不到素材 -> **所有**带素材引用的提交都被拒
   （报「该媒体尚未入库素材库」）。这是**有意的取舍** ——
   放行等于「没有素材库也能引用外部路径」，正好违反需求。
   代价：素材库掉线期间无法用素材引用功能（媒体库/生成本身不受影响）。
   「遗留项 1」说的挂载点问题在这里从「仅素材库页面受影响」
   扩大到了「素材引用功能受影响」。
7. **非素材的直传通道仍然存在**（`api_create` 的 multipart 解析里
   `file_first` / `file_last` / `file_ref` / `file_refvid` / `file_refaud`
   五个分支都还在）。它们现在**只**用于「让老客户端收到可读的中文原因」，
   所有媒体生成模式都会拒绝它们的值。若将来要彻底删，需要先确认
   没有第三方客户端依赖这些字段名。
8. **既有 flake（本轮未修，如实报出）**：
   `tests/test_page_size.py::TestPageSize::test_auto_refresh_keeps_page_size`
   在基线上以 2/5 的概率 flaky（已用同机同环境各跑 5 次证明）——
   它用固定 `wait_for_timeout` 等自动刷新，负载高时读到中间态。
   本轮 diff 与分页代码零重叠（`grep -c donePage` = 0），故不是本轮引入。
   修它属于「媒体库分页 / 实时刷新」模块的另一个任务范围，本轮**不偷跑**，
   留给 willis 决定是否另开一轮。
