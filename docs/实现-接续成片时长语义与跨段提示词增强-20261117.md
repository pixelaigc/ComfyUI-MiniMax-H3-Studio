## 1. 帧级对账：每帧的来源

### 1.1 完整算式表（场景A：5s → 5s）

```
段  请求秒  请求帧  网格帧  网格余量  TrimAV头裁(重叠)  本段交付  累计交付
0   5.0     120     124     +4       0（链首无重叠）      124      124
1   5.0     120     124     +4       22                  102      226
                                       └─ 124 - 22 = 102
成片（收口前）= 124 + 102 = 226 帧 = 9.4167s
用户口径       = 120 + 120 - 24  = 216 帧 = 9.0000s
差额          = 10 帧 = +0.4167s
```

**差额拆解（两个独立的差，各有来源）**：

| 差 | 帧数 | 来源 | 能否在上游消除 |
|---|---|---|---|
| 网格余量 | 8（每段 4） | H3 段长只能落 **17k+5** 网格：请求 5s = 120 帧，模型只能出 **124 帧**（5.1667s） | **不能** —— 120 帧不在网格上，H3 生成不出这个长度的段 |
| 重叠差 | 2 × 1 处 = 2 | 拷贝桥钉住窗口只接受 **5+17k** 网格（5/22/39/…/124），**24 帧（= 整 1 秒）会被 raise** | **不能** —— Relay-Kit `relay_core.py:411-419` |

### 1.2 上游硬约束的源码级依据

**约束 1：段长网格**（`h3studio/frame_expr.py` 的 `FRAME_EXPR`）

```
max(5, round(a * 24)) + (5 - (max(5, round(a * 24)) % 17)) % 17
```

`h3studio/continuation.py:152-159` 的 `align_frame_count` 是同一套：
`n % 17 == 5` 才原样返回，否则**向上**吸附。120 % 17 = 1 → 124。

**约束 2：钉住窗口网格**（Relay-Kit `relay_core.py:411-419`）

```python
if trim_frames not in GUIDE_RUNS:
    # 不静默吸附：改了帧数就是改了续接窗口，必须让你知道。
    near = snap_guide_run(trim_frames)
    raise ValueError(
        "%d 帧不是 H3 的整步续接窗口。\n"
        "    合法值：%s（= 5 + 17k ...）"
        % (trim_frames, ", ".join(...), hint))
```

`GUIDE_RUNS = (124, 107, 90, 73, 56, 39, 22, 5, 1)` —— **24 不在里面**。

**结论：两个差都无法在上游消除** ⇒ 只能走「可裁剪的解码后补偿」。

### 1.3 场景B（5s → 5s → 8s）的差额

```
段  请求秒  请求帧  网格帧  网格余量  TrimAV头裁  本段交付  累计
0   5.0     120     124     +4       0           124       124
1   5.0     120     124     +4       22          102       226
2   8.0     192     192     +0       22          170       396

差额          = 12 帧 = +0.5000s

```

## 2. 补偿落在哪一端：实测三选一

### 2.1 关键发现：段文件里 TrimAV 已经把重叠头部裁掉了

实测（线上真实产物 `v-h3-studio-000512/000513`）：

```
段1 文件 = 124 帧（网格全量）
段2 文件 = 102 帧（= 124 - 22，TrimAV 裁掉的重叠**头部**）
|段1 末帧 - 段2 首帧| = 0.6685 = **正常相邻帧差**
⇒ 段2[0] 紧接段1 末帧，**接缝连续性成立**
```

### 2.2 三种裁法的实测对比（同一对真实产物）

| 裁法 | 保留区间 | 成片帧数 | 接缝帧差 | 接缝/段内 | 判定 |
|---|---|---|---|---|---|
| **裁链首段尾部 + 裁续接段尾部** | 段1[0..119] + 段2[0..95] | 216 ✅ | **5.7976** | **10.32x** | ❌ **接缝被切断** |
| 裁链首段尾部 + 裁续接段头尾 | 段1[0..119] + 段2[2..97] | 216 ✅ | **5.7976** | **10.32x** | ❌ 同上 |
| **只裁最后一段尾部** | 段1[0..123] + 段2[0..91] | **216** ✅ | **0.6675** | **1.19x** | ✅ **接缝完全不变** |

⇒ **只能裁最后一段的尾部**。

**为什么裁链首段尾部会断接缝**：接缝是「段1 末帧 → 段2 首帧」。
裁掉段1 的尾部 4 帧后，接缝变成「段1 的倒数第 5 帧 → 段2 首帧」——
中间凭空少 4 帧 ⇒ 帧差从 0.67 涨到 5.80。

**只裁末段尾部为什么安全**：
- 接缝（段0→段1、段1→段2）所在的那些段**一帧不裁** ⇒ 接缝像素完全不变；
- 被裁的是最后一段末尾「超出请求时长」的那几帧 ——
  它们本来就是 H3 在网格上多生成的，用户没要求过；
- 实测：成片前 216 帧与旧 226 帧成片**逐帧一致**（最大差 0.0086）。

def formula_total_frames(requested_seconds):
    """成片总帧数 = Σ(各段请求秒数×24) - (段数-1)×24"""
    durations = [float(d) for d in (requested_seconds or [])]
    requested_frames = sum(int(round(d * FPS)) for d in durations)
    return requested_frames - max(0, len(durations) - 1) * FPS


def chain_compensation_plan(requested_seconds, window=DEFAULT_CONTEXT_FRAMES):
    account = chain_duration_account(durations, win)
    current = int(account["total_frames"])

    segment_trim = [0] * len(durations)
    if trim > 0 and len(durations) >= 2:
        segment_trim[-1] = trim          # 只裁最后一段尾部
    keep = [s["delivered_frames"] - t for s, t in zip(account["segments"], segment_trim)]

### 3.3 踩坑：`select` 滤镜会**静默失效**

第一版实现用 `select='lt(n\,216)'` 滤镜做裁剪：

```
ffmpeg rc = 0        ← 不报错！
stderr: video:0KiB   ← 但输出 0 帧
```

`-vf` 传参时逗号被转义吃掉，select 条件全部落空 ⇒ **退出码 0、产物 0 帧**。
坑在于「不报错」而不是「报错」。

**改用 `-frames:v N`**（输出选项，语义明确、可验证）。
`tests/test_cont_duration_exact_frames.py` 里那条真跑 ffmpeg 的用例
就是为了守住这个 —— mock 抓不到「静默失效」。

> 另外实测确认：`select` 必须放在 `fps` **之前**才有效
> （放之后时 `n` 是输出帧序号，实测得到 226 帧 = 等于没裁）。

## 7. 已知遗留

1. **单段链不补偿**：单段视频没有「成片拼接」这一步，段文件本身就是产物，
   它的时长是 H3 的 17k+5 网格决定的（请求 5s → 124 帧 = 5.1667s）。
   这是**所有**视频（不止接续链）都有的模型侧约束，不属于接续成片时长的收口范围。
   界面会如实写出残差 4 帧并点名 17k+5 网格。
2. **补偿只裁最后一段尾部** ⇒ 最后一段末尾那几帧「超出请求时长」的内容被丢弃。
   这是**用户口径本身的要求**（成片 = 请求时长之和 − 每段 1 秒），
   不是丢内容 —— 被裁的帧本来就是多生成的。
3. **音频**：成片音轨仍按「原始参考音频整条 + apad/-shortest」处理，
   尾裁后视频变短 ⇒ 音轨会相应截短（`-shortest` 生效）。
   实测场景A 成片 `format_duration = 9.0`、音轨 `aac` 在位。
4. **`select` 滤镜的坑**：本实现用 `-frames:v`，但如果将来有人改回 `select`，
   会**静默产出 0 帧**。`tests/test_cont_duration_exact_frames.py` 的真跑 ffmpeg
   用例就是守住这一点的。

## 三、修正前的实测现象与根因

### 3.1 用户实测的「只得到 4 秒」

根因**不是**时长算错，而是**成片根本没拼出来**：

（`_finalize_residual_with_outputs` / `_adopt_residual_running`）
只下载产物、标 `status='done'`，**不跑 `_finalize_continuation`**
（不登记分段、不拼完整视频）。

现场取证（线上 DB 全量对拍 22 条接续链）：
- 2 条链的 stage1 无成片（`is_full` 缺失），且这 2 条 stage1
  **全部**落在服务重启窗口内（19:09:21 / 20:34:02）；
- 另 20 条未被打断的链，stage1 **全部**有成片。

用户看到的「4 秒」= 本段真正新生成的 102 帧（4.25 秒）——
潜空间接续**本身是成功的**，只是成片没拼出来。
已在上一轮修复（commit `3576a87` + `058bfe8`）。

### 3.2 本轮要修的：时长账没有单一真源

修正前，「链首段不裁 / 续接段裁掉重叠」这条规则**写了两遍**：

## 四、实测值与口径值的差 —— 两处都是 H3 的硬约束

要让成片**严格**等于用户公式，需要两件事，**两件都做不到**：

### 4.1 段长只能落在 17k+5 帧网格

请求 5 秒 = 120 帧，但 H3 只能生成 **124 帧**（= 5.1667 秒）
—— `align_frame_count` 向上吸附到网格。
→ 链首段交付比请求多 4 帧。

（8 秒 = 192 帧**恰好**在网格上，无余量。）

### 4.2 重叠窗口只能落在 5+17k 帧网格

Relay-Kit 的拷贝桥只接受 5/22/39/56/73/90/107/124 这些窗口。
**24 帧（= 整 1 秒）不在网格上** ——
`/home/ubuntu/comfyui/custom_nodes/ComfyUI-H3-Relay-Kit/relay_core.py:411` 会直接 raise：

```
ValueError: 24 帧不是 H3 的整步续接窗口。
    合法值：5, 22, 39, 56, 73, 90, 107, 124（= 5 + 17k ...）
```

最接近 1 秒的合法窗口是 **22 帧 = 0.9167 秒**
（nonebot 咏唱 h3 的 seg1/seg2 同款：`context_frames: 22`）。

### 4.3 差值公式与实测

```
实测成片 = Σ align(请求帧数) − (续接段数) × 22 帧
与口径的差 = 网格余量 + (1 − 22/24) × (段数−1)
```

| 场景 | 口径值 | 实测帧数 | 实测时长 | 差 |
|---|---|---|---|---|
| 5s | 5.000s | 124 帧 | 5.1667s | +0.1667s（4 帧网格余量） |
| 5s → 5s | **9.000s** | **226 帧** | **9.4167s** | +0.4167s（8 帧余量 + 2 帧重叠差） |
| 5s → 5s → 8s | **16.000s** | **396 帧** | **16.5000s** | +0.5000s（8 帧余量 + 4 帧重叠差） |
| 5s × 4 段 | — | 430 帧 | 17.9167s | —（与线上真实 4 段链产物一致） |

**为什么不「改实现去凑用户的数字」**：要严格命中公式，需要
(a) 链首段交付恰好 = 请求帧数（120 帧不在 17k+5 网格，生成不出）、
(b) 每续接段恰好扣 24 帧（不在 5+17k 合法窗口，拷贝桥会 raise）。
改这两处只能去改第三方节点/模型的网格约束 —— 那是「为凑数字破坏协议」，
不是修复。所以本轮**如实算出实测值 + 与口径的差**，并在界面上把差值原因
说清楚。

## 九、已知遗留

1. **成片时长与口径值有 +0.42s / +0.50s 的固定差**（§四）。
   这是 H3 的两条帧网格硬约束，改不掉；已在界面上显式说明差值与原因。
   若将来 H3 支持非网格段长（或拷贝桥放开 24 帧窗口），差值会自动归零。

2. **成片容器时长比画面长**（9.4542s vs 9.4167s）。
   成片音轨用**原始参考音频整条** + `apad/-shortest`，
   容器时长按音轨算；「成片多长」说的是画面长度，用 `video_duration` 读。

3. **并发 E2E 会互相抢 ComfyUI 队列**。
   实测场景 B 第一次跑失败，报「ComfyUI 队列中已无该任务」——
   那是别的任务把队列抢了，不是时长算错。
   E2E 脚本加了 `H3STUDIO_DUR_SCENARIO=A|B` 开关，分开跑即可。

4. **服务重启仍会打断正在跑的任务**。本轮修的是「打断后成片补不出来」，
   不是「打断本身」。生成期间不要重启服务。

5. **跨段提示词历史无长度上限**。20 段的链会把 20 段提示词一起发给模型，
   可能撞模型上下文上限。当前靠模型自己截断，无显式告警。
