# 文生视频「接续生成」—— 实现说明与验证证据

> 分支：`local/feature/t2v-continue`（独立 worktree：`/root/projects/h3studio-t2v-continue`）
> 基线：`local/maintainer`
> 日期：2026-11-12
> **本分支未部署 8190**（部署由主线统一收口），验证跑在独立测试实例（8199）。

---

## 1. 它是什么

接续 = 把上一段生成的 **AV latent（潜空间）** 落盘，下一段生成时读回来，
把它的尾部**逐 token 拷贝**进本段初始 latent 的开头，并用 ComfyUI 原生的
`minimax_keyframes` 协议把同一段内容钉成条件行 —— 模型读到的是**真实的上一段运动**，
不是「猜」出来的相似画面。

**不是像素续接**（上一段 mp4 → 解码 → VAE 重编码 → 当锚图）。重编码会在每一段
接缝处掉一次画质、偏一次色档；潜空间桥不碰像素。

底层用的是本机已装的 **ComfyUI-H3-Relay-Kit** 的零重编码 latent 桥
（`H3RelayLatentSave` / `H3RelayLatentLoad` / `H3RelayCopyBridge` / `H3RelayTrimAV`），
我们没有重新实现这些节点。

### 3.3 工作流接线（关键）

```
MiniMaxH3ImageToVideo ──┬─→ H3RelayCopyBridge ─┬─[0]→ SamplerCustomAdvanced.latent_image
  (latent)              │   (300:bridge)        ├─[2]→ trim_frames
                        │                       ├─[3]→ BasicGuider.conditioning
                        └─[0]← H3RelayLatentLoad ──[0] (上游潜空间)
                                                       ↑
                          SamplerCustomAdvanced ─[0]→ H3RelayLatentSave (落盘下一段接力棒)
                                                       ↑
                          VAEDecode ─[0]→ H3RelayTrimAV ─[0]→ CreateVideo.images
                          VAEDecodeAudio ─[0]→ H3RelayTrimAV ─[1]→ CreateVideo.audio
```

要点：
* 拷贝桥接在 **latent 与采样器之间**（不是采样器之后）；
* `conditioning` 走拷贝桥第 4 路（钉帧后的条件）；
* 裁重叠在 **decode 之后**，且**音画同裁**（`H3RelayTrimAV` 的 audio 输入必须接上，
  否则画面裁了音频没裁 → A/V 不同步）；
* `mask_mode="hard"`（钉住区零重绘）。

已对本机 ComfyUI 0.37 的 `/object_info` 做过 schema 校验：新增 4 个节点的
全部输入名、必需/可选、输出索引全部合法；所有连线指向的节点存在且输出索引在范围内。

## 4. 关键设计决定

### 4.1 为什么钉住窗口只认 5+17k 网格

H3 的视频 latent 每步覆盖的像素帧按 **(1,4,4,4,4)** 循环，5 步一周期 = 17 帧。
不在网格上的窗口**切不出来** —— 切出来会错位，表现为**整体位移的接缝**。

合法窗口：5 / 22 / 39 / 56 / 73 / 90 / 107 / 124。生产档用 **22**（≈0.92s，
Relay-Kit 实测「nearly seamless」）。

段长走 **17k+5** 网格（124/243/362…）时，`total_steps − window_steps` 恒为 5 的倍数
⇒ 尾段起点天然落在 5 步周期边界 ⇒ 不需要额外对齐。

### 4.2 为什么二采（selflift）不能接续

二采走 `SelfLiftH3Sampler`：低分辨率一采 → 抬升 → 高分辨率二采，节点内部做了
`seed+1` 重新加噪，潜空间相位与标准采样路径**不同源**。把这种 latent 当
`context_latent` 喂给拷贝桥，切出来的尾段帧跨度与写入位置对不上 → 位移接缝。

所以：**二采产物一律不显示「接续」按钮**，服务端也直接拒绝并给出中文原因。

### 4.3 为什么按钮显隐只听服务端

「能不能接续」要同时看四样：模式、是不是二采、潜空间文件在不在、有没有链信息。
潜空间在 ComfyUI 的磁盘上，**前端看不到** —— 前端自己判断必然和服务端不一致。

服务端逐任务判定（`continuation_info.can_continue`）是权威，且**没有异步竞态**。
（早期版本额外叠了一层异步能力探测，导致 1280px 那档首屏按钮不出现 —— 已修。）

### 4.4 为什么段号由服务端重算

前端回填的 `continuation` 描述的是**上一段**；本段是新的一段，段号必须 +1、
接力棒必须指向上游。前端可以随便填数字 → 段号必须由服务端按**任务记录**重算，
否则用户改个数字就能让接缝错位。

### 4.5 上下文区为什么不提供手动添加入口

用户需求明确「只能从生成库添加，用户手动不可添加」。
接续上下文包含潜空间落盘位置这类**服务端才知道**的信息，手动填必然对不上。
所以前端**刻意**不提供任何添加入口 —— 该区唯一的按钮是「清除」。

## 5. 边界与错误处理

| 场景 | 行为 | 文案 |
|---|---|---|
| 二采产物 | 不显示「接续」按钮；服务端拒绝 | 「二采（SelfLift 渐进分辨率采样）的潜空间与标准采样路径不同源，接续会出现接缝位移 —— 二采产物不支持接续。」 |
| 潜空间文件被清理 | 不显示「接续」按钮；接口返回明确原因（含**真实路径**） | 「这段视频的接续潜空间文件已不在（/…/stage_00001.safetensors）—— 可能已被清理，或产物是二采（二采不支持接续）。请改用「复用参数」重新生成一段。」 |
| 上线前的历史任务（无链信息） | 不显示「接续」按钮 | 「这段视频没有可接续的潜空间（不是用「接续」生成的，或潜空间已被清理）—— 请改用「复用参数」重新生成一段。」 |
| 非视频模式 | 不显示「接续」按钮 | 「只有视频类产物支持接续。」 |
| Relay-Kit 节点没装 | 按钮不出现；`/api/continuation/state` 返回原因 | 「本机 ComfyUI 里缺少接续所需的节点：…（ComfyUI-H3-Relay-Kit）—— 接续功能不可用。」 |
| 拼接失败 | **不影响**本段产物；本段仍在生成库 | 日志 `[接续] 拼接失败: …` |

## 7. 已知限制

1. **只支持文生视频（t2v）**。首尾帧生成（flf）/ 参考生视频（r2v）走的是
   `workflows.py` 里的旧工作流路径，那两条路**还没接桥**。
   用户需求写明「未来参考生视频/首末帧生视频也应可接续」—— 补上桥之后把
   `continuation.CONTINUABLE_MODES` 加进去即可（前端无需改）。
   **现在硬说它们可接续会导致「点了之后静默退化成普通生成」** —— 那是最坏的失败。

2. **接续窗口固定 22 帧**（≈0.92s 钉住）。没有做成可调 —— 窗口越大，
   钉住区越长、可生成的新内容越少。

3. **完整视频用 ffmpeg concat 重新编码**（CRF 18）。分段视频各自音画同裁，
   拼接不会累积 A/V 偏移；但完整视频经过一次重编码，画质比分段略低。

4. **潜空间文件不自动清理**。每个 5s 段约 4.8 MB；链越长占用越大。
   删除任务时**不会**自动删潜空间（避免误删还在用的链）。
   ⚠️ 分叉后每一段都是独立目录，占用按**分支数**增长（不是按链长）。

5. **只接续上一段**，不做「多段历史锚」。拷贝桥的外观锚现在**显式**读链首段
   那一份（每段一个目录后不能再靠节点自动读），防长程漂移。

6. **测试实例与线上共用同一个 ComfyUI**（8188）。真实生成会占用 GPU。

7. `h3studio/continuation.py` 里的 `pixel_frames()` / `tail_aligned()` /
   `continuation_frames()` 是**协议层纯函数**，生产代码里没有调用方，
   但测试锁定了它们的语义（帧数换算的依据来自 Relay-Kit 源码），
   留着是为了「帧数账」有可验证的单一真源。

8. **外观锚缺失时静默降级为「无锚」**（不报错）。锚是防长程漂移的加分项，
   不是接续正确性的必要条件 —— 缺锚只影响长程一致性，不会接错段。

9. **接续要求本段与上一段分辨率完全一致**（2026-11-12 第三轮新增的硬约束）。
   潜空间桥是逐 token 拷贝上一段尾部，latent 分辨率固定 —— 跨分辨率
   接续在 Relay-Kit 里会被直接拒绝。
   三道闸会拦下不一致：点「复用参数」清接续上下文、提交前比对面板尺寸、
   服务端提交时校验。不一致时给出中文原因并**不建任务**（不占 GPU）。
   ⚠️ 这意味着「接续后改分辨率」这条路走不通 —— 要改分辨率就用
   「复用参数」独立生成一段。

## 7.1 D1 修复记录：分支接续的潜空间落盘坐标冲突（2026-11-12 第二轮）

### 缺陷现象

同一条链**分叉**时（对同一段点两次「接续」得到 B1 / B2），两个分支继承了
相同的 `chain_id` 与 `stage_index`，写入**同一个** `stage_00001.safetensors`
互相覆盖。再对 B1 接续得到的 C1 首帧实际来自兄弟分支 B2
（灰度 MAE：C1首帧 vs B1末帧 = 38.65，vs B2末帧 = 2.08，偏离 18.6 倍），
且**不报错**、界面全程显示成功 —— 静默的错误内容。

### 根因

落盘坐标是「链 id + 链段号」两元组。分叉时两兄弟的链 id 相同、段号也相同
→ 坐标必然相同。

### 参考实现

nonebot 插件 `nonebot_plugin_novelai` 的「咏唱 h3」长视频
（`h3_executor.inject_chain_segment_to_workflow` + `h3_chain_video.py`）
用**两条**机制防覆盖：

1. `run_id = long_id`（一部片子一个目录）+ `stage_index = 段号-1`；
2. **长视频级互斥锁**（`h3_chain_video._get_lock`），同一长视频串行执行。

但它的链是**线性**的（只允许从第 N 段接第 N+1 段，且禁止并发跑同一个长视频），
锁挡不住「先后两次」的分叉。本项目的链**允许分叉**（用户需求第 7 条），
所以不能照搬「一个目录 + 段号」。

### 本次修复：每段一个专属目录

| 项 | 旧 | 新 |
|---|---|---|
| 落盘坐标 | `(链id, 链段号)` | `(段任务id 派生的目录名, 0)` |
| 目录 | `relay_kit/h3studio_<chain_id>/stage_<N>.safetensors` | `relay_kit/h3studio_s<job_id>/stage_00000.safetensors` |
| 读回 | 按链段号推 | **上游任务记录里的精确坐标**（`source_latent_path`） |
| 拼接 | 链首段的**共享账本** | 沿 `source_job` 指针回溯的**血缘** |

- **写**：本段写**自己**的目录（`latent_run_id` 由本段任务 id 派生）。
  兄弟分支各写各的目录 → 结构上不可能互相覆盖。
- **读**：`H3RelayLatentLoad` 用 `explicit_path` 精确指向上游那**一个**文件。
- **拼接**：每段把分段路径记在**自己**的任务记录里，拼接时沿 `source_job`
  回溯血缘 —— 旧实现把分段列表存在链首段的**共享可变列表**里，
  分叉后 B2 会被混进 C1 的「完整视频」（同一类静默错误，本轮一并修掉）。
- **外观锚**：每段一个目录后，拷贝桥不能再靠 `run_id` 自动读链首段，
  改为显式加一个 `H3RelayLatentLoad` 节点读链首段那份接进
  `ref_anchor_latent` 槽位；锚缺失时降级为无锚（不报错）。
- **旧产物兼容**：上线前的任务没有 `latent_run_id` → 仍按老的
  「链目录 + 链段号」读，老产物照常可接续。

### 顺带修掉的一个显示 bug

`continuation_state` 的累计帧数对**链首段**也减了钉住窗口
（22 帧）。链首段没有上游、根本没裁过。实测对照（真实产物）：
2 段完整视频 ffprobe = 226 帧，旧算法报 204；3 段 ffprobe = 328，旧算法报 306。


## 7.2 混合态与错误文案修复记录（2026-11-12 第三轮）

### 缺陷现象

独立复验（自建实例 8201）报告两条：

1. 接续后再点「复用参数」（两张不同卡片）→ 提交后任务失败，生成库卡片显示
   ```
   'str' object has no attribute 'get'
   ```
2. 错误信息提取本身有基线缺陷：**向前端展示原始 Python 异常文本**。

### 根因（两条独立根因，叠加成用户看到的那句话）

**根因 A —— ComfyUI 的消息形状被读错了**

ComfyUI 的 `PromptQueue.status.messages` 里每条消息是**二元组**
`[事件名, 数据字典]`：

```python
["execution_error", {
    "node_type": "H3RelayCopyBridge",
    "exception_message": "拷贝桥禁止跨分辨率：上段 768x448 ≠ 本段 1024x576\n",
    "exception_type": "ValueError",
    "traceback": [...], "current_inputs": {...}, ...
}]
```

而本项目原来的提取代码把它当成了「`m[0]` 是字典」：

```python
(m or [{}])[0].get("x", "")   # m[0] 其实是字符串 "execution_error"
```

于是 `.get()` 作用在 str 上 → 抛 `AttributeError` → 被 worker 的兜底
`except Exception as e: str(e)` 吞掉 → **真正的原因被彻底丢掉**，
只剩一句 Python 报错。

> 实测证据（本机 ComfyUI `/history`）：
> `af4df18b-ef2` 的 `exception_message` 是
> `拷贝桥禁止跨分辨率：上段 768x448 ≠ 本段 1024x576`（Relay-Kit 的
> `relay_core.py:2809`）—— 这个原因**一直都在**，只是被读错了形状。

**根因 B —— 「接续」与「复用参数」没有互斥语义**

点「接续」后 context 挂在左侧；再点**另一张**卡片的「复用参数」，
复用参数只改左侧控件（尺寸/模型/步数…），**不清 context**。
于是提交时：**params 来自 B 卡片、continuation 来自 A 卡片**。

混合态的实测载荷（`/tmp/acceptance/acc-data/jobs.db` 里的
`ac3b9cb7f72d`）：

```json
{
  "width": 1024, "height": 576,          // 来自 B
  "continuation": {
    "source_job": "10b67841c757",          // 来自 A（768x448）
    "source_latent_path": ".../h3studio_s10b67841c757/stage_00000.safetensors"
  }
}
```

潜空间桥逐 token 拷贝上一段尾部，latent 分辨率固定 → 跨分辨率必然被拒。

### 修法

| 层 | 改动 | 文件 |
|---|---|---|
| 错误提取 | 新模块：按**真实形状**提取（不假设固定下标，两种形状都认）+ 中文化 | `h3studio/comfy_errors.py`（新） |
| 错误出口 | 三处调用点统一走它：worker 主路径 / 批次路径 / ws 进度监听 | `server.py` |
| 前端互斥 | 点「复用参数」→ **清掉接续上下文** | `web/app.js` + `web/continuation.js` |
| 前端闸 | 提交前比对尺寸，不一致**当场拦下**（不浪费一次生成） | `web/continuation.js`（`checkSubmitConsistency`） |
| 服务端闸 | `_prepare_continuation_params` 独立校验本段与上游分辨率 | `server.py` + `h3studio/continuation.py`（`size_mismatch`） |
| 顺带 | `applyConfig` 归零加速 LoRA（混合态的又一种形态） | `web/video-panel.js` |
| 顺带 | toast 不再退到**阻塞式** `alert`（自带非阻塞实现） | `web/continuation.js` |

**为什么「复用参数时清 context」是对的语义**：
两个动作本来就互斥 —— 复用参数 = 照这张卡片**独立重生成**（含提示词）；
接续 = 拿某一段的**潜空间**当接力棒续下一段。用户点「复用参数」
= 表达「我要照这张重新生成」，此时留着别的段落的接力棒只会制造混合态。

**三道闸的分工**：
1. 前端「复用参数清 context」→ 解决**用户操作**造成的混合态；
2. 前端「提交前尺寸闸」→ 解决用户**自己改手填宽高**造成的不一致；
3. 服务端「尺寸校验」→ 前端被绕过（直接调 API）时仍然拦得住，
   且**提交时**就 400，不建任务、不占 GPU。

### 复现-修复对照（真实执行，非推演）

| | 修复前 | 修复后 |
|---|---|---|
| 混合态提交 | 建任务 → 跑一次生成 → 失败 | **提交时 HTTP 400**，不建任务 |
| 用户看到的文案 | `'str' object has no attribute 'get'` | `接续失败：上一段是 768×448，本段是 1024×576 —— 潜空间桥不能跨分辨率接续（逐 token 拷贝上一段尾部，latent 分辨率必须一致）。请把输出尺寸改成 768×448，或改用「复用参数」重新生成一段。` |
| 正常接续（尺寸一致） | 跑通 | **仍然跑通**（226 帧完整视频，真实生成） |
| 浏览器「复用参数」后 | context 仍挂着（混合态） | **context 被清掉**，提交载荷无 `continuation` |

浏览器脚本：`tests/verify_mixed_state_browser.py`（375 / 1280 两档）
