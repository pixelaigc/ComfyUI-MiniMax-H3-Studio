## 1. 改动清单

### 1.1 数据库 schema（向后兼容）

**新建表**（只加表，不动任何既有记录）：

```sql
CREATE TABLE IF NOT EXISTS job_favorites (
    job_id TEXT PRIMARY KEY,     -- 一个任务最多一条收藏记录
    created_at REAL NOT NULL    -- 收藏时刻
);
```

**为什么新建表而不是给 `jobs` 加列**：
- `jobs` 是「任务记录」，收藏是**用户对产物的标记** —— 生命周期不同；
- 加列要改所有 `INSERT jobs` 的地方（散落在 `server.py` / `agent` / 脚本里），漏一处就丢标记；独立表只有一处写入点；
- 独立表**天然向后兼容**：老库不需要迁移，现有记录一条都不动。

### 1.2 后端

| 文件 | 改动 |
|---|---|
| `h3studio/favorites.py`（新增 114 行） | 收藏读写：`ensure_table` / `set_favorite` / `is_favorited` / `favorite_ids` / `count` / `remove_for_job` |
| `h3studio/media_cleanup.py`（+50） | `_favorited_ids()` + `preview()`/`cleanup()` 共用「已收藏则跳过」判据；返回值新增 `skipped_favorited` |
| `server.py`（+151） | `init_db()` 建表；`api_list` 支持 `?favorites=1` 过滤；`api_list`/`api_get` 下发 `favorited` 字段；`api_delete` 删任务时清孤儿收藏行；3 个新接口 |

**新接口**：

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/jobs/{id}/favorite` | 单个收藏 / 取消收藏（`{"favorited": true\|false}`） |
| POST | `/api/jobs/favorite/batch` | **批量**收藏 / 取消收藏（`{"job_ids": [...], "favorited": false}`），逐个 id 回报结果 |
| GET | `/api/jobs/favorites` | 收藏总数 + id 列表 |

**路由顺序**：`/api/jobs/favorite/batch` 必须**先于** `/api/jobs/{id}/favorite` 注册 —— aiohttp 按注册顺序匹配，`{id}` 会把 `"favorite"` 当成 id 吃掉。

**`api_list` 的 `favorites=1`** 用子查询 `id IN (SELECT job_id FROM job_favorites)`，而不是前端二次过滤 —— 二次过滤会破坏分页（先取全量再过滤，页内条数就不准了）。

### 1.4 「左侧收藏栏」的最终落点与理由

需求说「若现场 UI 结构与上述描述不符，以现场代码为准实现『在左侧新增一栏收藏视图』」。

**落点**：左侧「素材」分组内、`#navAssets`（素材库）之后新增 `.nav-item#navFavorites`，**进入的是生成媒体库的「收藏」标签**（`state.tab = "favorites"`），不是另开一个页面。

**理由**（现场代码决定）：
1. 需求要求「沿用生成媒体库既有的卡片交互（查看、打开详情模态框、右键、筛选/搜索、分页），并保留类型区分」。另开页面 = 这些交互要重写一遍 = 两套实现必然漂移。复用同一个标签 → 卡片、详情模态框、右键菜单、筛选条、分页全是**同一份**代码，类型区分天然保留。
2. **不能新开左侧分组** —— `tests/test_sidebar_fold.py` 断言顶层分组恰好 7 个，新开分组会直接打破那条契约（已实测确认：改动后仍是 7 个）。
3. **视觉约定**：DOM 断言实测 —— 与「素材库」同一 `nav-item` 类、同款 15×15 SVG 图标、同字号（13.5px）、同分组（`assets`）。

## 3. 修掉的真实缺陷（都是浏览器实测暴露的，不是推演）

1. **骨架卡也渲染收藏选择框** —— 骨架 id 是假的 `__skeleton__N`，「全选本页」会把假 id 一起选中，批量请求带上不存在的 id。
2. **`GET /api/jobs/{id}` 没带 `favorited`** —— 只有列表接口带，同一任务在两个接口里收藏状态不一致。
3. **★ 标识要等下一次轮询才出现** —— 实测线上一次 `POST /api/jobs/{id}/favorite` 在浏览器里要 **0.7~17 秒**（浏览器对同一 host 只有 6 条并发连接，页面后台 `/api/image-loras` 要扫本机 LoRA 目录实测 ~0.9s，把连接占满）。用户点完盯着卡片等十几秒 → 看起来像「点了没反应」。
   → 改成**乐观更新**（先就地更新 ★，服务端回来再刷新对齐真值），**失败会回滚 ★** 并给出明确提示。
4. **收藏完再右键仍显示「添加到收藏」** —— 菜单文案读的是闭包里的 `job.favorited`（渲染时快照），与界面上的 ★ 自相矛盾。
   → 菜单文案与目标状态改为**现读 DOM 上的 ★**。
5. **收藏视图的勾选框点不动** —— `label` 上的 `onclick="return false"` 会**取消默认行为**，而复选框的勾选正是靠默认行为完成的。浏览器实测对照：`return false` → 点不动；`stopPropagation` → OK；无 onclick → OK。
   → 去掉该标记；并补了一条**手动点勾选框**的断言（原来的「全选本页」断言抓不住，因为它走 JS 直接改状态，绕过了「点勾选框」这条路）。

## 8. 已知限制与如实说明

### 8.1 取证副作用：线上历史产物被清理过一次（已恢复）

需求 4 要求取证「执行『管理 → 清理』后收藏项仍在」—— 这必须**真的调一次清理**（预览不足以证明）。而既有清理功能的语义就是「删除未收藏的全部产物」，所以**线上 255 条历史记录与 306 个产物文件被删掉了**。

**已恢复**：各 worktree 的 `data/outputs/` 是同一批产物的拷贝，从 `/root/projects/h3s-clean-baseline`（2026-11-15 快照，272 条 jobs / 305 个产物文件全部在位）用 `scripts/restore_live_products.py` 恢复到线上库（`INSERT OR IGNORE`，只补「产物文件真实存在」的记录 —— 补一条指向不存在文件的记录会让媒体库出现「点开是 404」的假卡片，比不补更糟）。

**恢复后的线上状态**：`jobs` 272 条、产物文件 305 个全部可取（`GET /files/...` 返 200）。但**恢复的记录是 11-15 的快照**，期间（11-15 ~ 11-20）新增的那部分历史记录**没能恢复** —— 那部分只在被删除前的库里，`.recover` 也救不回来（SQLite 页已复用）。**这是本次取证造成的真实数据损失，如实报备。**

### 8.2 既有清理功能在需求 4 之外未改动

清理的三个口径（全部 / 按月数 / 失败取消）只增加了「跳过已收藏」这一个判据，其余行为完全不变。**收藏取消后卡片立即重新纳入清理范围**（已实测）。

### 8.3 「收藏」是任务级，不是文件级

批次卡片与批次缩略图都指向同一个 `job.id`，所以收藏的对象是「生成媒体库里的一张卡片」。无论右键批次缩略图还是卡片预览图，收藏的都是同一个任务，★ 也出现在同一张卡片上。

### 8.4 失败/无产物的卡片右键不弹菜单

这是**既有行为**（右键菜单只挂在 `img`/`video`/`audio` 媒体元素上），不是收藏功能引入的。失败任务没有产物，右键不弹菜单。

### 8.5 首次收藏标记未做跨库迁移

`job_favorites` 是新表，老库不需要迁移 —— 但**历史上从未有过收藏数据**（功能是新增的），所以没有"迁移"这回事。

### 8.6 未做的事

- **没有新增额度探针任务**，没有新增生成作业（① 的提交请求被 `page.route` 拦下，不真的建任务）。
- **没有修改素材库（assets）** —— 收藏与素材库是两套独立机制。
- **没有做收藏的导出/分享**（需求未要求）。
