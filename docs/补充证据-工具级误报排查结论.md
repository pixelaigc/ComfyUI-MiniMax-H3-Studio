## 结论二：真正的缺陷有两个

### 缺陷 A：负面提示词「不生效」被当成**硬失败**拦下任务

`h3studio/agent_schema.py:1196-1210` 的注释原文写着：

> 关键：**不因为「该族不支持负面提示词」就拒绝任务** —— 用户要的是图/片/曲，
> 负面提示词只是附加诉求。但必须**如实告知**它不生效。

`docs/内置多模态Agent-接口契约.md:568` 也写着：

> | `negative_not_supported` | 400 | 该模式/模型版本的负面提示词**不生效**（**不拦任务**，只如实告知） |

**但实现与自己的注释/契约相反**：
`validate_params()` 把 negative 问题塞进 `issues` 列表 →
`_precheck_tool_args()` / `_validate_create_job_args()` 只要 `issues` 非空就
`raise AgentError(..., code="invalid_params")` → **任务被拦下，一个都没建**。

契约里 `negative_not_supported` 标的是 400 + 「不拦任务」，
`resolution_upscaled` 标的是「—（允许）」—— 说明 issues 列表里本来就有
「只是告知、不该拦」的**软问题**与「必须拦」的**硬问题**之分，
但代码**没有区分**，一律拦。

后果链：模型拿到硬失败 → 不会改参数（提示词里已经给了可执行替代方案，
但任务根本没建）→ 反复用同样的错参数重试 5 次 → 撞上 8 步上限 →
用户看到「5 个红色 ✗ + 红色条 + 已截断」。

**这才是这轮截图的根因**：不是「工具级误报」，而是「工具级如实报错，
但那个报错本身是过度拦截 + 反复重试 → 步骤耗尽」。

### 缺陷 B：「步骤上限 / 截断」被渲染成**红色失败条**

后端 `h3studio/agent.py:2783`：
```python
if status == "truncated" and truncated_reason:
    error = truncated_reason      # truncated 的说明被塞进 error 字段
```
前端 `web/agent.js:379`：`${msg.error ? renderError(msg) : ""}`
→ `renderError` 渲染成 `.ag-error`（`web/style.css:1916`，背景 `#fdecec` 纯红）。

语义完全错位：
- `status = "truncated"` → 徽章是黄色「已截断」（warn），**不是**失败；
- 但同一条消息底部的说明条用的是**红色**失败样式。
- 「已达到步骤上限，返回已完成的部分结果」是**中性/警告**语义，
  不是「执行失败」。

用户要求里的第 2 点（「步骤上限截断不应显示为失败」）= **确实成立，是真缺陷**。

## 结论三：5 次 create_job 里的重复调用

5 次 create_job 参数**完全相同** → `repeat_count` 递增。
`REPEAT_LIMIT = 3`：第 2 次给 nudge，第 3 次（`repeat_count >= 3`）判定打转并
`return "truncated", "模型重复调用同一工具..."`。

但实测截图里 5 次都出现了，且提示条是「已达到步骤上限（8 步）」而不是
「模型重复调用同一工具」—— 说明**打转检测没生效**。
原因：nudge 分支在 `steps.append(...)` 之后 `continue`，
`repeat_count` 的自增发生在**函数调用前**（`signature == repeat_signature`），
但 5 次调用的 `call["arguments"]` 里含**不同的 prompt**？需要复核。
（本次不作为修复目标 —— 属于「模型是否该被打转拦下」的策略问题，
  与「误报失败」无关。留作遗留项。）

## 修复方案（本次）

1. **缺陷 A**：区分「软问题（只告知）」与「硬问题（必须拦）」。
   `negative_not_supported` / `negative_needs_cfg` / `resolution_upscaled`
   归为**软问题**：不再拦任务，改成**在工具结果里如实告知**，
   让任务正常建出来、界面对应工具块显示 ✓。
   硬问题（非法取值 / 超上限无放大路径 / 缺参考图 / 未知模式…）**照旧拦**。

2. **缺陷 B**：`truncated` 的说明改走**中性提示条**（黄色），不再用
   `.ag-error`（红色）。真正的失败（`status=failed`）继续用红条。

3. **工具级判定**（用户第 3 点要求）：`create_job` 的 ✓/✗ 仍以**工具是否
   真的建出了任务**为准 —— 权威核对 = jobs 表。
   本次实测证明该判定**没有误报**（5 次失败 → jobs 表 0 条 → ✗ 正确）。
   但为满足「以数据库权威记录为准」的要求，补一条**回归测试**锁住它：
   工具返回成功但库里查不到 → 不标 ✓（仍标 ✗），
   工具返回失败但库里真有记录 → 不标 ✗。

## 遗留项

- 「重复调用同一工具」打转检测在实测 5 次同参调用下未触发（提示条是步骤上限
  而非「重复调用」）。属模型行为策略问题，与本次「误报失败」无关，未修。
