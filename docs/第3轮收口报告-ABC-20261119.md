### 3.1 C-1【严重】Agent 的 `cancel_job` **不终止** longfilm 的 ffmpeg 进程

**根因**：longfilm **不经过 ComfyUI** —— 它是 `asyncio.create_subprocess_exec`
起的 **ffmpeg 子进程**（`server.py` 的 `run_longfilm`）。
服务端有**两条**取消实现：

| 实现 | 入口 | longfilm 分支 |
|---|---|:--:|
| `api_cancel` | HTTP `DELETE /api/jobs/{id}`（面板） | ✅ 有 |
| `cancel_job_record` | **Agent 的 `cancel_job` 工具** | ❌ **没有** |

⇒ **后果**：Agent 走的那条路径**只**把 DB 状态改成 `canceled`，
**ffmpeg 进程继续跑到结束**。用户以为「已终止」，实际还在烧 CPU
（合成一段长片可能耗几分钟）。

**修法**：抽出共用的 `_terminate_longfilm_process(job_id)`，两条路径都调它
（**两份实现必然漂移 —— 这正是本缺陷的成因**）。
`cancel_job_record` 补上 longfilm 分支，并返回 `terminated_process` 标记。

**线上双向实证**（真实 ffmpeg 子进程，live 服务进程内）：

| | 修复前（monkeypatch 模拟 `91f5060` 的 `cancel_job_record`） | 修复后（线上已部署） |
|---|---|---|
| 返回 | `{"status":"canceled","ok":true}` | `{"status":"canceled","ok":true,**"terminated_process":true**,"message":"已取消长片合成"}` |
| **ffmpeg 进程** | ❌ **仍在跑**（PID 2832272 活着，`ps` 可见完整 ffmpeg 命令行） | ✅ **已终止**（进程消失，returncode=255 = SIGTERM） |
| 判定 | **❌ 缺陷复现** | ✅ **修复生效** |

对照：HTTP 的 `api_cancel` 路径（面板取消）修复前后都正常
（它本来就有 longfilm 分支；实测 ffmpeg PID 2828277 → 取消后进程消失）。

证据：`evidence/20261119-r3-env-diff/c1_live_verification.json`
+ 两个探针脚本（`live_probe_fixed.py` / `live_probe_prefix_sim.py`）。

**回归**：`tests/test_cancel_longfilm_process.py`（新增 5 条，用假进程对象，
不起真 ffmpeg、不连真库）

| 变异 | 结果 |
|---|---|
| M1 删掉 `cancel_job_record` 的 longfilm 分支 | **3 条红** ✅ |
| M2 让 `_terminate_longfilm_process` 变成空操作 | **2 条红** ✅ |

**commit**：`d05868b`

### 3.2 C-2【中等】CPU「型号来源」显示本机绝对路径

**根因**：`h3studio/hardware.py::detect_cpu()` 在 cpuinfo 命中时写
`source = CPUINFO_PATH`（= `"/proc/cpuinfo"`）。该字段经 `/api/hardware` 下发，
被前端 `web/app.js` 渲染成「**型号来源 /proc/cpuinfo**」。

**线上实测确认**：

```
GET http://127.0.0.1:8190/api/hardware
  -> cpu.source = "/proc/cpuinfo"
```

（与 R2 修的「出处」/「位置」同类：内部实现细节被原样透出。）

**修法**：
- **主修**：`source = "cpuinfo"` —— 只保留**来源名**，
  「型号是怎么读到的」这个语义没有丢；
- **兜底**：出口加一道「`source` 绝不能是路径」的闸（以 `/` 开头 → basename）——
  因为 `source` 是自由文本，将来加新取值很容易又写成某个 `/proc/...`；
- **连带修正**：`tests/test_hardware.py` 里那条
  `assertEqual(info["source"], hw.CPUINFO_PATH)` —— 它**锁死了路径泄漏**。

**线上实证（部署后）**：

```
GET http://127.0.0.1:8190/api/hardware
  -> cpu.source = "cpuinfo"        （修复前 = "/proc/cpuinfo"）
  -> 含本机路径的 source: 0 条
  -> cpu.name = "Intel(R) Core(TM) Ultra 9 285K ×24"（其余字段不变）
```

同时复核 `/api/video-options`：含本机绝对路径的 source **0 条**（第 2 轮 R2 的
清洗仍然有效）。

**回归**：`tests/test_hardware.py` 33 → **35 passed**
（新增 `test_source_is_never_a_path`，4 条分支全覆盖）
变异自证：把 `source` 改回路径且去掉出口兜底 → **2 条红** ✅

**commit**：`d05868b`
