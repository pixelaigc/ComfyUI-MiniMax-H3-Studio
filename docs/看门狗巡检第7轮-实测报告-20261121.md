## 3. 已修并上线

### 3.1 修的什么（三条真实根因）

**根因 1 —— 载荷里 93% 是一段没人要的噪声**
`z-image-effects/zit-deepthroat-31epoc-k3nk.safetensors` 的
safetensors `__metadata__["_"]` 是 **5,668,456 字节**的随机噪声标记。
全仓检索（`web/*.js`、`server.py`、`h3studio/**`、`tests/**`、`scripts/**`）
对 LoRA 条目的 `metadata` 字段**零引用** —— 前端 `imgLoraMeta()` 只取具名字段。
去掉 `metadata` 后整包是 226,411 字节 ⇒ **这一个字段占 93%**。
且扫描时要 JSON 解析它：`cProfile` 实测单次 `json.loads` 占 **0.43 秒**
（整个扫描的一半以上）。

**根因 2 —— 每次请求都重新全盘扫一遍**
扫描 712 个 safetensors + 465 次 `open()` 读头，0.7~1.0 秒。

**根因 3（顺带发现，同一处）—— 任务提交路径 2.2 秒**
`workflows._lookup_lora_meta` 直接调三个未缓存的 `list_*_loras`，
实测**单次 2.225 秒**；它在**每个工作流构建点**都被调（Z-Image/Qwen/MOSS 三处）
⇒ 一次提交 3 × 2.2s。

### 3.2 怎么修的

| 改动 | 文件 | 要点 |
|---|---|---|
| metadata **单字段**上限 4096 B | `h3studio/loras.py` | 短字段原样保留；`modelspec.architecture` / `ss_base_model_version` **显式豁免**（参与扫描内部 `base` 兜底判定）；截断后带 `_truncated` + `_original_length` —— 「被截断」是**可观测事实**，不是静默丢数据 |
| **目录指纹**扫描缓存 | `h3studio/loras.py` | 指纹 = 所有 loras 目录下每个 `.safetensors` 的 `(路径, mtime_ns, size)`，实测成本 **0.032 秒**（扫描的 4%）。**指纹变了自动作废** ⇒ 装完 LoRA **立刻可见**，不靠等 TTL。另有 60 秒 TTL 上限兜住「模型目录配置变了」这类指纹覆盖不到的情况。写回缓存前**再校验一次指纹**，避免把扫描期间的旧快照当新快照 |
| `_lookup_lora_meta` 走缓存入口 | `h3studio/workflows.py` | 2.225s → 0.075s。⚠️ **必须取「效果类 + 加速类」并集** —— 调用方靠 `kind == KIND_ACCELERATION` 拒绝「把加速 LoRA 当效果 LoRA 用」，只取 `effect` 会让那道闸门失效 |
| 缓存 key 含 `scan_fn` 本身 | `h3studio/loras.py` | 测试把 `list_z_image_loras` 换成假实现时**自动换 key**，不会命中旧缓存 |
