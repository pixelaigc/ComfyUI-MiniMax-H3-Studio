## 一、用户反馈的两个缺陷

### 缺陷①：接续段时长叠加 —— 5 秒接续 5 秒只得到 4 秒

用户实测：**19 点**先生成一段 5 秒视频，点该视频「接续」，再次生成目标 5 秒，
理论上应得到 9 秒，实际**只得到 4 秒**。

### 缺陷②：提示词「增强」不带历史段落上下文

用户需求：接续时用户先在提示词框输入本段新内容提示词，再点「增强」；
增强时要把**此前所有段落的提示词**一并提供（第 4 段就把前 3 段都带上），
再基于全部提示词做专业增强，以保证跨段内容一致性。

## 二、缺陷① 根因（现场取证，不沿用历史结论）

### 2.1 取证方法

对线上 DB（`/root/projects/comfyui-minimax-h3-studio/data/jobs.db`）
做**全量接续链对拍**：把每条链的 stage1 是否有 `is_full` 成片条目、
与 systemd 服务重启时刻做交叉。

### 2.2 关键数据（22 条接续链）

| 链 | stage1 有成片？ | stage1 运行区间 | 是否被服务重启打断 |
|---|---|---|---|
| `b204023eea47`（用户 19:00 那条） | ❌ | 19:05:06 → 19:11:15 | ✅ **19:09:21** |
| `8ea44931470a` | ❌ | 20:32:13 → 20:34:42 | ✅ **20:34:02** |
| 其余 **20 条** | ✅ 全部有 | — | ❌ 全部未被打断 |

**相关性 2/2 vs 20/20** —— 失败链与「服务重启」完全重合。

用户那条链的精确时间戳：
- stage1 `started_at = 19:05:06`
- 服务重启 `19:09:21`（systemd `Started h3-studio.service`）
- stage1 `finished_at = 19:11:15`

`finished_at` 晚于重启 2 分钟且任务状态是 `done` —— 说明**收尾不是原 worker 做的**，
是重启后的**自愈路径**做的。

### 2.3 根因

服务重启会杀掉正在跑的 worker 协程，
`_finalize_continuation`（登记分段 + 拼完整视频）**来不及跑**。
重启后的自愈路径（`_finalize_residual_with_outputs` /
`_adopt_residual_running`）原来**只做两件事**：

1. 下载产物
2. `UPDATE jobs SET status='done', outputs=...`

**没有**登记分段（`continuation.segment_rel` 缺失）、**没有**拼完整视频（无 `is_full` 条目）。

现场 DB 佐证：两条失败链的 stage1 `continuation.segment_rel` **确实是 `None`**，
而 20 条成功链的 stage1 都有值。

### 2.4 为什么用户看到的是「4 秒」而不是「没有成片」

段2 分段文件 = 124 帧（5 秒总长）− 22 帧（钉住窗口）= **102 帧 = 4.25 秒**。
也就是说**潜空间接续本身是成功的**（本段真的新生成��� 102 帧），
只是**成片没被拼出来**，用户只看到那孤零零的一段 4.25 秒。

## 三、缺陷① 修法

### 3.1 改动清单

| 文件 | 行号 | 改动 |
|---|---|---|
| `server.py` | 3143-3260 | `Worker._finalize_continuation` 的实现提到**模块级** `_finalize_continuation_impl` |
| `server.py` | 2222-2233 | `Worker._finalize_continuation` 改为**薄委托**（`return await _finalize_continuation_impl(...)`） |
| `server.py` | 476-489 | `_finalize_residual_with_outputs`（**自愈收尾**）补跑接续收尾 |
| `server.py` | 543-556 | `_adopt_residual_running`（**接管路径**）补跑接续收尾 |
| `server.py` | 3168-3172 | 接续收尾取分段时**跳过 `is_full`**（成片）—— 见 §5.2 缺陷③ |

**为什么必须提到模块级**：原实现是 `Worker` 的实例方法（`self._finalize_continuation`），
但体内**没有任何 `self.` 引用**。而自愈路径是**模块级函数**，
没有 `Worker` 实例可用 —— 不提取就调不到它。

### 3.2 幂等性

`_finalize_continuation_impl` 幂等：
- 登记分段 = 写本段**自己**的 `continuation.segment_rel`（同值覆写）；
- 拼成片 = 按血缘重新拼一遍，产出**新的**成片文件（旧成片留在盘上，不影响正确性）。

重跑只会多出一个内容相同的成片文件，**不改变用户看到的结果**。

## 四、缺陷② 修法（跨段提示词增强）

### 4.1 数据链路（三段）

```
服务端 /api/jobs/{id}/continuation
  └─ context["prompt_history"] = _lineage_prompts(jid)      server.py:5794
       ↓
web/continuation.js  →  Continuation.promptHistory()          continuation.js:585
       ↓
web/enhance-menu.js  →  /api/enhance 携带 prompt_history
     ├─ 普通增强（runBasic）                                    enhance-menu.js:1697
     └─ 视频导演稿（runDirector）                               enhance-menu.js:1607
       ↓
服务端 /api/enhance
  ├─ _normalize_prompt_history(raw, current_stage)              server.py:8061
  │    └─ 剔除**本段自己**（stage == current_stage）、容错脏数据
  └─ enh.build_messages(spec, original, lang, history=history)  server.py:8204
                                     enhancer.py:862
```

### 4.2 改动清单

| 文件 | 行号 | 改动 |
|---|---|---|
| `server.py` | 3095-3140 | 新增 `_lineage_prompts()`：沿 `source_job` **血缘**回溯取各段 `params["prompt"]` |
| `server.py` | 5794 | 接续上下文下发 `prompt_history` |
| `server.py` | 8047-8059 | 新增 `_safe_int()`：安全转 int（`stage` 是前端传的） |
| `server.py` | 8061-8100 | 新增 `_normalize_prompt_history()`：剔除本段 + 脏数据容错 + 按段号排序 |
| `server.py` | 8195-8204 | `/api/enhance` 接收并传递历史 |
| `h3studio/enhancer.py` | 862-915 | `build_messages()` 新增 `history` 参数：历史**在前**、本段原文**在后** |
| `web/continuation.js` | 585-603 | `Continuation.promptHistory()`：从上下文取历史并规整 |
| `web/enhance-menu.js` | 1651-1680 | 新增 `continuationPromptHistory()`：取不到就**安全退回空数组** |
| `web/enhance-menu.js` | 1607 / 1697 | 两处增强入口都透传 `prompt_history` |

### 4.3 口径要点

- **血缘口径与拼接口径完全同源** —— 兄弟分支（B1/B2）互不污染：
  B1 的历史里不会有 B2。
- **剔除本段自己**：`original` 已经是本段原文了；本段再进历史，
  模型会看到两遍同一段，容易把「本段」误当成「前情」。
  但**字符串数组**形态（无可信段号）**不套用**剔除规则 —— 宁可多带一条，
  也不能把整份历史丢掉。
- **历史排在原文之前**：模型读到最后才输出，前情在前、本段在后，
  模型更不容易把多段内容糊成一段。
- **不接续时行为完全不变**：`prompt_history` 为空数组 → 消息内容与今天一致。

## 五、线上实测抓到的第三个缺陷（顺手修掉）

### 5.1 现象

跑完 E2E 后做「自愈路径重跑」验证，发现：

```
heal_idempotency.segment_rel_before = videos/v-h3-studio-000455.mp4  （分段）
heal_idempotency.segment_rel_after  = videos/v-h3-studio-000456.mp4  （成片！）
heal_idempotency.segment_rel_unchanged = false
```

### 5.2 根因

接续收尾取「本段分段视频」时，原实现取 `saved` 里**第一个** video。

- **首次运行**：`saved = [分段]` → 取到分段，没问题；
- **重跑**（自愈重跑 / 用户重试）：`saved = [成片(is_full), 分段]`
  → 取到**成片** → `segment_rel` 被覆盖成成片路径。

后果：
1. 本段的分段登记被冲掉；
2. 下一段按血缘回溯拿到的是**成片** → 拼接链 = 段0 + 成片 + 段2
   → **成片长度翻倍**。

### 5.3 修法

`server.py:3168-3172` —— 只取**非 `is_full`** 的第一个 video：

```python
video = next((o for o in saved
              if o.get("kind") == "video" and not o.get("is_full")), None)
```

## 十、已知遗留

1. **服务重启仍会打断正在跑的任务**。本轮修的是「打断后成片补不出来」，
   不是「打断本身」。重启期间正在跑的段会走自愈路径（产物回收 + 补成片），
   但**生成中途被打断的段本身**不可能凭空完成 —— ComfyUI 侧也要重跑。
   用户侧建议：生成期间不要重启服务。

2. **缺陷③的同类风险**。`is_full` 判定是**按字段名**做的。若将来产物条目
   换了字段名（比如 `kind: "video"` + `role: "full"`），这条防线会失效。
   建议后续把「成片」概念抽成显式字段而不是靠 `is_full` 约定。

3. **跨段提示词历史的容量**。历史无长度上限；一条 20 段的链会把 20 段提示词
   一起发给模型，可能撞上模型上下文上限（`/api/enhance` 已有 4000 字上限，
   但那是**原文**上限，历史不计入）。极端情况下模型会截断历史。
   当前实现按段号顺序拼接，超长时靠模型自己截断 —— 没有显式告警。

4. **本轮没有改 `/home/ubuntu/comfyui` 任何第三方节点代码**。
   两个缺陷都在 Studio 侧（服务端收尾路径 + 前端链路）。
