## 1. 为什么要重建

现有测试集有两条腿，都**不驱动真实浏览器**：

| 现有资产 | 实际在测什么 | 漏掉什么 |
|---|---|---|
| `tests/test_*.py`（约 200 文件） | 契约测试：解析 HTML/JS **文本**，断言 DOM「应该」长什么样 | 按钮点不动、输入框能输入但提交旧值、永远运行中 |
| `scripts/verify_*.py`（约 70 个） | 手写走查脚本：起实例 → 点几下 → 截图 | 一次性、不可重复、断言散落、没有统一证据格式 |

结果就是：界面与用户预期脱节的那类问题，一次都没被自动化拦住。

### 2.3 假 ComfyUI 为什么必须自己写

仓库原有的 `tests/fake_comfyui.py` 只够测「队列顺序」。本套测试要支撑**完整链路**，
所以另写了 `tests/e2e/fake_comfyui_e2e.py`，多做了四件事：

1. **真的产出媒体字节** —— `/view` 按工作流里的请求尺寸生成真实 PNG，
   于是「卡片显示的实际像素 == 提交尺寸」这类断言才有意义；
2. **真的落盘潜空间** —— 看到 `H3RelayLatentSave` 节点就写
   `<output>/relay_kit/<run_id>/stage_<N>.safetensors`。
   **没有它，服务端的「这一段能不能接续」永远判否，接续链路根本测不了**；
3. **可注入故障** —— `/control/drop` 把任务从队列抹掉且永不返回（复现「ComfyUI 那边任务丢了」）；
4. **可回读工作流** —— `/control/workflow/<prompt_id>` 返回原始 prompt JSON，
   用例据此断言「接续段真的挂了 `H3RelayLatentLoad` + `explicit_path`」。

## 4. 缺陷清单

### DEF-01 —— 提示词增强不携带此前段落提示词（需求 B.4）

**状态**：**已被并行任务修复**（commit `3576a87`，2026-11-17 22:48）。
本轮 E2E 在重建过程中先测出「未实现」，随后并行任务落地了实现，
E2E 重新复验**通过**。

**发现过程（E2E 的价值）**：

重建测试集时，这条需求被写成断言后**立刻失败**。实测请求体只有：

```json
{"prompt": "第三段：两人对峙，剑锋相交", "mode": "replace",
 "spec_id": "image", "mode_ctx": "t2i", "model_key": "z_image_turbo_bf16"}
```

**没有任何「上文」字段** —— 模型在扩写第 3 段时看不到第 1、2 段，
跨段一致性（角色外观、场景、光线）无从保证。

**并行任务的实现口径**（commit `3576a87`）：

| 层 | 改动 |
|---|---|
| `server.py` `_lineage_prompts()` | 沿 `source_job` 血缘回溯，取链首段到本段每一段的提示词（与拼接口径同源 —— 兄弟分支隔离） |
| `server.py` `GET /api/jobs/{id}/continuation` | 把这份 `prompt_history` 下发给前端 |
| `server.py` `/api/enhance` | 接受 `prompt_history`；`_normalize_prompt_history()` 剔除本段自己 + 容错脏数据 |
| `h3studio/enhancer.py` `build_messages()` | 支持 `history`（历史在前、本段原文在后）；无历史时行为完全不变 |
| `web/continuation.js` | 暴露 `Continuation.promptHistory()` |
| `web/enhance-menu.js` | 普通增强 + 视频导演稿两处入口都透传历史 |

**E2E 复验结果**（用例 `test_enhance_carries_previous_segment_prompts`）：

真实跑出**三段接续链**（第 1 段 5 秒 → 接续 → 第 2 段 → 接续 → 第 3 段），
在第 3 段点「增强」，实测请求体：

```json
{"prompt": "第三段：两人对峙，剑锋相交，镜头缓慢推近",
 "mode": "replace", "spec_id": "video-director", "mode_ctx": "t2v",
 "model_key": "lora",
 "prompt_history": [
   {"stage": 0, "prompt": "第一段：月光下的竹林，黑衣剑客背对镜头，剑未出鞘"},
   {"stage": 1, "prompt": "第二段：白衣剑客转身，剑光照亮面部，竹叶纷飞"},
   {"stage": 2, "prompt": "第三段：两人对峙，剑锋相交，镜头缓慢推近"}]}
```

**此前所有段落的提示词都在** —— 需求 B.4 达成。

**这条用例的关键设计**：它走**真实的接续链**（真的点接续、真的生成三段），
而不是「伪造一个历史数组」。因为历史来自**任务血缘**（`source_job` 指针），
只有真的跑出链才能验证 —— 伪造数组只能测到「前端会不会把数组传上去」，
测不到「服务端会不会从血缘里正确取出来」。

**本轮为此发现并修掉的一个测试陷阱**：点「接续」会**清空提示词框**
（设计如此：用户要写下一段），所以测试必须在点接续**之后**重新输入本段提示词，
否则增强会提示「请先输入要增强的提示词」—— 那是测试写错了，不是产品缺陷。

### DEF-02（已修复）—— 播放器打开时恒停在空页签

**严重度**：中（用户会以为「添加到播放器」没生效）

**定位**：`web/asset-player.js` 的 `open()`。

**原行为**：`S.mode` 初始值恒为 `"image"`，`open()` 拉完清单后直接 `render()`。
用户只往清单里加了一个**视频**时，打开播放器看到的是：
「图片播放」页签 + 「清单里还没有图片素材 —— 在素材库里勾选后点「添加到播放器」」。
**明明清单里有 1 个视频，界面却说清单是空的。**

**复现步骤**：

1. 素材库上传一个 mp4；
2. 右键该素材 → 点「▶ 添加到播放器」；
3. 点右上角「播放器」。

**修复**：新增 `pickAvailableMode()`，打开时把当前页签落到**清单里真有内容**的那一类
（当前页签有内容就保持不动；没有就切到有内容的那个；三个都空才保持）。
改动 28 行，单文件、单函数，不碰其它逻辑。

**修复后验证**：`test_player_playlist_from_manual_selection` 通过 ——
只加视频时，播放器落在「视频播放」页签并显示该视频。

## 5. 证伪的疑似缺陷：接续时长「5+5 ≠ 9 秒」

**现象**：题面口径是「5+5 → 9 秒，再接 8 秒 → 16 秒」，
但系统显示 **9.417 秒 / 16.500 秒**。

**结论**：**不是缺陷**。系统给的是**帧级真值**，题面口径是近似。

**推导**（`h3studio/continuation.py`）：

- H3 的潜空间帧网格是 **17k+5**（`align_frame_count`）——
  每段请求时长会**向上**吸附到网格：5 秒 → 124 帧（5.167 秒），不是 120 帧；
- 接续段还要减掉 22 帧钉住区（`DEFAULT_CONTEXT_FRAMES = 22`）。

于是：

| 段 | 计算 | 累计帧数 | 累计秒数 | 题面口径 |
|---|---|---|---|---|
| 5 + 5 | 124 + (124−22) | **226** | **9.417 s** | 9 s |
| 5 + 5 + 8 | 124 + 102 + (192−22) | **396** | **16.500 s** | 16 s |

差的 0.417 / 0.500 秒全部来自网格取整（每段最多 +5 帧 = 0.208 秒）。

**实测佐证**（线上真实产物，`ffprobe` 数帧）：

```
v-h3-studio-000451.mp4 -> 9.416667,226 帧
v-h3-studio-000449.mp4 -> 9.416667,226 帧
v-h3-studio-000442.mp4 -> 9.416667,226 帧
v-h3-studio-000439.mp4 -> 9.416667,226 帧
```

4 个独立产物全部是 **226 帧 / 9.416667 秒**，与系统 `total_frames=226`、
`total_seconds=9.417` 完全一致 —— **视频文件本身就是这个长度**。

**测试怎么断言**：断言**帧级精确**（`total_frames` 必须等于按网格算出的值），
秒级允许「每段 ≤ 0.208 秒」的网格容差。见
`test_continuation_flow.py:_expected_frames` / `_grid_tolerance`。

## 6. 本次重建顺带修掉的实现问题

除了 DEF-02（用户可见缺陷），还修了三个**测试基础设施自身**的问题，
它们都会让测试「假失败」或「假通过」：

| 问题 | 位置 | 后果 |
|---|---|---|
| 素材库按 sha256 去重，同内容第二次上传会「复用原素材」（标签也不更新） | `h3studio/asset_api.py`（**产品行为，未改**） | E2E 的「标签生效」断言会读到上一条用例的标签 → 假失败。修法：每条用例用**内容也不同**的素材（`e2e_lib.make_fixtures(unique=True)`） |
| 素材库拒绝写非独立挂载点的目录 | `h3studio/assets.py:check_disk_mounted`（**产品行为，未改**） | 隔离实例的素材库放在普通临时目录时全部 503。修法：素材库放 `/dev/shm`（tmpfs，设备号与 `/` 不同） |
| 提交后前端自动切到「进行中」标签，任务跑完就不在那儿了 | 前端行为（**未改**） | 「批次结果折叠块」断言找不到元素 → 假失败。修法：断言前先切回「已完成」标签 |
| 播放器清单跨用例累积（隔离实例的素材库是 session 共用） | — | 「初始播放列表应为空」断言在第二条用例必失败。修法：断言本次添加后的**增量** |

## 8. 剩余风险与后续

1. **DEF-01 已由并行任务修复**（commit `3576a87`），本轮 E2E 复验通过。
   实现口径：上文取自**接续链的血缘**（`source_job` 指针回溯），
   不是「本面板的提示词历史」—— 兄弟分支互不污染。
2. **假 ComfyUI 与真 ComfyUI 的差异**：假 ComfyUI 不跑真模型，所以
   「模型产出质量」类断言（真出图、真实音色）不在本套覆盖内 ——
   需要 `--live` 或 `--real-comfy` 跑（会占 GPU、耗时以分钟计）。
3. **本地模型服务是共享单槽**：并发跑别的任务时 `/api/enhance` 偶尔 502。
   用例已做 3 次重试，但 CI 上仍可能偶发。
4. **E2E 会真的跑生成任务**：全量 `pytest tests/` 会比原来慢 15 分钟左右。
   CI 里建议 `-m "not e2e"` 排除（用例已打 `e2e` 标记）。
