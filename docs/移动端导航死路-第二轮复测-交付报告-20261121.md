## 4. 本轮修掉的真缺陷

### D1：平板档（701~1100px）FAB 压住分页条与卡片底部

**根因**：给 FAB 让位的 `padding-bottom: 76px` **只写在 `≤700px` 那档**，
而 FAB 是 `position:fixed`、在 **`≤1100px`（平板档）就出现** ⇒ 701~1100px 整段没让位。

**实测（768×1024）**：
```
修前：分页条 rect = {top:944, bottom:1008}
      FAB   rect = {top:964, bottom:1008}   ← 重叠 44px
      卡片「☆ 收藏」按钮被盖 79×16px（占按钮面积 35%）
修后：分页条 rect = {top:884, bottom:948}   ← 与 FAB 不再重叠
```

**修法**（`web/responsive.css`，≤1100px 档）：把让位规则提到 FAB 出现的同一档
```css
.jobs-area { padding-bottom: 76px; }
.jobs-pagination .page-summary { margin-left: 0; }
```
375/390px 行为**完全不变**（那档本来就有同值规则），1280px 桌面端**零影响**（FAB 不出现）。

**但要说清楚 —— 这不是「点不到」的死路**：
用滚动全程 24 步扫描（`scripts/probe_fab_scroll_sweep.py`）测可达性：

| 实例 | 视口 | 瞬时重叠次数 | 最大重叠面积 | **任何滚动位置都点不到的元素** |
|---|---|---|---|---|
| 修前 8190 | 375px | 23 | 3330px² | **0** |
| 修前 8190 | 768px | 13 | 3364px² | **0** |
| 修后 8922 | 375px | 23 | 3330px² | **0** |
| 修后 8922 | 768px | 13 | 2640px² | **0** |

⇒ FAB 是 `fixed`，内容滚过它底下时**瞬时**被盖是浮动按钮的固有行为
（Material FAB 就这样），**不构成功能死路**。
所以验收 ⑤ 的正确判据是**可达性**（每个可交互元素是否存在可点的滚动位置），
而不是「重叠面积恒为 0」—— 后者对 fixed 浮动按钮在数学上就不可能成立。

我第一版守卫写成了「重叠面积 = 0」，它会**假红**；已改成可达性判据。

那用户为什么还报？三个**可验证**的原因，按可能性排序：

### 原因 1（最可能）：用户测试发生在 09:23 之前

`edba2ef` 之前的版本（`ba33586`）就是现在 8921 实例在跑的那个 ——

⇒ **用户描述的现象与修复前的版本完全吻合**。

### 原因 2：本机有 7 个 h3studio 实例，其中 5 个不含修复

```

port 36705  bind=0.0.0.0:36705  cwd=/root/projects/h3s-base-truth     HEAD=7436883  ❌ 无修复
```

⇒ **如果用户访问的是 8391 / 35597 / 36705 / 52145 之一（而不是 8190），
   拿到的就是没修复的旧前端** —— 现象与修复前完全一致。

### 原因 3：静态资源启发式缓存（已实测排除）

`/static/*` 的响应头**没有 `Cache-Control`**（实测只有 `Etag` + `Last-Modified`）
⇒ 浏览器会按启发式新鲜度缓存。而 `index.html` 是 `no-cache, must-revalidate`
⇒ 版本清单每次都是新的，但**已缓存的旧 `app.js` / `responsive.css` 不会主动重取**。

**但我实测排除了它**：
```
SCEN1 修前实例读到:              {"drawerHead": false, "respCss": false}
SCEN1 同 context 访问修后实例:   {"drawerHead": true,  "respCss": true}   ← 拿到新版
SCEN2 全新 context 访问修后实例:  {"drawerHead": true,  "respCss": true}
```
⇒ 因为 `?v=` 版本号变了（`cr20261115b` → `assetview20261121a`），URL 变了，
缓存不可能命中。**缓存不是本次的原因**（但 `?v=` 机制正是为了防这个，值得保持）。

## 10. 未做到的项与已知限制（如实）

1. **视频卡长按右键菜单仍然唤不出来** —— `<video>` 的原生手势处理吞掉 touch 事件，
   Chrome 不允许页面拦截。已提供不依赖右键的入口（卡片底部「☆ 收藏」按钮）。
   **这一条仍然成立**，本轮未改变。

2. **长按阈值 550ms 是经验值** —— 可能与个别用户预期有出入。本轮未调整。

3. **FAB 是 `position:fixed`，内容滚过它底下时瞬时被盖** —— 这是浮动按钮的固有行为。
   已用滚动全程扫描证明「不可达元素 = 0」，
   但**用户仍可能在一瞬间觉得某个按钮被挡住了**。真要彻底消除需要把 FAB 改成
   跟随滚动容器（视觉变化较大），本轮**不做**。

4. **本轮未在真机上验证** —— 全部用 Playwright Chromium（headless + Xvfb headed）
   模拟 375/390 视口 + touch 事件。**没有真实 iOS Safari / Android Chrome**。
   iOS Safari 的地址栏收放、PWA standalone 模式等行为可能仍有差异。

5. **768px 平板档在需求里只要求「交叉参考」** —— 本轮按两档手机验收，
   平板档作为额外发现（并修了 FAB 让位）处理。

6. **本机另外 4 个无修复的实例仍在跑**（8391 / 35597 / 36705 / 52145）。
   它们是**别的任务**的产物，本轮**没有权限也没有授权**去停它们。
   ⇒ 如果用户访问的是这些端口，现象依然存在。**这是当前最需要确认的一点。**

7. **额度快照已滞后 2 天** —— 本轮未做任何额度刷新（不新建探针任务）。
   由于本轮**未产生任何 GPU 生成作业**，风险为零。
