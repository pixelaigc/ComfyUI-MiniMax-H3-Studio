## 一、根因

### 1.1 直接原因

`web/app.js` 里的 `openAssetPickerForSlot(kind, onPick)` 是**槽位填素材的唯一入口**，
但「**点空槽位**」那条路径调用时**漏传了 `onPick` 回调**。

修复前（`0722404:web/app.js`）：

```js
784:  function openAssetPickerForSlot(kind, onPick) {
...
911:      openAssetPickerForSlot(kind);                       // ← 漏传 onPick（点空槽位）
921:      openAssetPickerForSlot(kind, (asset) => fillFromAsset(asset));  // ← 「素材库」小按钮（正确）
```

- `911` 行 = 点**空槽位本体**（`.up-slot` 的 click 处理器）
- `921` 行 = 点槽位右上角的**「素材库」小按钮**（`.pick-asset`）

### 1.2 为什么报错信息是误导性的

漏传后，`openAssetPickerForSlot` **本身不报错**，照常打开素材库弹窗。
用户选完素材、点「确定使用」，`assets.js` 的 `onDone` 回调触发：

```js
onDone: (ids) => {
  ...
  fetch(`/api/assets/${assetId}`).then(r => r.json()).then(asset => {
    onPick({ ... });          // ← onPick 是 undefined -> TypeError
  }).catch(err => alert("读取素材失败：" + err.message));
}
```

那个 `TypeError` 被 `.catch()` 吞掉，于是弹成
「读取素材失败：**onPick is not a function**」。

**提示指向「读取素材」，真实失败点却是「回调没传」** —— 素材其实读取成功了
（HTTP 200、JSON 也解析完了），是读取**之后**调用回调时才炸。排查方向被带偏。

### 1.3 为什么只有「点空槽位」坏，「素材库」按钮是好的

两条路径调的是同一个函数，但**只有一条漏传**：

| 入口 | 修复前调用 | 结果 |
|---|---|---|
| 点空槽位本体 | `openAssetPickerForSlot(kind)` | ❌ 报错、槽位不回填 |
| 点槽位上的「素材库」小按钮 | `openAssetPickerForSlot(kind, a => fillFromAsset(a))` | ✅ 正常 |

这也解释了为什么缺陷能长期存在：小按钮那条路径好用，用户只要点对了就没事；
而「点空槽位」是更自然的操作习惯。

### 1.4 影响面

两条路径由**同一个** `mk(key, label, kind)` 工厂函数生成（`web/app.js:805`），
所以漏传影响到**全部**走 `mk()` 的槽位：

| 模式 | 槽位 | 类别 |
|---|---|---|
| 参考生视频（r2v） | 参考 1 ~ 参考 9 | image |
| 参考生视频（r2v） | 参考视频 1 ~ 3 | video |
| 参考生视频（r2v） | 参考音乐 1 ~ 3 | audio |
| 首尾帧生视频（flf） | 首帧 / 尾帧 | image |
| 首尾帧生视频（flf） | 参考视频 1 ~ 3 | video |
| 首尾帧生视频（flf） | 参考音乐 1 ~ 3 | audio |

**共 20 个槽位，全部走这条坏路径**（只要用户点槽位本体而不是小按钮）。

### 1.5 其它素材库选择入口的核查结果

全仓 `openPicker` 调用点只有 4 处，逐个核实**均无此缺陷**：

| 文件:行 | 入口 | 回调写法 | 结论 |
|---|---|---|---|
| `web/app.js:789` | 视频槽位（本次修复对象） | `onDone(ids)` → 内部调 `onPick` | ❌ 漏传 → ✅ 已修 |
| `web/music.js:768` | 参考生音乐「参考音频」 | `onDone(ids)` 内联逻辑，无二次回调 | ✅ 无此问题 |
| `web/qwen-refs.js:213` | Qwen 图片编辑「参考图」 | `onDone(ids)` → `addAssets(ids)` | ✅ 无此问题 |
| `web/video-effect-lora.js:139` | 效果 LoRA 选择器 | **同名但不同模块**（原生 select 浮层，与素材库无关） | ✅ 不相关 |

素材库选择器契约（`web/assets.js:1159` `openPicker(options)` / `web/assets.js:1235` 确定按钮）：
`options.onDone(ids)` —— 回调名是 **`onDone`**，不是 `onPick`。
`onPick` 只是 `app.js` 内部 `openAssetPickerForSlot` 的参数名。
组件 API 与调用方签名**没有**不一致 —— 问题是调用方**少传了一个参数**。

## 二、改动清单

### 2.1 `web/app.js`（唯一的产品代码改动，+16 / -1）

**改动 1 —— 补上漏传的回调**（`web/app.js:926`）

```diff
-      openAssetPickerForSlot(kind);
+      openAssetPickerForSlot(kind, (asset) => fillFromAsset(asset));
```

现在「点空槽位」与「点素材库小按钮」走**完全相同**的调用方式。

**改动 2 —— 给 `onPick` 加必填守卫**（`web/app.js:784`）

```js
function openAssetPickerForSlot(kind, onPick) {
  if (typeof onPick !== "function") {
    console.error("[素材库选择] 缺少 onPick 回调，无法打开选择器", {kind});
    alert("素材库选择器调用有误（缺少回调），请刷新页面重试。");
    return;
  }
  ...
}
```

守卫的价值：万一将来又有调用点漏传，**在打开弹窗之前**就拦下来 ——
用户不会白选一遍素材才看到失败；提示也会说清是「缺少回调」，
而不是把 `onPick is not a function` 这种内部细节甩给用户。

### 2.2 `web/index.html`（缓存版本号，+1 / -1）

| 资源 | 旧 ?v= | 新 ?v= |
|---|---|---|
| `app.js` | `cr20261116b` | `cr20261116c` |
| `video-panel.js` | `vparams3` | `vparams4`（并行任务随后升到 `vparams5`） |

**这一步不是顺手做的，是必须的**：`/static/*` 没有 `Cache-Control`，
浏览器按启发式新鲜度缓存。`app.js` 内容变了而 `?v=` 不变 ⇒
老用户浏览器拿到的仍是**旧的坏文件**（漏传 onPick 那版）—— 修复等于没上线。

### 2.3 `tests/test_assetlib_and_seed_guard.py`（修正一条固化了缺陷的旧断言）

原断言：

```python
def test_empty_slot_click_opens_asset_picker(self):
    """点空槽位 -> 打开素材库选择器（不是系统文件框）。"""
    self.assertIn("openAssetPickerForSlot(kind)", APP_JS_CODE)
```

它匹配的**正是有缺陷的那一行**（漏传 onPick 回调）。
也就是说这条断言当时没守住行为，反而把缺陷**固化**进了测试：
修复一改它就红了，而红的原因恰恰是修复对了。

现改为表达真实意图：① 走的是 `openAssetPickerForSlot`（不是 `inp.click()`）；
② 每一处调用都带回调；③ 点空槽位那处必须写成
`openAssetPickerForSlot(kind, (asset) => fillFromAsset(asset));`。

## 五、过程记录：一次并行任务冲突及其修复

**发生了什么**：2026-11-17 20:34 前后，一个并行任务把 `b8f3cb5`（二采 NFE 预算护栏）
与 `e1cf598`（升 `video-panel.js` 的 `?v=` 到 `vparams5`）合入了 `local/maintainer`。
本会话在 20:40 执行 `git branch -f local/maintainer local/feature/fix-onpick`，
把这个引用**重置**掉了 —— 那两笔提交因此从 `local/maintainer` 上消失。

**为什么没造成损失**：那两个提交仍然在
`local/feature/cont-seam-hires` 与 `local/deploy/qwen-ref-assets-live` 上可达，
且 live 分支上也有（live 的 merge 是 `--no-ff` 建在它们之上的）。

**怎么修的**：用 `git merge --no-ff` 把 `local/feature/cont-seam-hires` 合回
本分支（`b73b237`），再把 `local/maintainer` 指向合并后的状态，
四个关键提交（`e1cf598` / `b8f3cb5` / `7517fb2` / `fbfcb4e`）全部可达。
live 也已回灌到同一状态（`997f59b`），探活 200、日志无 ERROR。

**教训**：`git branch -f` 改共享分支引用会**抹掉**别人刚合进去的工作。
共享分支（`local/maintainer`）只能用 merge 推进，不能用 `branch -f` 重置。

   `scripts/fix_onpick_apply.py` / `scripts/bump_static_version.py` 做行级精确替换。
   后续若再改这两个文件，请注意保持 CRLF。
4. **素材库选择器的契约是 `onDone(ids)`**（`web/assets.js`），不是 `onPick`。
   `onPick` 只是 `app.js` 内部函数的参数名。若将来要统一所有入口，
   建议把「选一个素材并取回完整素材对象」抽成素材库模块的公开 API，
   避免每个调用方各写一遍 fetch + 映射。
5. **字符串断言要谨慎**。`assertIn("openAssetPickerForSlot(kind)", ...)`
   这种写法会把「当前实现的形状」当成「期望的行为」——
   本次就有这样一条断言**固化**了缺陷。行为断言优先用真浏览器。
