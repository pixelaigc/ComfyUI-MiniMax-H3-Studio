### [MAJOR-1] 显式放行标记 `allow_twopass` 在服务端归一时被丢弃

**严重度**：MAJOR（用户勾选并二次确认的功能完全无效，且界面还谎称生效）

**位置**：`server.py::_prepare_continuation_params`（重建 `params["continuation"]` 的那段）

**证据**（修复前 `tests/r7_probe_twopass_split.py` 实跑）：

```
步骤 1：面板提交体
  continuation.allow_twopass = True
  twopass.enabled            = True
步骤 2：归一层 normalize_t2v_params
  normalize_notes = ['接续段按你的显式设置走了二采（SelfLift）路径：…']
步骤 3：_prepare_continuation_params（重建 continuation）
  重建后 continuation 的键 = [... 'anchor_latent_stage', 'chain_id', ...]   # 没有 allow_twopass
  allow_twopass 是否还在 = False
步骤 5：worker 的工作流层
  resolve_effective_twopass -> use_twopass=False disposition=deny
```

**根因**：`_prepare_continuation_params` 在重建 `params["continuation"]` 时只写一组
**固定字段**（`chain_id` / `stage_index` / `source_job` / 坐标 / `context_frames` /
`anchor_frames` / `chain_total_frames` / `segment_frames`），
**没有**把前端显式提交的 `allow_twopass` 带过去。
服务端策略层 `h3studio/twopass_policy.py::continuation_allows_twopass`
读的正是 `params["continuation"]["allow_twopass"]` ⇒ 读不到 ⇒ 判定 `deny`。

**后果链**：
1. 用户勾选「接续段也用二采」→ 弹二次确认 → 提交 → **服务端丢弃**；
2. 归一层在丢弃**之前**已经算过策略（`normalize_t2v_params` 跑在 `_prepare` 之前，
   见 `server.py:5597` 与 `server.py:5627`）⇒ 记下
   `normalize_notes = "接续段按你的显式设置走了二采（SelfLift）路径…"`；
3. 工作流层再算一次（读的是**丢弃后**的 params）⇒ `deny` ⇒ 走标准采样。

⇒ **界面告诉用户「按你的设置走了二采」，实际走的是标准采样。**

**修复**（`server.py`，F1）：重建之后补一行
`if info.get("allow_twopass") is True: params["continuation"]["allow_twopass"] = True`

**回归测试**：`tests/test_r7_review_fixes.py::AllowTwopassPreservedTest`（3 条）
**变异**：M1（删掉保留逻辑 → 红）、M2（无条件 True → 反向断言红）

### [MAJOR-2] 参考视频帧数 `ref_video_frame_count` 沿链丢失 ⇒ 2026-11-19 的「按 C_n 跳帧」修复在真实接续链上等于没生效

```
  ref_video_frame_count = 300
前端拿到的 continuation（build_continuation_context）:
  ['anchor_frames', 'chain_id', ..., 'source_latent_stage', 'source_segment', 'stage_index']
  含 ref_video_frame_count ? False
```

**根因**：`_record_ref_video_frame_count`（`server.py:2244`）把探测到的帧数写进

⇒ `video_skip_frames = 0` ⇒ **参考视频又从 0 开始喂**
⇒ 正是 2026-11-19 实测到的「段头亮度阶跃」的触发条件。

**修复**：
- F2（`server.py`）：从上游 `source_info` 继承 `ref_video_frame_count`；
- F4（`h3studio/continuation_service.py`）：`build_continuation_context` 一并下发。

**修复后实测**（同一探针）：

**回归测试**：`tests/test_r7_review_fixes.py::RefVideoFrameCountInheritedTest`（4 条，

### [MAJOR-3] 产物回写把加速 LoRA 写成**权重文件名** ⇒ retry 出来的工作流**一枚加速 LoRA 都不挂**，且不报错

**严重度**：MAJOR（静默降级到「一条不存在的路径」：8 步采样的非蒸馏权重）

**位置**：
- `h3studio/artifact_meta.py::apply_to_params`（回写 `accel_lora` / `fixed_accel_lora` / `accel_loras[].key`）
- `h3studio/video_models.py::resolve_accel_lora_slot`（工作流层只认**目录 key**）

**证据**（修复前 `tests/r7_probe_retry_workflow.py` 实跑，完整走
「源任务落库 → retry_job 整份拷贝 → prepare_job_params → build_workflow」）：

```
源任务落库后的 params（worker 回写之后）：
   accel_lora       = 'dmad_minimax_h3_4step_full_critic_comfyui'   ← 权重文件名
   fixed_accel_lora = 'dmad_minimax_h3_4step_full_critic_comfyui'
   steps            = 8
工作流里的 LoRA 节点：
   （无）                                              ← 一枚都没挂
采样步数节点：
   9 basicscheduler steps=8 scheduler=beta            ← 仍是蒸馏档步数
```

**根因（两处配合）**：
1. `apply_to_params` 写的是 `first.get("name")` —— 这是
   `artifact_meta._clean_weight_name(raw_name)` 的结果，即**权重文件名**
   （`dmad_minimax_h3_4step_full_critic_comfyui`）；
2. 工作流层 `video_workflow._resolve_accel_chain` →
   `video_models.resolve_accel_lora_slot(params)` → `accel_lora_meta(key)`
   查的是 `VIDEO_ACCEL_LORAS` / `VIDEO_ACCEL_LORA_COMBOS`，
   键是**目录 key**（`dmad_4step_critic` / `ckpt850`）⇒ 查不到 ⇒
   `_resolve_accel_chain` 直接 `return chain`（空链）。

⇒ 工作流里没有任何 LoRA 节点，但 `steps` 仍是 8（蒸馏档）
⇒ **8 步采样的非蒸馏权重**，画面必然糊 —— 而**全程零报错**。

**线上存量证据**：线上 jobs 库里 9 条视频任务的 `params["accel_lora"]`
**全部**是权重文件名形态（`dmad_minimax_h3_4step_full_critic_comfyui`），
`accel_lora_meta(...)` 认不出来 ⇒ 这批任务 retry 出来必然复现该缺陷。

**修复**：
- F5（`artifact_meta.py`）：回写时**只写认得出目录 key 的值**；认不出就**不覆盖**
  已有槽位（提交时写进去的本来就是正确 key）；
- F7（`video_models.py`）：`resolve_accel_lora_slot` 新增 `_normalize_accel_key()`，
  把「权重名形态」的 key 归一成目录 key —— 与显示层
  `job_meta._accel_lora_key_for_any_form` 同口径（存量数据也能救回来）。

**修复后实测**（同一探针）：
```
源任务落库后的 params： accel_lora = 'dmad_4step_critic'   ← 目录 key ✅
工作流里的 LoRA 节点：
   ('138:0', 'LoraLoaderModelOnly', 'dmad_minimax_h3_4step_full_critic_comfyui.safetensors', 1.0)  ✅
```

**回归测试**：`tests/test_r7_review_fixes.py::ArtifactAccelKeyTest`（5 条，
含「存量权重名形态仍能解析」与「认不出的权重不得写进槽位」）
**变异**：M5（写回权重名 → 红）、M6（去掉工作流层归一 → 红）
