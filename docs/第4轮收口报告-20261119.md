## 2. 目标 2｜`retry_job` 指纹副本不刷新 —— 🔴 真实缺陷

### 2.1 机制（为什么这是真缺陷，不是观察项）

| 环节 | 事实 | 证据 |
|---|---|---|
| Relay-Kit 落盘 | `save_file(tmp)` + **`os.replace(tmp, path)`** —— **原子写 ⇒ 换 inode** | `custom_nodes/ComfyUI-H3-Relay-Kit/relay_core.py::save_av_latent` |
| 指纹副本 | `ensure_fingerprinted_copy` 用 **`os.link`** 建硬链接 ⇒ 副本指向**旧 inode** | `h3studio/continuation_service.py:342` |
| 正常接续路径 | `_prepare_continuation_params` **每次都重算** ⇒ 没问题 | `server.py:4152` |
| **重试路径** | Agent 的 `retry_job` 把源任务 params **整份拷贝** ⇒ **不经过**上面那条 ⇒ **沿用旧路径** | `h3studio/agent_tools.py:287` |

⇒ 上游一旦被重跑，retry 读回**上一版的 latent** ——
**静默错误**：不报错、画面接错、界面全程显示成功。

### 2.2 线上同口径取证（`evidence/…/target2_retry_fingerprint_probe.py`）

```
副本 inode: 4098837   源 inode: 4098838   同 inode? False
副本内容头: VERSION-ONEVERSION-ONEVERSION-      ← 旧副本还是旧内容
源内容头  : VERSION-TWO-NEW-INODEVERSION-T      ← 源已被重跑
新接续路径: stage_00000_c9f9481b.safetensors      ← 正常路径算出的正确路径
RETRY 沿用的 source_latent_path: stage_00000_7cd33ac5.safetensors   ← **旧的**
RETRY 沿用副本内容头: VERSION-ONEVERSION-ONEVERSION-                ← **读到旧 latent**
=> retry 读到的是旧版 latent？ True
```

### 2.3 修法（改动面最小）

| 文件 | 改动 |
|---|---|
| `h3studio/continuation_service.py` | **新增** `refresh_fingerprinted_path(params)`（单一真源） |
| `server.py` | **新增**同名模块级入口（Agent 的 `ctx.server` 就是 server 模块） |
| `h3studio/agent_tools.py` | `retry_job` 在建任务前刷新 `continuation.source_latent_path` |

**为什么不放在 `prepare_job_params`**：那是三条建任务路径的公共点，但**只有
retry** 会带着「上一段已算好的 `source_latent_path`」进来；面板提交与 Agent
create 走 `_prepare_continuation_params`，那条路径本来就会重算。
放在 retry 这一处 = 改动面最小，且**不碰**面板/新任务的既有语义。

**语义保持**：只改 `source_latent_path` 一个字段 ——
段号 / 链 id / 接力棒坐标（`source_latent_run_id` / `source_latent_stage`）**不动**
（「重跑这一段」的语义，第 3 轮报告 §3.3 已确认那是正确设计）。

**失败不阻断**：刷新失败（源潜空间已被清理等）时保留原路径，
由 worker 按「潜空间不在」明确报错 —— 不静默改语义。

## 3. 目标 3｜`_record_ref_video_frame_count` 失败结果不缓存 —— 🔴 真实缺陷

### 3.1 现场取证（`evidence/…/target3_ref_frame_count_probe.py`）

```
probe_calls_for_3_invocations: 3          ← 调 3 次就探了 3 次
ref_video_frame_count_in_params: null      ← 什么都没记
db_row_written: false                      ← 也没落库
success_case_probe_calls: 1                ← 成功时是 1 次（既有正确行为）
```

**代价实测**：`ffprobe -count_frames` 对 32MB / 2 分钟 480P 参考视频
**单次 ≈ 3.0 秒**（要真解码一遍），且是**同步阻塞**子进程调用。

### 3.2 为什么不只是「轻微性能问题」

1. worker 的 `_run` 每次跑这个任务都调一次；任务被重跑/重试时又调一次
   ⇒ 每次都是 3 秒的**同步阻塞**。
2. **更关键**：探测失败 ⇒ 下一段拿不到 `ref_video_frame_count`
   ⇒ 工作流层走「探测不到 -> 不猜」的分支 ⇒ `video_skip_frames = 0`
   ⇒ **段2 的参考视频从 0 开始喂** —— 这正是第 3 轮那个「亮度阶跃」缺陷的
   **触发条件之一**。所以「不缓存」= 每段都可能重新踩一次同样的坑。

（继承关系已核：`evidence/…/target3_inheritance_probe.py` ——
段2 的 `continuation` **不继承** `ref_video_frame_count`，
`_prepare_continuation_params` 会重建整个字典。）

### 3.3 修法

| 改动 | 说明 |
|---|---|
| 落失败标记 | 失败时写 `ref_video_frame_count_probe = "failed"` 并**落库** ⇒ 后续调用直接返回，不再重探 |
| 探测走线程 | `frames = await asyncio.to_thread(_probe_video_frame_count, local)` ⇒ 不再阻塞事件循环 |

**语义保持**：帧数仍然是 **0**（= 不知道），**不猜**；
标记作用域只限**这一份**参考视频（换段不受影响）。
