# 实现报告：突破首尾帧/参考生分辨率限制（按 nonebot seg 机制）

**日期**：2026-11-17
**任务**：用户报「首尾帧 / 参考生面板的最大分辨率被限制」，判断是「当前用了错误的节点」，
要求以 nonebot 示例 `minimax_h3_seg1.json` / `minimax_h3_seg2.json` 为准突破该限制。

**结论一句话**：**用户的判断方向对（确实是"我们的配置写错了"），但不是"节点选错了"——
我们用的条件节点没问题，是我们在 `VIDEO_MODE_SIZE_POLICY` 里把 flf/r2v 的面积上限
硬编码成 0.8MP，把「旧面板的档位表」误当成了「生成侧的硬约束」。
上游（ComfyUI 核心节点 + T8 插件 + H3 权重）对画布面积**没有任何门禁**。
现已对齐 nonebot seg1/seg2 的 `ResolutionSelector(megapixels=2)` → **2.0 MP / 1920×1088**。**

## 一、取证：限制到底在哪一环

### 1.1 限制的完整链路（4 跳，全部在我们自己这边）

| # | 环节 | 文件:行号 | 作用 |
|---|---|---|---|
| ① | **策略表**（根因） | `h3studio/video_models.py:1132-1149`（旧） | `VIDEO_MODE_SIZE_POLICY["flf"]["max_pixels"] = int(0.8*1024*1024)`、`max_pixels_mp = 0.8`、`custom_size = False` |
| ② | 归一层 | `server.py:2559-2573` | `normalize_video_size(..., max_pixels=max_pixels_for_mode(vid_mode), strict_over_limit=True, mode=vid_mode)` → 超限直接返回 `width=0` 并报错 |
| ③ | 尺寸语义层 | `h3studio/h3_video_size.py:107-117 / 149-164` | `dimensions_for()` / `resolve_size()` 按 `max_pixels_for_mode(mode)` 裁剪 |
| ④ | 前端下发与提示 | `web/video-panel.js:248-258`（上限文案）、`:309-322`（预设过滤） | 按 `mode_size_policy[mode].max_pixels` 过滤预设下拉 + 显示「上限 X 像素」 |

### 1.2 实测：超限时**前端根本不让选**，服务端也**直接拒收**

**前端**（`web/video-panel.js:309-322`）：超出 `max_pixels` 的档位**不出现**在下拉里。

**服务端**（`server.py:2559-2573`，`strict_over_limit=True`）：超限**不静默缩放**，
直接返回宽度 0 + 中文错误。改前实测输出：

```
mode=flf: normalize_video_size(1920,1088) = 0x0
  reasons=['首尾帧生视频分辨率上限为 0.8M 像素（838,860 px）。
            当前请求 2,088,960 px（1920×1088），超出上限。…']
mode=r2v: 同上，文案为「参考生视频分辨率上限为 0.8M 像素（838,860 px）…」
```

→ 这就是用户看到的「最大分辨率被限制」。

### 1.3 关键判定：**不是节点能力限制，是我们自己写的策略**

逐条核对上游源码（**全部实测，非推断**）：

| 上游位置 | 事实 | 是否限制面积 |
|---|---|---|
| `comfyui-minimax-h3-audio-T8/h3_t8/nodes.py:302-303` | T8 条件节点 `width/height`：`min=32, max=MAX_RESOLUTION, step=32` | **否** |
| `comfyui-minimax-h3-audio-T8/h3_t8/nodes.py:286` | `MAX_RESOLUTION = 16384` | 上限 16384 像素/边 |
| `comfyui-minimax-h3-audio-T8/h3_t8/conditioning.py:574-577` | 超参考区只打 warning：`"canvas exceeds the 1920x1088 reference area; execution remains allowed and VRAM/runtime risk is owned by the user"` | **否（只警告）** |
| `comfyui-minimax-h3-audio-T8/h3_t8/conditioning.py:604` | `"reference_area_policy": "warning_only_no_area_gate"` —— **节点自己明写「无面积门禁」** | **否** |
| `comfyui-minimax-h3-audio-T8/h3_t8/core.py:88-95` | `empty_av_latent()`：`torch.zeros((1,24,latent_t,height//16,width//16))` —— latent 按请求值**原样**建立 | **否（无降采样）** |
| `comfyui/minimax_h3` 核心节点 `comfy_extras/nodes_minimax_h3.py:145-146`（ImageToVideo）、`:280-281`（ReferenceToVideo） | `width/height` 同样 `max=nodes.MAX_RESOLUTION`（16384） | **否** |
| `comfy_extras/nodes_resolution.py:47-54` | `ResolutionSelector` 的 `megapixels`：`min=0.1, max=16.0` | 上限 16 MP |

> **结论**：上游 T8 插件、ComfyUI 核心节点、H3 权重三层**全都没有面积硬限制**。
> 2.0 MP（1920×1088）是**官方模板 Note 背书**的档位，且 t2v 早就在用。
> flf/r2v 被卡在 0.8 MP，**纯粹是我们自己 `VIDEO_MODE_SIZE_POLICY` 写错了**。

### 1.4 旧注释错在哪（这才是缺陷的根源）

改动前的 `video_models.py` 原文注释：

```
#  * flf / r2v（老面板）：走 ResolutionSelector（aspect_ratio + megapixels
#    + multiple=32），档位只有 RES_MP = {544p: 0.4, 768p: 0.8}，
#    实测最大 0.8 MP -> 1216x672 = 817,152 px。
#    它们**没有**「手填宽高」这条交互，所以 2.0M 对它们没有意义；
#    保持原有档位不变（不误放宽）。
```

两处事实错误：

1. **`RES_MP = {544p, 768p}` 是**旧面板**（`#resSeg` 只有两档）的档位表**，
   不是工作流的约束**。把它当成「生成侧硬约束」是**范畴错误**。
2. **「没有手填宽高这条交互」已经不成立** —— 2026-11-15 的修复③ 把 flf/r2v
   改成了与 t2v **共用同一套视频面板**（`web/video-panel.js`），面板里本来就有
   「输出尺寸」直填框和「尺寸预设」下拉。

## 二、逐节点对照 nonebot seg1/seg2

### 2.1 nonebot seg1/seg2 的尺寸链路（实测 JSON）

```json
// minimax_h3_seg1.json  与  minimax_h3_seg2.json  完全一致
"115": { "class_type": "ResolutionSelector",
          "inputs": { "aspect_ratio": "9:16 (Portrait Widescreen)",
                      "megapixels": 2, "multiple": 32 } },
"136": { "class_type": "MiniMaxH3ReferenceToVideo",
          "inputs": { "width":  ["115", 0],     // ← ResolutionSelector 的输出
                      "height": ["115", 1],     // ← 直接接线，没有别的节点
                      "ref_image_size": "max", ... } }
```

消费关系实测（脚本遍历所有节点的 inputs 引用）：

```
seg1: [115] ResolutionSelector  -> [136] MiniMaxH3ReferenceToVideo.width  <- [115, 0]
      [115] ResolutionSelector  -> [136] MiniMaxH3ReferenceToVideo.height <- [115, 1]
seg2: 同上（完全一致）
```

**seg1/seg2 用的是 `megapixels: 2`（= 2.0 MP），不是 0.8。**
16:9 下 `ResolutionSelector(2.0, multiple=32)` → **1920×1088**。

### 2.2 差异表

| 维度 | nonebot seg1/seg2 | 我们（改前） | 我们（改后） |
|---|---|---|---|
| 尺寸来源节点 | `ResolutionSelector{megapixels:2, multiple:32}` | 前端算好 width/height 直传 | 同 seg（前端直传，服务端权威吸附） |
| 条件节点 | `MiniMaxH3ReferenceToVideo`（ComfyUI 核心） | `MiniMaxH3AudioConditioningT8`（T8 插件） | **不变**（见下） |
| 底模 | `minimax_h3_hybrid_fl2va_ref2va_b30-49-int8.safetensors` | flf=`fl2va_pruned_int8` / r2v=`hybrid_fl2va_ref2va` | 不变 |
| 送进节点的宽高 | **1920×1088（2.0 MP）** | **1216×672（0.78 MP）** | **1920×1088（2.0 MP）** |
| `ref_image_size` | `"max"` | `"match"` | 不变（见下） |
| 接续链路 | `LatentSave / CopyBridge / TrimAV`（Relay-Kit） | 同（上一轮已完成） | 不变 |
| 服务端面积门禁 | 无（节点无 gate） | **0.8MP 硬拦截** | **2.0MP** |

### 2.3 为什么**不需要**换节点（两点澄清）

**① 条件节点不用换。**
seg 用核心节点 `MiniMaxH3ReferenceToVideo` 是因为**它没有音频输入**；
而我们必须支持「参考音频当音轨」「参考视频音轨同步切割」等能力，
只有 T8 的 `MiniMaxH3AudioConditioningT8` 一个节点能同时覆盖
首尾帧 / 参考图 / 参考视频 / 参考音频 / 驱动音频（见 `h3studio/h3_video_modes.py:1-40`
的选型说明）。换回核心节点会**丢掉已验收的音频续接时序能力**。

**关键证据：两个节点的宽高上限完全相同（都是 `MAX_RESOLUTION=16384`），
面积策略也都无 gate** —— 所以**「分辨率上限」与「用哪个节点」无关**，
换节点解决不了任何问题。

**② `ref_image_size` 不用改。**
seg 用 `"max"`（参考图短边缩到 `REF_IMAGE_SHORT_EDGE=2048`），
我们用 `"match"`（参考图按生成画布面积等比缩放，`conditioning.py:335-343`）。
**这是刻意选择**：seg 的 `"max"` 会把参考图按**它自己的**短边缩放，与画布尺寸无关；
而我们要求「参考图与生成画布同尺度」，否则大画布下参考图会相对变小、
参考强度失真。改 `ref_image_size` 与「突破分辨率上限」**不是同一件事**。

### 4.6 收尾复验时发现并修掉的取证脚本缺陷（3 处真实缺陷）

本轮收尾复核「分辨率突破证据是否成立」时，逐条去盘上核对，发现**上一轮留的
`live_reso_e2e.json` 里 r2v 记的是 `ok:false / "没有产物路径"`**。查下来
**不是 r2v 没跑通**（作业 `done`、产物 1920×1088 在盘上），而是**取证脚本自己
有三个缺陷**，导致证据「假阴性」。三处都已修（commit `85a2659`）：

| # | 缺陷 | 根因（带源码坐标） | 后果 | 修法 |
|---|---|---|---|---|
| 1 | 产物路径取不到 | 脚本只认 `outputs[].path`，但库里视频条目的字段是 `{"kind":"video","file":...}`（`server.py:5509`） | flf/r2v 都记成「没有产物路径」 | 同时接受 `file`/`path`，`file` 优先 |
| 2 | 相对基准错 | `outputs[].file` 是相对 **`data_dir/outputs`** 的路径（`server.py:289` `OUT_DIR = DATA / "outputs"`），脚本拼成 `DATA/rel` | 得到 `data/videos/xxx.mp4`（不存在） | 改为 `DATA / "outputs" / rel` |
| 3 | r2v 参考视频选材 | 脚本取「最新一个视频素材」，而素材库大量 1 秒 `e2e-sample` 短片只有 24 帧；上游 T8 的参考策略要求 **ref_video ≥ 48 帧**（`comfyui-minimax-h3-audio-T8/h3_t8/core.py:31` `reference_video_frame_warnings`） | r2v 被上游拒收：`ValueError: ref_video_1 must contain at least 48 frames` | 按 ffprobe 实测帧数筛第一个 ≥ 48 帧的素材 |

> 第 3 条是**上游既有正确行为**，不是我们系统的缺陷 —— 参考视频太短时
> T8 拒绝是正确行为。缺陷在于取证脚本没有按这个前置条件选材。

修完后在 8190 上重跑 `tests/live_reso_e2e.py --mode both`：


如果只看 `live_reso_e2e.json` 就写进报告，就会把一个假失败当成真缺陷。
本轮的做法是：**一律回盘上用 ffprobe 独立复核**，不信脚本自述。

1. **2.0 MP 是上限，不是无限。** 3.5 MP（2560×1440）仍被服务端拦住，
   中文文案为「首尾帧生视频分辨率上限为 2.0M 像素（2,097,152 px）。

   若将来要更大，需要重新评估 H3 权重本身的训练分辨率（官方模板 Note 只背书到 2.0 MP）。
2. **VRAM 由用户承担。** 上游节点对超参考区只警告不拦
   （`reference_area_policy: warning_only_no_area_gate`），2.0 MP 在 4090D 上已验证跑通；

   理由见 §2.3②。若将来要完全对齐 seg 的参考图缩放语义，需单独评估对
   「参考强度」的影响。
4. **本轮改动引入了两次行尾事故（已修复）**：编辑脚本用 `Path.write_text`
   把 `server.py` / `web/app.js` 的 CRLF 归一化成 LF，触发 `.gitattributes` 的
   `-text` 规则告警（diff --stat 虚增到 20751 / 15058 行）。已转回 CRLF 并
   逐个核对 `.gitattributes` 里全部 `-text` 文件与基线行尾一致。
   **教训**：本仓 `-text` 文件必须用二进制方式读写，不能用 `write_text`。
5. **并发**：本次实测期间本机还有另一测试集任务在跑，ComfyUI 队列会互相排队，
   1920×1088 的 flf 单段实测耗时约 12 分钟（4 步采样）。
6. **r2v 的参考视频有前置长度要求**（上游既有行为，不是我们系统的限制）：
   `MiniMaxH3AudioConditioningT8` 要求参考视频 **≥ 48 帧**
   （`h3_t8/core.py:31`），短于 2 秒的参考视频会被拒
   （`ValueError: ref_video_1 must contain at least 48 frames`）。
   取证脚本已改为按 ffprobe 实测帧数选材（§4.6 第 3 条）。
   **但前端目前没有对「参考视频太短」给出前置提示** —— 用户提交后才由
   服务端报错。若要优化，应在 r2v 面板选素材时校验帧数并提前中文提示；
   本轮**未做**（属新增功能，超出「突破分辨率上限」的范围）。
7. **取证脚本的三处假阴性已修，但「脚本自述 ≠ 事实」这个教训没有工具化**：
