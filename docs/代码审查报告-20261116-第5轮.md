## 2. A 段 · 前端用户可见文案污染

### 2.1 真实泄漏（已修）

**位置**：`web/app.js:5842`（`skeletonJob()` 的 `prompt` 字段）

**原文案**：「正在载入任务内容，模型与参数稍后显示，**此处的临时文字仅用于对齐布局**。」

**为什么是真实泄漏**（不是误判）：

1. 该字符串经 `escapeHtml((p.prompt || "").slice(0, 80))` 直接进 `jobCard()` 的 `<b>` **文本节点** → 真的在 DOM 里。
2. CSS 只是用 `color: transparent` 把它**涂掉** —— 视觉上看不见，但：
   - 「复制页面内容」能带走；
   - 读屏软件会读出来；
   - 用户 Ctrl+A 复制时能看到。
3. 「临时文字」「对齐布局」是**开发者内部说法**，不是给用户看的话。

**修法**：换成纯用户向的加载态文案（33 字，与原文案等长 → 布局不变）：

```
正在载入任务内容，模型与生成参数稍后显示，请稍候片刻即可查看详情。
```

**修后证据**：见 §5.2 —— 线上渲染后 DOM 的 `textContent` + 全部属性值里不含该文本。

### 2.2 扫描器自身的三个真实 bug（本轮修掉）

上一轮（第 4 轮）留下的 `docs/scan_visible_pollution.py` 有三个问题，导致**它的结论不可信**：

| bug | 现象 | 影响 |
|---|---|---|
| 只扫「赋值点同一语句」 | 文案定义在**对象字面量**里 → 漏掉「对象字面量 → 后续渲染进 DOM」的间接路径 | **本轮真实泄漏正是这种形态 → 第 4 轮扫描器抓不到** |
| 用正则抽字符串字面量 | 模板串内部也含引号（`<div class="enhance-warn">`），正则把模板静态文本里的 `"` 当成字符串起点 | 一路吞到下一个 `"`，把中间注释和代码全算进来 → 大量假阳性 |
| 正则字面量 / 嵌套模板串未处理 | `${cond ? \`<span>${x}</span>\` : ""}`（providers.js 实测存在）→ 内层反引号提前终止外层模板串 | 整段后续代码被当成字面量 |

**本轮新建** `scripts/cr5_scan_text_candidates.py`：统一分词器（正确处理行注释 / 块注释 / 字符串 / 模板串 / 正则字面量，递归处理 `${}` 里的**嵌套模板串**）+ 宽口径候选池 + 新增一道「innerHTML 模板里嵌 HTML 注释」的面（不渲染但进 DOM，「查看源代码」能带走）+ 排除 CSS 类名/选择器。

**扫描器自身的回归测试** `tests/test_cr5_text_scanner.py`（10 用例）：
- **假阴性防护**：把真污染注回去必须被抓到（含本轮真实泄漏的形态）；
- **假阳性防护**：CSS 类名（`bar` / `bar-label` / `.prompt-enhance-bar`）与正常用户提示语（「暂时无法确认任务是否仍在运行」/「User 模板必须包含 {prompt} 或 {original} 占位符」）不得被报成污染。

### 4.2 并发对拍的已知局限（必须说明）

并发对拍里浏览器测试会抢同一个 Chrome / 端口 → 一侧失败、另一侧**根本没跑到**该文件 → `comm` 会报出假「新增失败」。

**处置**：并发对拍只用于**筛出候选差异文件**；每个候选差异文件再用 `scripts/serial_recheck_cr5.sh` **串行**复跑（同一时刻只跑一个 pytest）定性。

### A.3 `tests/test_agent_oneshot_e2e.py` —— 1 条 · **测试隔离缺陷（非产品缺陷，非预算不足）**

严重度：Medium
用例：`_E2EBase::test_one_shot_real_http_tool_card_has_args_and_result`

**失败形态**（现场复现）：
```
playwright._impl._errors.TimeoutError: Timeout 90000ms exceeded while waiting for event "response"
  at tests/test_agent_oneshot_e2e.py:568  page.expect_response(..., timeout=90000)
```

**根因**：测试只打桩了 Agent 主循环的 LLM 调用，**漏了提示词增强管线的 LLM 调用**。

调用链（现场核实）：
```
h3studio/agent.py:1581        agent_enhance.enhance_for_mode(ctx, mode, prompt, ...)
  -> h3studio/agent_enhance.py:122   llm_client.call_provider(provider, messages, options={...,"timeout": _step_timeout()})
     -> h3studio/llm.py:374          ClientTimeout(total=compute_timeout(max_tokens), connect=10)
```
- `call_provider` 在 **`h3studio.llm`** 模块；测试打桩的是
  **`h3studio.agent.llm_client.call_provider_with_tools`** —— 不同模块、不同函数。
- 测试替身 `_fake_server` 在 `model_providers` 表注册了指向 `http://127.0.0.1:5000` 的
  「测试模型」provider（`tests/test_agent_oneshot_e2e.py:142-147`），并设为 default
  → 增强管线**真的去调本机 LLM**。

**实测证据（本轮现场插桩）**：

| 指标 | 数值 |
|---|---|
| 用例总耗时（打桩前） | 17.06s |
| 其中 `llm.call_provider` | **10.50s（占 62%）** |
| 单独测同一 provider 的真实响应 | 10.5s ~ 27.9s（随本机负载波动） |
| `refresh_comfy_node_names(force=True)` | 0.00s（ComfyUI 空闲，**不是**阻塞点） |
| 打桩后整文件耗时 | **14.42s / 5 passed**（原 46.25s） |

**为什么不是「等待预算不足」**：
- 90s 预算被击穿的那次总耗时 90s+，而**同一用例**另外几次跑出 14.69s / 22.84s；
  若只是「慢」，90s 应该够（最坏 27.9s 响应 + 6.5s 其余 ≈ 35s）。
- 波动来自**本机 LLM 的负载**，不是固定开销。
- ⇒ 真实缺陷是**测试没隔离外部依赖**：E2E 用例不该依赖本机 LLM 的可用性与速度。

**修法**：`_patch_model` 补上第二条链的打桩 —— 打桩 `h3studio.llm.call_provider`，
返回固定的、且能通过增强管线校验的扩写文本（非空 / 非系统提示词复读 / 不违反提示词硬约束）。
**产品代码一行没动；没有 skip / xfail / 放宽断言。**

**为什么只有这一条受影响**：同文件其它 4 条用例用的工具是 `list_modes` / 未知工具，
**不建任务** → 不走增强管线 → 不调 LLM。与观测（1 failed / 4 passed）完全吻合。
