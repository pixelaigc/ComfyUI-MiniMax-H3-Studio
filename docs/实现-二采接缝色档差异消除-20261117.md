## 1. 现场重新取证（不沿用历史结论）

### 1.1 为什么必须重做

上一轮报告（附录 B）给出的归因是：

> 「SelfLift 的低分辨率段把钉住区**降采样**后当锚点 → 新生成区继承了低分辨率段的色档」

这句话隐含一个可检验的推论：如果色档阶跃来自段2 的**采样过程**，
那么段2 自己的头几帧内部就已经有色档阶跃，而且这段阶跃在**段2 单独播放时同样存在**
（不依赖拼接）。上一轮没有做这个检验。

本轮要求「**不沿用历史结论**（历史报告可能有误）」，所以写了**独立测量器**从零实现度量口径。

### 1.2 独立测量器（tools/seam_metric.py）

新写的测量器与上一轮的口径**不同**，并且刻意避免了自指循环：

| 项 | 上一轮口径 | 本轮口径 | 为什么要改 |
|---|---|---|---|
| 帧间差范数 | 未记录（历史值 19.39 无法用 L2 复现） | **同时**给 L1 与 L2 | 历史数字无法复现 ⇒ 口径不明 ⇒ 不能对拍 |
| 段内尺度 | 未记录 | **中位数**（robust） | 用均值会被接缝异常值污染；用均值会形成「跳变越大→尺度越大→比值越小」的**自证循环** |
| 归因 | 只量拼接点 | **段2 内部**也量 | 决定修法方向的分水岭 |
| 空间高频 | 只量色度/亮度 | 加**空间高频能量**（Laplacian 近似） | 降采样锚点有独特的细节档指纹 |
| 通道级 | 只量总差 | 加**逐通道**差 + Lab 色度 | 区分「亮度阶跃」vs「色相阶跃」 |

测量器还做**帧数守恒**校验（`full == seg1 + seg2`）和**接续点交叉验证**
（在全片里反向搜段2 首帧出现的位置）。

### 1.3 决定性发现：断点在段2 内部，不在拼接点

用同一套测量器量线上真实产物（受控复现，老提示词 + 老种子）：

| 链 | 参数 | 拼接点跳变 | 拼接比值 | **段2 内部断点** | 段内比值 |
|---|---|---|---|---|---|
| 缺陷档 | steps=4, ts=3, rho=0 | 10.137 | 15.372x | **13.746** | **58.436x** |
| 改 ts | steps=4, ts=2, rho=0 | 2.799 | 2.996x | **1.076** | 1.724x |
| 非二采对照 | twopass=off | 2.236 | 1.622x | 0.386 | 0.252x |
| 高 NFE 档 | steps=7, ts=5 | 3.446 | 8.072x | 0.231 | 1.312x |

逐帧亮度剖面（受控复现的缺陷档）：

```
段1 尾10帧亮度: [95.949, 95.751, 95.184, 93.818, 94.55, 93.294, 92.485, 92.603, 91.544, 91.013]
段2 头10帧亮度: [89.04,  93.49,  88.571, 90.386, 89.592, 87.688, 85.951, 84.956, 84.802, 86.048]
拼接边界跳变: 91.01 -> 89.04  = -1.97   ← 拼接点本身不算大
段内断点    : 89.04 -> 93.49  = +4.45   ← 真正的大跳变在这里（段2 内部）
```

**结论**：拼接点只跳 -1.97，而段2 内部第 0→1 帧跳 +4.45（RGB L1 更是 13.75）。
⇒ 上一轮的「拼接 setpts + match_prev」**方向没错但打不中要害** ——
它修的是拼接点，而真正的断点在段2 的采样结果里。

### 1.4 机制（ComfyUI 日志，决定性证据）

ComfyUI 日志的 `[SelfLift plan]` 行直接给出 NFE 分配：

```
steps=4  transition_step=3 -> low_nfe=3 high_nfe=1 sigma_prediction=0.92336 sigma_resume=0.72073
steps=7  transition_step=5 -> low_nfe=4 high_nfe=5 sigma_prediction=0.75    sigma_resume=0.58682
steps=4  transition_step=3 rho=0.6 -> low_nfe=3 high_nfe=1 sigma_resume=0.72073
```

SelfLift 的切表语义（`comfyui-SelfLift/nodes.py`）：

- 低分辨率一采 = `sigmas[:transition_step+1]` → **transition_step 次评估**
- 高分辨率二采 = `sigmas[transition_step:]` → **steps - transition_step 次评估**

**⇒ 默认档（steps=4 + transition_step=3）高分辨率二采只剩 1 步 NFE，
且这 1 步的起始 sigma 高达 0.72（噪声极重）。**

### 1.5 空间高频指纹（降采样锚点的直接证据）

段2 各帧的空间高频能量（Laplacian 近似均值）：

| 链 | 帧0 | 帧1 | 帧2 | 帧3 | 帧10 | 帧50 |
|---|---|---|---|---|---|---|
| 缺陷档 | 0.436 | 0.429 | 0.431 | 0.468 | 0.506 | **2.922** |
| 缺陷档（另一条） | 0.440 | 0.433 | 0.432 | 0.469 | 0.515 | **2.922** |
| ts=2 改档 | 0.446 | 0.494 | 0.495 | 0.506 | 0.414 | 0.444 |
| steps=7/ts=5 | 5.578 | 5.574 | 5.582 | 5.580 | 5.651 | 5.767 |
| 非二采对照 | 1.607 | 1.506 | 1.547 | 1.477 | 0.797 | 0.510 |

缺陷档的段头 4 帧高频只有段中段的 **15%** —— 这就是「低分辨率段降采样后当锚点」的指纹。
（steps=7 那条头尾一致，是因为它本来就是另一条链，不是同一提示词，不能直接比。）

### 1.6 机理小结

低分辨率一采把「钉住区 + 新生成区」一起降采样（`lowres_scale=0.75`），
在**降采样空间**里定下了色档与细节档；抬升回高分辨率后，
高分辨率二采必须同时做三件事：**提分辨率 + 收敛色档 + 生成内容**。

当高分辨率只剩 1 步 NFE（sigma 0.72 → 0）时，这个预算不够，
结果就是段头几帧**色档 + 细节档双重掉档** —— 肉眼就是「闪一下」。

## 2. 修法与取舍

### 2.1 为什么不需要改 comfyui-SelfLift

`transition_step` **本来就是 SelfLift 的公开节点输入**
（`comfyui-SelfLift/nodes.py` 的 `INPUT_TYPES` 里就有，tooltip 写着
「Number of low-resolution denoiser evaluations」）。
高分辨率 NFE = `steps - transition_step` 是**纯算术**，Studio 侧就能算清楚并夹住。

⇒ **零 comfyui 改动**，`/home/ubuntu/comfyui` 的 git 状态与本轮开始时一致。

### 2.2 修法：NFE 预算护栏

新增 `h3studio/twopass_budget.py`（纯函数层）：

```python
HIGH_RES_NFE_MIN_RATIO = 0.5

def high_res_nfe(steps, transition_step):
    return max(0, int(steps) - int(transition_step))

def clamp_transition_step(steps, transition_step, min_ratio=0.5):
    # 高分辨率 NFE 下限 = ceil(steps * min_ratio)
    # => transition_step <= steps - ceil(steps * min_ratio)
    ...
    return min(ts, max_ts)
```

夹取效果：

| steps | 原 ts | 夹后 ts | 低分辨率 NFE | 高分辨率 NFE |
|---|---|---|---|---|
| 4 | 3 | **2** | 2 | **2**（原 1） |
| 4 | 2 | 2 | 2 | 2 |
| 4 | 1 | 1 | 1 | 3 |
| 7 | 5 | **3** | 3 | **4**（原 2） |
| 7 | 4 | **3** | 3 | 4 |
| 8 | 6 | **4** | 4 | 4 |
| 20 | 8 | 8 | 8 | 12 |

### 2.3 夹取的代价（必须说清）

夹取是**有损**的：一采步数变少 = 低分辨率段的提速收益变小
（低分辨率段的注意力面积小，本来就是二采提速的主要来源）。

具体地，steps=4 时：
- ts=3：低分辨率 3 步（快），高分辨率 1 步（**色档掉档**）
- ts=2：低分辨率 2 步（略慢），高分辨率 2 步（色档正常）

所以取 1/2 而不是 1/4：**保证高分辨率段拿到一半预算，同时保留一半的低分辨率收益**。

### 2.4 留痕（不允许静默改参数）

夹取**必须**让用户看得见。服务端 `normalize_t2v_params` 走既有机制
（`normalize_notes` → 任务详情展示）：

```
twopass.transition_step：3 不是合法取值，已改用 2
（高分辨率二采至少要拿一半的 NFE 预算：一采 2 步（二采 2 步，高分辨率占 50%）；
  否则段头会色档掉档 = 接续点闪烁）
```

前端（`web/video-panel.js`）也**提前**提示会怎么夹：

```
（高分辨率二采只剩 1 步，服务端会自动把一采步数夹到 2 步，
  否则段头会色档掉档＝接续点闪烁）
```

### 2.5 双层闸

| 层 | 位置 | 作用 |
|---|---|---|
| 第 1 层 | `server.py:normalize_t2v_params` | 归一 + **留痕**（用户可见） |
| 第 2 层 | `h3studio/video_workflow.py:_twopass_block` | **节点下发那行**再夹一次（最后一道闸） |

第 2 层的原因：工作流构建可能被别的入口直接调用（测试 / 其它调用方），
在那里再夹一次保证**节点永远拿不到「高分辨率 NFE 不足」的 transition_step**。

## 6. 已知遗留

### 6.1 二采接缝比值仍非二采的 1.85 倍（2.996x vs 1.622x）

修复后两者**同量级**（修复前是 9.5 倍差距），但二采仍略高。
残差来自 SelfLift 的低分辨率锚点机制本身：即便给了高分辨率一半预算，
抬升起点仍带一点低分辨率段的色档残影。
