### B-3【High】切模式不清 `state.files` / `state.assetRefs` ✅ 已修

**位置**：`web/app.js:461` `renderMode()` → `row.innerHTML = ""`；写入点仅 `web/app.js:589/615-616`（填槽位时），**全仓零清理点**

**问题**
```js
// renderMode() 只重建 DOM，state 里的槽位状态从不清空：
row.innerHTML = "";
```
`grep 'state\.files\s*=|state\.assetRefs\s*=|delete state\.'` → 除「填槽位时写入 / 同槽位覆盖时 delete」外**命中 0 处清理点**。

**危害（这是 B-2 的根因，不是 B-2 本身）**
第 3 轮修的 B-2 是在**提交处**加模式白名单。它能挡住「槽位 key 不属于当前模式」（如 flf 的 `first` 到了 r2v），但**挡不住同 key 跨模式复用** ——
`refvid0` / `refaud0` 在 **flf 与 r2v 都存在**。用户在 flf 选了参考视频，切到 r2v 后它会原封不动跟着进 r2v 的提交体。

连带 B-12：`audioTrackAvailability()` 读的就是 `state.assetRefs` / `state.files` → 新模式里错误出现「使用参考音乐作为成片音轨」。

**修法**
```js
// web/app.js 模块级唯一真源（渲染侧与提交侧共用）
const MODE_ALLOWED_SLOT_KEYS = {
  flf: (key) => key === "first" || key === "last"
    || /^refvid\d+$/.test(key) || /^refaud\d+$/.test(key),
  r2v: (key) => /^ref\d+$/.test(key)
    || /^refvid\d+$/.test(key) || /^refaud\d+$/.test(key),
};

function resetSlotsForMode(mode, keepSlots) {
  const allowed = MODE_ALLOWED_SLOT_KEYS[mode];
  const keep = (key) => allowed ? allowed(key) : false;
  if (keepSlots) return;          // 同模式重渲染例外（见下）
  for (const key of Object.keys(state.files || {})) {
    if (keep(key)) state.files[key] = null;
    else delete state.files[key];
  }
  state.assetRefs = {};
  state.slotPreviewUrls = {};
  state.audioTrackSource = "";
}
```

**「keepSlots 例外」为什么必要**（本轮踩到的坑，如实记录）：
队列化改造（2026-11-13）明确要求「提交后**不再清空**参考图 / 参考帧选择」—— 用户要能**连续提交**多个任务。若 `renderMode()` 无条件清，第二次提交会被前置校验拦下，**已交付的「连续提交」能力直接坏掉**。
所以区分两类 `renderMode()` 调用：
- 切模式（`activateMode` / 启动恢复）→ `keepSlots` 未传 → **清**
- 提交成功后的同模式重渲染 → `keepSlots = true` → **保留**

**现场实测（8190 线上，部署后）**
```
注入 flf 状态后： refs=[first, refvid0, refaud0]  audio=reference
切到 r2v 后：     refs=[]  files=[]  prev=[]  audio=""
                 audioOptions=[""]   ← 不再错误出现音轨选项
```

**「B-2 残余绕过」已一并堵住（复核 agent 专项提出，现场复验）**

第 3 轮修的 B-2 是**提交处**的白名单守卫。复核 agent 指出它有两条残余通道，本轮实测确认**两条都已堵住**：

| 残余通道 | 基线行为（8190 实测） | 修复后（8190 实测） |
|---|---|---|
| **共享槽位** `refvid0`/`refaud0`（flf 与 r2v **都合法**） | flf 填 `refvid0` → 切 r2v → 提交体仍带 `{"slot":"ref_video"}`，而 r2v 界面 `filled=false` | 切 r2v 后 `refs=[]` → 提交体 **0 条** `asset_refs` |
| **本地文件通道** `state.files`（白名单管不到） | 切回 flf 后提交体仍带 `file_first=[File:first.png]`，而界面 `filled=false` | 白名单外的 `first` 被**删除**；白名单内的 `refvid0` 值被**置 null**；提交体 **0 条** `file_*` |

> 这两条正是「白名单正确但底层 state 仍脏」的两种形态。**只修提交处白名单不够，必须同时清 state** —— 本轮的核心结论。

### B-10【Medium】`#genBtn` handler 是 async 且无顶层 try/catch ✅ 已修

**位置**：`web/app.js` 原 `addEventListener("click", async () => {...})`

**问题**：handler 主体 async，但 `try` **只包住最后的 fetch 段**。在它之前的这些调用一旦抛错就是**未捕获的 promise rejection**：
- `await askEnhanceGate()`（模态框操作）
- `imgCtx()` / `imgCurrentSize()`（图像模式参数计算）
- `window.VIDEO_PANEL.submitParams()`（共享面板参数收集）
- `currentPromptLevel()` / `currentOriginalPrompt()`

**用户影响**：**不会白屏**（复核 agent 实测确认：页面完整、DOM 正常、按钮在位），但用户看到的是「点生成**毫无反应**」—— 比报错更难排查（控制台里只有一条 `unhandledrejection`，且全站无 `onunhandledrejection` handler，只有 DevTools Console 可见）。

**修法**：原 body **原样**搬进 `async function onGenerateClick()`（避免 500 行整体缩进产生伪 diff），事件绑定处加顶层 try/catch → 异常从「静默丢弃」变成「明确告知用户」。
