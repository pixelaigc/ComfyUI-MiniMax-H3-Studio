## 1. 一句话结论

生成任务从「阻塞式提交」改为「入队式提交」：所有生成器共用**同一条**队列，
后端本来就是真正的串行队列（未改调度语义），本次补齐的是**队列可观测性** +
**前端去阻塞**，让用户能在任务运行中继续添加新任务。

## 2. 队列语义

### 2.1 队列是**后端已有的真队列**，不是前端改名

核对基线 `local/maintainer` 后确认：后端早就实现了真正的任务队列，本次**没有改动它的调度语义**：

| 环节 | 位置 | 既有行为（未改） |
|---|---|---|
| 建任务 | `server.py` `create_job_record()` | `INSERT INTO jobs ... status='queued'` |
| 取任务 | `server.py` `Worker._next_queued()` | `SELECT * FROM jobs WHERE status='queued' AND mode!='longfilm' ORDER BY created_at LIMIT 1` → 置 `running` |
| 执行 | `server.py` `Worker._loop()` / `_run()` | 单协程循环，**一次只跑一个**，跑完才取下一个 |
| 取消 | `server.py` `api_cancel()` | 已支持取消 `queued` 与 `running` 两态 |

也就是说需求 4「后端需真正支持任务排队与串行执行」**本来就满足**；
真正缺的是前端把提交按钮锁死，导致用户无法继续添加。

### 2.2 一个队列通道，所有生成器共用

所有生成器都走同一条路，没有任何按模式分流：

```
面板「生成」按钮 (#genBtn)
  └─ POST /api/jobs          （文生图 / 图片编辑 / 文生视频 / 首尾帧 /
  │                            参考生视频 / 文生音乐 / 参考生音乐 —— 同一个按钮）
  └─ create_job_record(mode, params)
       └─ INSERT status='queued'
  └─ Worker 单协程 FIFO 串行执行
```

内置 Agent 的 `create_job` 工具也复用同一个 `create_job_record()`，
因此 **Agent 建的任务与面板建的任务进同一条队列**。

### 2.3 状态机

| 状态 | 含义 | 队列面板显示 |
|---|---|---|
| `queued` | 已入队，尚未开始执行 | 排队中（带「第 N 位」序号） |
| `running` | 正在执行（同一时刻最多 1 个） | 运行中（▶） |
| `done` | 执行成功 | 成功 |
| `failed` | 执行失败 | 失败（带错误原因） |
| `canceled` | 用户取消 | 已取消 |

## 3. 后端接口

### 3.1 新增：`GET /api/queue`（只读队列快照）

`server.py` 新增 `queue_snapshot()` + `api_queue()`，路由注册在 `make_app()`。

响应 JSON：

```json
{
  "running": "faaa328f789c",
  "running_mode": "t2i",
  "pending": 2,
  "total": 3,
  "items": [
    {"id": "faaa328f789c", "mode": "t2i", "status": "running",
     "position": 1, "created_at": 1794569945.0,
     "label": "Z-IMAGE 文生图", "prompt": "queue probe 0"}
  ],
  "recent": [
    {"id": "c145df2c7187", "mode": "t2i", "status": "canceled",
     "created_at": 1794569947.7, "label": "Z-IMAGE 文生图",
     "prompt": "queue probe 2", "error": ""}
  ]
}
```

| 字段 | 含义 |
|---|---|
| `items[]` | 队列中任务，**按执行顺序（队首在前）**；含正在跑的那条 |
| `items[].position` | 1 = 队首（正在跑或下一个就跑），2、3… 依次后排 |
| `items[].status` | `running` / `queued` |
| `items[].label` | 生成类型中文标签（来自 `gen_types` 注册表，不硬编码） |
| `items[].prompt` | 提示词摘要（截断 120 字） |
| `pending` | 排队中（还没开始跑）的条数 |
| `total` | `items.length`（排队中 + 正在跑） |
| `recent[]` | 最近 12 条终态任务（成功 / 失败 / 已取消），按完成时间倒序 |

**设计约束**：

- `position` 从 1 开始且**包含正在跑的那条** —— 前端直接把 position 显示成
  「第 N 位」，用户一眼看出「我刚提交的那个排在第几」。
- 只统计 `mode != 'longfilm'`。长片合成走自己的
  `asyncio.create_task` + `LONGFILM_LOCK` 通道，不经过 Worker ——
  放进同一队列视图会给出「排在第 N 位但永远轮不到」的假信息。
- 队列视图最多返回 50 条（`QUEUE_VIEW_LIMIT`），防止异常情况下一次拉太多。
- 纯只读：不建任务、不改任何状态。

### 3.2 复用的既有接口（未改动）

| 接口 | 用途 |
|---|---|
| `POST /api/jobs` | 入队（返回 `{"id": ..., "status": "queued"}`） |
| `POST /api/jobs/{id}/cancel` | 取消排队中 / 运行中的任务 |
| `GET /api/jobs?status=queued` | 任务列表（生成库「进行中」标签） |
| `GET /api/system` | 状态栏（已含 `queued` 计数） |

## 4. 前端 UI 行为

### 4.1 生成按钮

| 场景 | 文案 | 可点 | 样式 |
|---|---|---|---|
| 队列为空 | `生成` | ✅ | 默认 |
| 队列非空 | `已入队（队列 N）` | ✅ **仍可点** | `.queued`（浅蓝底 + 蓝字） |
| 提示词增强中 | `已入队（队列 N）` / `生成` | ❌ 禁用 | 默认 |

- **关键**：队列非空时按钮**不再禁用**，用户可以连续提交多个任务。
- 只有「提示词增强中 / 二次细化中」才禁用 —— 增强会改写提示词，
  提交半成品提示词没有意义。
- `title` 提示：「当前队列 N 个任务（队首正在跑）。点击可继续加入队列。」

### 4.2 队列面板

位置：任务区顶部（`#queuePanel`），状态标签行下方。

```
┌─ 生成队列 ──────────────── 运行中 1 · 排队 2　　最近完成 3 · 失败 1 ─┐
│  ▶  文生视频      一只猫在屋顶上散步…              运行中      [取消] │
│  2  Z-IMAGE 文生图 赛博朋克城市夜景…                排队中      [取消] │
│  3  文生音乐      抒情钢琴…                        排队中      [取消] │
│  ·  文生视频      上一段视频…                      成功                 │
└───────────────────────────────────────────────────────────────────┘
```

- 序号列：运行中显示 `▶`，排队中显示 `position`（第几位），终态显示 `·`
- 状态列：`运行中` / `排队中` / `成功` / `失败` / `已取消`
- 每条待处理任务有**取消**按钮（复用既有 `/api/jobs/{id}/cancel`）
- 队列与近期记录都为空时面板整体隐藏，不占空间
- 「明细」按钮可折叠/展开列表
- 每 1 秒轮询 `/api/queue`（比任务列表的 2 秒更快，队列变化更及时）

### 4.3 顺带修掉的一个阻塞点

旧代码在提交成功后**清空**参考图 / 参考帧选择：

```js
state.files = { first: null, last: null, refs: [] };
state.assetRefs = {};
```

那是配合「提交一次就锁死按钮」的交互 —— 反正只能提交一次，清掉无所谓。
改成队列后，第二次提交时槽位已被清空，`flf` / `r2v` 会被前置校验直接拦下
（「首尾帧模式需要上传首帧图片」），**连续提交根本走不通**。
因此本次**不再清空**参考帧/参考图选择（提示词本来就一直保留）。

### 4.4 连点节流

按钮不再禁用后，用户可能手抖连点两下 → 队列里多一条**完全相同**的任务。
因此提交前有 800ms 节流（`GenerationQueue.shouldAcceptSubmit()`）。
800ms 足够区分「故意连做多个」与「手抖连点」。

### 6.5 回归中发现并修掉的一个「假失败」

首轮跑回归时 `test_running_job_card_shows_progress` 红了
（`168 passed, 1 failed`）。**基线 `local/maintainer` 同一条测试是绿的**，
所以确实是本次改动引入的。

**根因**：该测试用

```python
self.page.wait_for_function("() => document.body.innerText.includes('运行中探针')")
```

来等「卡片渲染出来了没有」，然后断言 `#jobsGrid` 的 HTML 里有 `progress-bar`。
但新增的**队列面板也会显示任务提示词**，而且它的轮询更快（1 秒 vs
任务列表的 2 秒）—— 于是 `document.body.innerText` 被**队列面板**提前满足，
那时任务列表还没重画，`#jobsGrid` 里自然没有那条 running 卡片的进度条。

**修法**：等待条件**收窄到卡片所在的容器** `#jobsGrid`，而不是整个 body：

```python
self.page.wait_for_function(
    "() => (document.getElementById('jobsGrid')?.innerText || '').includes('运行中探针')")
```

这才是该测试本来的断言意图（「卡片渲染出来了没有」）。
同类修正在 `test_status_realtime.py`（3 处）与
`test_frontend_defaults.py`（1 处）各做了一轮。

**这不是放宽断言** —— 断言本身（`progress-bar` 必须在 `#jobsGrid` 的 HTML 里）
一字未动，改的只是**等待条件指向错了容器**。

## 7. 已知限制

1. **长片合成不在队列里**。`longfilm` 走自己的 `asyncio.create_task` +
   `LONGFILM_LOCK` 通道，不经过 Worker，因此不参与队列排序，
   `/api/queue` 里也不含它。语义是「长片合成与生成任务并行」，
   不是「排在生成队列后面」。长片面板的「合成长片」按钮保持原样
   （提交后变「正在提交…」并短暂禁用），未做队列化。

2. **队列视图是全进程共享的**，不含用户维度。单机单用户部署下没有歧义；
   若将来做多用户隔离，需要给 jobs 表加 owner 维度。

3. **`recent` 只取最近 12 条终态任务**。更早的历史在生成库里看，
   队列面板不重复展示。

4. **队列面板每 1 秒轮询一次 `/api/queue`**。队列很长时（>50 条），
   面板只显示前 50 条，但计数 `total` 是全量。

5. **前端节流 800ms**。极快的手动连点会被吞掉一次提交；
   这是有意为之（避免重复任务），代价是「手速极快地连发两个不同任务」
   时第二个可能被拒。

6. **未做队列优先级**。严格 FIFO，先进先出。

7. **本次未部署**。分支 `local/feature/gen-queue` 需由用户决定合并到
   `local/maintainer` 与上线 8190 的时机。上线时注意：`server.py` 改了
   → **必须重启 h3-studio 服务**；`web/*.js` / `web/index.html` /
   `web/style.css` 是静态文件 → 改了立刻生效，但要破浏览器缓存
   （`generation-queue.js` 用的是新 URL `?v=genqueue1`，天然不冲突；
   `app.js` / `index.html` / `style.css` 的 `?v=` 版本参数需按惯例升版）。
   后端 `BUILD_FINGERPRINT` 会随 `server.py` 变化，前端据此提示
   「后端未重启」。
