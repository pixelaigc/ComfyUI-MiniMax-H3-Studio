#### 2.A.1 本轮修复的缺陷（真 500，线上实测复现）

**定位**：`server.py:6194 async def api_create` —— 第 1 行就是 `await request.multipart()`，**没有 Content-Type 校验**。

**根因**：aiohttp 的 `MultipartReader.__init__` 要求请求头里有 Content-Type
（`aiohttp/multipart.py:691` → `parse_mimetype(headers[CONTENT_TYPE])`）：
- 无 Content-Type → `KeyError: 'Content-Type'`
- 非 `multipart/*` → `AssertionError: multipart/* content type expected`
- `multipart/form-data` 但无 boundary → `ValueError: boundary missed for Content-Type`

三者都**抛异常**，aiohttp 默认错误处理把它变成 **HTTP 500「Server got itself in trouble」**。

**修复前实测（5 种，全是 500）**：

| 请求 | 修复前 | 修复后 |
|---|---|---|
| 无 Content-Type | **500** | **415** `content_type_required` |
| `application/json` | **500** | **415** `unsupported_media_type` |
| `text/plain` | **500** | **415** `unsupported_media_type` |
| `application/x-www-form-urlencoded` | **500** | **415** `unsupported_media_type` |
| `multipart/form-data` 无 boundary | **500** | **400** `content_type_invalid` |
| 正常 multipart | 400（业务校验） | 400（业务校验，**不变**） |

**为什么 500 必须修**：500 会被理解成「服务端崩了」，排查方向被带去 ComfyUI / GPU / 队列；
而真实原因只是「请求头没带对」—— 这是**调用方自己就能纠正**的问题，应该回 4xx 并说清楚该带什么。

**为什么不用 try/except 把异常包成 4xx**（假修法）：
那会把**真实的服务端故障**（DB 挂了等）也伪装成 400，排查难度反而更高。
本轮在**异常发生之前**做校验，并加了专门断言「业务错误不被内容类型校验的 code 覆盖」。

## 3. 已修并上线

### 3.1 修了什么

**`server.py:api_create` 补 Content-Type 校验**（自包含，43 行）。

```
缺 Content-Type              -> 415 content_type_required
非 multipart/*               -> 415 unsupported_media_type
multipart/form-data 无 boundary -> 400 content_type_invalid
正常 multipart               -> 穿过校验，交给业务校验（行为不变）
```

**为什么是 415 而不是 400**：415 Unsupported Media Type 的语义就是「请求体格式不对」。
**为什么不把 `application/json` 静默降级成能处理**：提交路径要的是文件流；
静默降级会让「文件没带上」这类问题**更晚暴露、更难查**。
