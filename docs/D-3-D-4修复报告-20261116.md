## 1. D-4 根因

**现象**：全量扫 534 个 job，**26 条**卡片显示 `MiniMaxH3TurboLoRA`，
而工作流实际用核心 `LoraLoaderModelOnly`（LightX2V×13 / DMAD×9 / 更好运动×2 / SLA×1 / 中文名×1）。

**根因链**（本轮实测逐环核实）：

1. 存量落库数据的 `params["accel_lora"]` 存的是**权重名形式**，不是目录 key。
   本轮实测全量扫描：**253/253 个**带 `accel_lora` 的 job 全是**裸权重名**
   （如 `minimax_h3_fl2v_turbo_4step_v1.0_768p_comfyui_bf16`，无目录前缀、无扩展名），
   形态分布 `{bare: 253}`，**没有一条**是目录 key 形式。
2. `video_models.accel_lora_meta(key)` 按**目录 key**查清单 -> 权重名查不到 -> 返回 `None`。
3. 显示层 `vmodels.detect_accel_lora_loader(meta["name"])` 拿到 `meta["name"]` 是空串
   -> `find_weight("")` 返回 `None` -> 走「**读不到文件 -> 保守回落 Turbo 节点**」分支
   （`video_models.py:1989-1991`）-> **显示 Turbo 节点**。

**工作流实际挂载正确**（history 逐条反查 class 确为 `LoraLoaderModelOnly`、权重确实生效），
**不影响出片**；但该字段的用途正是排查静默失效，显示反了会误导。

**为什么不能直接改 `detect_accel_lora_loader`**：它的保守回落是**工作流构建侧的正确防御**
（「宁可要一个能看见的失败，也不要静默失败」—— Turbo 节点加载失败会打日志，核心节点失败是静默的）。
显示侧要的是「事实」，两边语义不同 ⇒ **在显示层单独归一，不动工作流侧**。

### 4.2 与验收方建议的差异（已核对后采用不同写法，说明理由）

验收方给的同族归一参考：`turbo_4step_cn*` -> **scheduler simple**；shift 12/3。

本轮**没有**把 `turbo_4step_cn*` 的 scheduler 写成 `simple`，理由：
- 权重 `__metadata__` 里**只**写了 `sampler_steps=4`，**没有** scheduler 字段；

  （带运行期 AdaLN 重注入）；`turbo_4step_cn*` 键名带 `diffusion_model.` 前缀、
  必须走**核心** `LoraLoaderModelOnly` —— **两者不是同一个加载路径**，
  照抄 scheduler 属编造。
- 故如实写「作者未提供」；shift 用 ComfyUI 的 H3 内生值 12/3 并把来源标成
  **`comfyui`**（不是「作者提供」）—— 前端会显示「（ComfyUI 模型硬性值）」。

`lightx2v_4step_v01_comfy` / `lightx2v_sla_768p_root` 的 **shift 6/3** 与验收方建议**一致**，
且已由同族已有条目的作者规格表佐证。
