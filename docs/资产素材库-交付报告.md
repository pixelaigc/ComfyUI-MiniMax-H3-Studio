## 4. 深度音频分析管线

### 4.1 接入方式（不重写算法）

素材库 → `h3studio/audio_deep.py` → 子进程调 `/root/projects/audio-analysis/analyze_audio.py`
→ 拿固定结构 JSON → 渲染成全中文分析文本 + 结构化 extra → 写入 `asset_analyses`。

运行环境**强制** ComfyUI venv：`/home/ubuntu/comfyui/venv/bin/python3`
（系统 hermes venv 没有 torch/transformers/funasr/demucs）。

### 4.2 输出内容（真实素材 `05.wav`，116.66s）

| 章节 | 内容 | 实测值 |
|---|---|---|
| 一、音频基本信息 | 容器/编码/时长/采样率/声道/比特率 | wav / pcm_s16le / 116.66s / 44100Hz / 2ch |
| 二、节拍与速度 | BPM 双引擎互证 + 候选值 + 规整度 + 局部速度曲线 | 151.999 / essentia 151.714，候选 76/152/304，规整度 0.9426 |
| 三、乐器与音色 | CLAP 零样本占比 + AST 帧数 + 逐窗乐器情绪 | 合唱 0.3877、人声演唱 0.3567、口播旁白 0.1254…；CLAP 45 帧 / AST 45 帧 |
| 四、人声检测与分离 | silero VAD 语音段 + demucs stem 占比 | voiced_ratio 0.2997、speech 34.97s、vocals 98.53% |
| 五、语音识别（带时间戳） | faster-whisper 段级 + 字级 | 29 段，如 `[00:11.04 → 00:14.12] 西瓜大又甜啊,` |
| 六、语义补充分析 | H3 Studio Provider 的 LLM JSON | mood / structure / lyrics_summary / use_cases / tags |
| 七、分析过程说明 | 耗时、计算设备、**源文件校验**、失败阶段 | md5 一致，未转码；全部阶段成功 |

### 4.3 不二次转码（硬校验）

分析前后各取一次源文件指纹（md5 + size + mtime），不一致直接抛
`audio_source_mutated` 并中止，不静默接受。

实测：`/mnt/usb2t/Project/src/music/05.wav` 与素材库内存储的原件
md5 均为 `534e44c53c45c7f6101e3237f845d657`，size 同为 20578348。
脚本本身只在内存里重采样，demucs 只统计不落盘。

### 4.4 异步与进度

深度分析 512 秒（CPU），不能阻塞上传/触发接口：
- 触发 → 立刻返回 `job_id`（实测 HTTP 200 + `{job_id: 2, status: queued}`）
- 后台线程执行，状态实时写 `asset_analysis_jobs`
- 前端每 2 秒轮询 `/analysis-status`，进度条显示中文阶段：
  测算节拍速度 / 识别乐器与音色 / 检测人声与分离伴奏 / 语音识别（含时间戳）/ 大模型语义补充
- 同一素材已有在跑的任务时返回 `already_running: true`，不重复排队

### 4.5 实测暴露并修掉的 5 个缺陷

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | GPU 加速形同虚设，永远退回 CPU | 显存表用了子引擎名（`clap/ast/vad/separation`），而脚本阶段名是 `instruments/vocals` → 需求恒为 0 | 显存表键名对齐脚本 `STAGES`；加回归测试断言两边键名集合一致 |
| 2 | P40 上跑 demucs/ASR 直接 SIGABRT（退出码 −6） | P40 是 sm_61，cuDNN 9.x 要求 sm_70+ | 选卡加 compute_cap 门槛（<7.0 跳过）；提示说明「算力不足，退回 CPU」 |
| 3 | 顶层 `errors[]` 为空但 asr/separation/ast 全挂 | 脚本的阶段内部失败只写在 `stage["error"]`，不进顶层 errors | 新增 `collect_stage_errors()` 汇总所有阶段失败，如实写进分析文本 |
| 4 | 进度条永远停在 2% | `progress_cb` 从没被调用 | 改为流式读脚本 stderr，检测 `stage xxx` 标记即回调；顺带用 Popen + 双线程读 stdout/stderr 避免管道写满死锁 |
| 5 | 前端「提交纠错」报 `Cannot operate on a closed database` | `_run_multimodal` / `_run_correction` 先 `conn.close()` 又复用同一 conn | close 后重新 `_library_conn()`；新增 `TestJobConnectionLifecycle` 3 例回归 |

## 6. 已知限制

1. **深度音频分析在 CPU 上很慢**（116s 音频 = 512s）。本机 4 张卡里
   4090D 被 Strata 占 46.8G、2080Ti ×2 各占 21G，只有 P40 空但算力不够 ——
   这是**本机当时状态**导致退回 CPU，代码会在有合适显卡时自动用 GPU。
2. 音频深度分析与多模态描述是**两条独立通道**：前者是确定性信号处理
   （BPM/乐器/人声/ASR），后者是模型看图看帧写自然语言。
   两者结果都落在 `asset_analyses.text`，用 `extra.analyzer_mode` 区分
   （`deep_audio_pipeline` / `multimodal` / `multimodal_correction`）。
3. 素材版本管理只做了数据结构，未做「上传同素材自动升版本」的完整交互。
4. 素材集 / 派生 fork / 版本回滚 UI 未实现（计划书列为第二版或可选）。
5. 全量检索用 LIKE，未上 FTS5（计划书建议 ≥1 万条再迁）。
6. 素材库使用独立数据库，与 jobs.db 的关联靠 `asset_refs` 显式登记 + 应用层约束，
   未启用跨库外键（SQLite 跨库不支持）。
7. `detect_instrument_switches.py`（乐器切换点）已具备但**未接入素材库**
   —— 它依赖 CLAP embedding 逐窗计算，与主管线重复计算一遍；
   如需接入，应做成独立阶段而不是复用 instruments 的结果。
