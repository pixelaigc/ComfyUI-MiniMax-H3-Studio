### P1-1 · 成片尾裁会**跨过接缝**（内容丢失 + 接缝断裂）

**位置**：`h3studio/continuation.py::chain_compensation_plan`（`trim` 计算段）

**严重度**：P1

**根因**

```python
trim = current - formula          # 无条件全扣到最后一段尾部
segment_trim[-1] = trim
```

`trim` 可能**超过最后一段自己的交付帧数**。那时尾裁一路吃进上一段：

| 场景 | 最后一段交付 | trim | keep_frames[-1] |
|---|---|---|---|
| 4 段 × 2 秒 | 34 帧 | **38 帧** | **−4**（负数） |
| 7 段 × 2 秒 | 34 帧 | 68 帧 | −34 |
| 7 段 × 4 秒 | 85 帧 | 89 帧 | −4 |

`keep_frames[-1]` 为负 ⇒ 成片里**该段被裁光并啃进上一段** ⇒
「上一段末帧 → 本段首帧」那个接缝**从成片里消失**，画面从段2 中段直接跳到段3 中段。

**为什么是 P1 而不是 P2**：接缝连续性是接续功能的**核心价值**
（`continuation.py` 自己的 docstring 记载：裁链首段/中间段会让接缝跳变从 0.67 涨到 5.8，
实测 10.32x）。本缺陷在**用户能通过面板选出的参数**下触发
（面板时长滑块 min=2，段数不限），且失败形态是**静默的内容丢失 + 画面跳变** ——
用户看到的是「成片少了一段 / 中间跳了一下」，不会收到任何提示。

**触发条件穷举**（整数秒 2~60 × 段数 1~11，共 594 组）：

```
n=4 dur=2s  trim=38  last_raw=34  keep_last=-4    ← 跨接缝
n=5 dur=2s  trim=48  last_raw=34  keep_last=-14
n=6 dur=2s  trim=58  last_raw=34  keep_last=-24
n=7 dur=2s  trim=68  last_raw=34  keep_last=-34
n=7 dur=4s  trim=89  last_raw=85  keep_last=-4
n=8 dur=2s  trim=78  last_raw=34  keep_last=-44
n=8 dur=4s  trim=102 last_raw=85  keep_last=-17
```

**修法**：**裁不到就不裁**。

```python
if trim > 0 and len(durations) >= 2 and trim > last_delivered:
    trim_clamped = True
    trim_clamped_extra = trim - last_delivered
    trim = 0          # 一帧都不裁 —— 保住全部内容与全部接缝
```

**为什么不是「夹到 `last_delivered`」**：夹住之后残差仍然 > 0（依然命中不了用户口径），
而代价是最后一段被**整个裁光**（内容彻底消失，且用户看不到提示）——
那是更糟的失败。宁可成片比口径长几帧并**如实报出残差**。

**新增字段**：`trim_clamped`（是否因会跨接缝而少裁）、`trim_clamped_extra`（少裁了多少帧）。

**回归**：`tests/test_cr6_p1_fixes.py::TestTailTrimNeverCrossesSeam`（4 条）
- `test_four_two_second_segments_keep_all_frames` —— 4×2s 专项
- `test_no_combination_yields_negative_keep_frames` —— 594 组穷举，负 keep = 0
- `test_normal_chains_unaffected` —— 5s→5s / 5s→5s→8s 不受影响
- `test_clamped_case_explains_why_in_notes` —— notes 说清「差多少、为什么不能补」

**变异自证**：注入「去掉夹住逻辑」→ 2 条断言失败（报出 `keep_frames[-1] = -64 / -43 / -22`）。

### P1-2 · 显示的累计时长 **≠ 真实成片长度**

**位置**：`h3studio/continuation_service.py::continuation_state`（返回值）
→ `server.py::row_to_job`（下发）→ `server.py::api_continuation_context`（下发）

**严重度**：P1

**根因**

成片拼接时做了尾裁（`server._concat_chain_video` 的 `trim_tail_frames`，
目的是让成片帧数精确命中用户口径「Σ请求时长 − (段数−1)×1 秒」）；
但 `continuation_state` 的 `total_frames` / `total_seconds` 是
「链上累计**交付**帧数」（= 各段帧数之和，**不含尾裁**）：

```python
state["total_frames"] = chain_frames + seg_frames      # 未尾裁口径
state["total_seconds"] = round(state["total_frames"] / cont.FPS, 3)
```

⇒ 卡片与接续面板显示的累计时长**比真实成片长**一个尾裁量。

**线上实测证据**（尾裁上线后的真实链，2026-11-18）：

| 任务 | 显示值 | 真实成片（ffprobe 实测） | 差 |
|---|---|---|---|
| `e451d93897e6`（5s→5s） | `total_seconds = 9.417`（226 帧） | `v-h3-studio-000531.mp4` = **216 帧 = 9.000s** | 10 帧 |
| `342cdf02533d`（5s→5s→8s） | `total_seconds = 16.500`（396 帧） | `v-h3-studio-000533.mp4` = **384 帧 = 16.000s** | 12 帧 |
| `1b29c6628914`（4 段 5s） | `total_seconds = 13.667`（328 帧） | `v-h3-studio-000033.mp4` = 328 帧（尾裁上线前） | 0 |

差值与「尾裁帧数」**完全吻合**（10 / 12 帧），根因确认。

**为什么是 P1**：用户看到「当前累计 9.417 秒」，拿到手的成片是 **9.000 秒**。
这是本项目最忌的「界面说的和产物不是一回事」（`h3_video_size.py` 模块 docstring
把这类缺陷称为「说谎的分辨率」，本轮是同一类问题在时长维度的复现）。
且这个显示值**会一路带偏**后续每一段 —— 它同时是 `chain_total_frames` 的来源。

**修法**：**协议层口径不动**，只在**展示层**补尾裁口径。

*协议层为什么不能改*：`continuation_state` 的 `total_frames` 有两个**不可改**的下游：
1. `server._prepare_continuation_params` 拿它当**音频偏移** C_n
   （口径：第 n 段之前已累计交付的帧数）。尾裁只砍**最后一段尾部**，
   永远不会影响任何一段的**起始**位置 —— 若把 C_n 改成尾裁后的值，
   后面每一段的参考音频都会偏移（音画错位）。
2. 它被写进下一段的 `continuation.chain_total_frames`，继续往后累加（同一理由）。

新增 `server._continuation_info_for_row(r, job_params)`：
用与拼接时**同一套** `cont.chain_compensation_plan` 算出 `keep_frames` 之和
= 成片真实帧数，作为展示值；同时保留 `raw_total_frames`（诊断用，就是 C_n 的来源）。

**修后实测**（同一批线上任务，用修后的算法重算）：

```
e451d93897e6: 显示(旧)=226帧/9.417s  →  显示(新)=216帧/9.000s   ✅ 与 ffprobe 一致
342cdf02533d: 显示(旧)=396帧/16.500s →  显示(新)=384帧/16.000s  ✅ 与 ffprobe 一致
1b29c6628914: 显示(旧)=328帧/13.667s →  显示(新)=312帧/13.000s  ✅
fec6e25740b9: 链首段（无拼接）124帧/5.167s → 不变              ✅
```

**回归**：`tests/test_cr6_p1_fixes.py::TestDisplayMatchesRealProduct`（3 条）
- `test_keep_frames_sum_is_the_real_product_length` —— 断言 216 / 384（线上 ffprobe 实测值）
- `test_protocol_layer_total_frames_is_not_changed` —— 断言协议层仍是 226 / 328（防回归）
- `test_server_display_layer_applies_trim` —— 断言展示层调用了 `chain_compensation_plan`
  且卡片行走的是展示层入口
