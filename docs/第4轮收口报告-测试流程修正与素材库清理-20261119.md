## 2. A｜E2E / 自动化脚本的生成动作修正

### 2.1 先取证，再动手（不靠推断）

| 取证 | 结论 |
|---|---|
| E2E 隔离实例面板**实际提交**（浏览器探针量出） | `steps=20 / accel_lora=""`（面板默认「不挂」）、`sampler=res_multistep` |
| 线上 8190 面板**实际状态**（只读探针量出） | `accel_lora=dmad_4step_critic`、`steps` 滑杆初值 4、`sampler=euler`、`scheduler=beta` |
| `steps=4` **不传**加速字段（服务端归一实测） | 自动兜底挂 `ckpt850`（`MiniMaxH3TurboLoRA` 节点进链），采样档 4/euler/beta |
| `steps=4` **显式** `accel_lora=""`（服务端归一实测） | **不挂任何 LoRA**，但 steps 仍被显式传成 4 → **4 步采样非蒸馏权重** = 真正的那条「不存在的路径」 |
| `/api/video-options` 实测清单 | 12 枚加速 LoRA，其中 7 枚 `recommended_steps=4` |
| 线上增强实测 | 返回 915 字导演稿，`#enhanceReplace` 写回提示词框成功 |

**关键判定**：用户说的「4 步没配加速 LoRA」，在服务端有两种形态 ——
不传字段时**隐式兜底**挂 ckpt850（看起来对了，其实没表达意图）；
显式不挂时**真的一条不存在的路径**。
所以修法不是「补个字段」，而是让 **steps 与加速 LoRA 成对出现**。

### 2.2 生产侧缺口与边界（重要）

`server.py::normalize_t2v_params` 对「显式不挂加速 LoRA + 用户显式传 `steps=4`」
**不报错**：它只在 `steps` 为空时才用标准多步档（20 步）。

- 这**不是**生产业务逻辑的 bug —— 用户手动拖 4 步是合法意图；
- 但脚本靠手写 `"steps": 4` 来「配 4 步」时，就必须同时配加速 LoRA。

> **决定：不改生产逻辑**，改在测试/脚本侧（steps 与 accel 成对）。
> 生产代码 diff = **0 行**（本轮只动 `tests/` 与 `scripts/`）。

### 2.4 一个必须说清楚的设计决定：增强失败允许重试

服务端对增强产物有**硬约束校验**
（`h3studio/skills/prompt-enhancer/scripts/validate.py`）：
产物里出现质量元标签（`高清` / `8K`）或 Compel 权重语法（`(S1)`）会被**拒收**（HTTP 502）。

- 这是**模型产物的随机性**，不是功能缺陷；
- 模板（`video-director.txt` 第 59-60 行）**本来就禁止**这些词，所以是模型偶尔不听话；
- 现实里用户看到「扩写结果违反硬约束」就是**再点一次「增强」**。

所以 `enhance_prompt()` 按用户真实行为**重试 3 次**；3 次全失败才报错。
**绝不静默跳过**（跳过 = 测试跑的是「没增强」的路径却看起来通过）。
