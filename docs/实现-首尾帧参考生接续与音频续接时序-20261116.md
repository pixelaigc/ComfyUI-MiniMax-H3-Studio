首尾帧（flf）与参考生（r2v）视频**已能真正按 nonebot 的 seg1/seg2 方式接续**

## 2. 时序实现细节

### 2.1 口径（唯一一条）

```
t_a_start(n) = C_n / 24          C_n = 第 n 段之前已累计**交付**的帧数（整数帧）
D_deliver(n) = (F_seg(n) − W) / 24    W = 钉住窗口（22 帧）
```

`C_n` 是**整数帧** → `t_a_start(n)` 与参考视频的 `skip_first_frames = C_n`
**严格对应**，不存在浮点累计误差（10 段接续后 `source_start × 24` 仍精确等于 `C_n`，
见 `test_integer_frame_grid_has_no_float_drift`）。

`C_n` 的来源：上游任务自己记录里的 `chain_total_frames`
（`continuation_service.continuation_state()` 的 `total_frames`）。

### 2.2 两条链路必须分开（本次实现的核心）

| 用途 | 音频内容 | 长度 | 落地方式 |
|---|---|---|---|
| **采样用**（进 DiT 的 `ref_audios` 槽位） | `1s 空白 ⊕ 原始音频切片` | `1.0 + D_deliver` 秒 | 每段一个独立文件（`data/uploads/segment_audio/seg-<hash>.m4a`），ffmpeg `adelay` 前插空白 |
| **成片用**（合并时贴的音轨） | **原始参考音频整条** | `A_total` 秒 | 合并阶段 `-i 原始音频 -map 0:v -map 1:a -af apad -shortest` |

> 若成片也用切片，每段开头那 1s 空白会**累积**（3 段 = 3s 空白）→ 音画错位。
> 这条已被线上实测证实与证伪（§6.3）。

### 2.3 参考视频的音画同步切割

```
视频侧：VHS_LoadVideo.skip_first_frames = C_n      （帧级）
        VHS_LoadVideo.frame_load_cap   = D_deliver × 24
        VHS_LoadVideo.force_rate       = 24         （接续段强制归一）
音频侧：VHS_LoadAudioUpload.start_time = C_n / 24  （秒级）
        VHS_LoadAudioUpload.duration   = D_deliver
```

视频已用 `force_rate=24` 归一 → 「跳 N 帧」与「从 N/24 秒起」指向同一时刻。

### 2.4 音轨来源以链首段为准

nonebot 的做法是「整部长视频共用第 1 段的 `audio_decision`」
（`h3_chain_video.py:1677-1681`）。本实现沿用：接续段从上游**继承**
音轨状态，而不是看本段前端传了什么。

## 5. 实测抓到的两个真实缺陷（已修）

### 5.1 缺陷 1：段2 的音频起点被算成 0

- **现象**：第一次线上跑，段2 的 `audio_segment_start = 0.0`
  （正确值是 56/24 = 2.333333s）—— 也就是「第 2 段又从参考音频的第 0 秒开始听」，
  前一段已用过的音频被**重复用了一遍**。
- **根因**：`_inherit_audio_continuation()` 里按「上游有没有上游」分支取 C_n：
  ```python
  if str(upstream_info.get("source_job") or "").strip():
      consumed = int(chain_total or 0)
  else:
      consumed = 0
  ```
  而「上游是**链首段**」时，`upstream_info["source_job"]` 恰好是**空串**
  （链首段没有上游）→ 走进 `else` 分支 → `consumed = 0`。
- **修法**：C_n 的定义只跟「上游链上累计了多少帧」有关，与上游自己是不是链首段无关
  —— 恒取 `chain_total`。
- **回归**：`test_second_segment_audio_offset_is_not_zero`（变异验证：还原分支 → `0.0 != 2.333333`）。

### 5.2 缺陷 2：ffmpeg 的 `-t` 放在输出侧 → 1s 前导空白被裁掉

- **现象**：切出来的段音频只有 **1.416009s**（正确应为 1s 空白 + 1.416667s 切片 = 2.416667s）——
  1s 空白**消失了**。
- **根因**：`ffmpeg -ss S -i IN -t D`（`-t` 在输出侧）会先解码整条再截断，
  而 `adelay` 加的空白在解码之后 → `-t D` 把「空白 + 切片」整体截成 D 秒。
- **实测对照**（149.88s 的 flac，切 2.333333s 起、1.416667s 长）：
  | `-t` 位置 | 结果 |
  |---|---|
  | 输出侧 | **1.416009s**（空白没了） |
  | 输入侧 | **2.416009s**（空白 + 切片，正确） |
- **修法**：`-ss` 与 `-t` 都放**输入侧**（ffmpeg 只解码需要的那一段，既快又不会裁掉空白）。
- **回归**：`test_segment_audio_keeps_lead_blank`（变异验证：`-t` 移回输出侧 → `3.0 != 4.0`）。

### 5.3 缺陷 3（前端）：接续回填的素材被自己清掉

- **现象**：前端实测 `state.assetRefs` 回填后为空。
- **根因**：`applyAssetRefs()` 回填完调 `window.renderMode()` 让槽位显示出来，
  而 `renderMode()` 内部会调 `resetSlotsForMode(mode, false)` ——
  那会把 `state.assetRefs` **整块清空**（槽位状态本来就是「切模式要清」的）。
- **修法**：新增 `renderModeKeepSlotsRender()`（「保留槽位状态」重渲染），
  接续回填走这一条。
- **回归**：`test_continue_backfills_asset_slots`（真实浏览器）。

### 6.4 接缝量化（接缝 vs 段内帧间差）

判据：把「段1 末帧 vs 段2 首帧」的灰度 MAE 与「段内相邻帧 MAE 的均值」相比。
比值 ≈ 1.0 表示接缝与普通运动同量级（**无整体位移**）；
比值远大于 1 就是「位移型接缝」。

| 链 | 段1 帧数 | 段2 帧数 | 接缝 MAE | 段内平均帧间差 MAE | **比值** |
|---|---|---|---|---|---|
| r2v（`000395` → `000396`） | 56 | 34 | 5.637 | 3.686 | **1.53x** |
| flf（`000398` → `000399`） | 56 | 34 | 3.024 | 2.505 | **1.21x** |

两条链的接缝都在「段内运动同量级」附近（1.2–1.5x），**没有出现位移型接缝**
（位移型的特征是比值远大于 1 —— 拷贝桥的网格对齐若失效，
尾段切片的帧跨度会与写入位置错位，接缝 MAE 会出现数量级的偏离）。
这与「拷贝桥 `mask_mode="hard"` 逐 token 拷贝 + 22 帧窗口落在 5+17k 网格」
的机制预期一致。

> ⚠ 这条量化只证明「**没有位移型接缝**」，**不**证明画质完美 ——
> 钉住区被裁掉后接缝处的清晰度渐变（研究报告 §4.3.1 提到的
> 「清晰度台阶」）仍可能存在，那需要人眼目检，本次未做。

## B.3 根因假设逐条证伪/坐实

用户要求的 5 类假设，**逐条**用帧级证据判定：

### a) 段间 latent 首帧不一致 / 未用零重编码桥接 → **证伪**

直接读线上落盘潜空间（safetensors header + 数据段），对比
**段2 的钉住区（前 7 个 latent 步）** 与 **段1 的尾 7 步**：

| 链 | 钉住区 max 差 | 逐通道 mean 最大差 | 判定 |
|---|---|---|---|
| 非二采 r2v | 4.768e-07 | 3.725e-08 | ✅ 逐位保住 |
| 二采 r2v | 4.768e-07 | 2.235e-08 | ✅ 逐位保住 |
| 二采 t2v | 4.768e-07 | 5.960e-08 | ✅ 逐位保住 |

差值是 **float32 舍入量级（1e-7）**，相对段内相邻步差（mean 0.2945、
max 6.5152）可以忽略 → **零重编码桥接完全生效，钉住区逐位保住**。

### b) 段边界帧被重复采样或双写 → **证伪**

`ffprobe` 的容器权威帧数：

```
段1 nb_frames=124 + 段2 nb_frames=102 = 226
成片 nb_frames=226   ✅ 帧数守恒
```

> **过程中的一次自我修正**：最初用 `ffmpeg -f rawvideo` 逐帧解码数出 227 帧，
> 一度判为「多一帧」。复核发现那是**解码器因 `start_time=0.041016 ≠ 0`
> 多吐的一帧**（容器 `nb_frames` 仍是 226）。**帧数守恒，假设 b 不成立。**
> 这个坑也写进了 `tests/test_cont_concat_frames.py` 的夹具注释。

### c) shift / scheduler / steps 不一致导致段间噪声水平跳变 → **证伪**

段1 与段2 的实际下发工作流逐项对比：

| 节点 | 段1 | 段2 | 一致？ |
|---|---|---|---|
| `139 MiniMaxH3SigmaShift` | shift_video=12.0, shift_audio=3.0 | 同 | ✅ |
| `9 BasicScheduler` | beta, steps=4, denoise=1.0 | 同 | ✅ |
| `17 KSamplerSelect` | euler | euler | ✅ |
| `171 transition_step` | 3 | 3 | ✅ |

**且 steps 不是根因**（实测对照）：

| 配置 | 接续点 RGB 跳变 | 段内量级 | 比值 |
|---|---|---|---|

| 二采 ON，steps=7 / transition=5 | 44.51 | 0.76 | **58.64x**（更差） |

### e) 拼接时音视频帧对齐 / 时间戳问题 → **坐实（但非主因）**

成片的 `start_time=0.041016`（不是 0），且首帧 PTS 序列是
`0.041016, 0.082682, 0.124349, ...`（从 0.041016 起铺，间隔 1/24）。
原因：`fps=24` 滤镜按**输出时间轴**重采样，concat demuxer 拼起来的
各段时间戳撞车后，滤镜从第一个输出时刻开始铺帧。
→ 已修：滤镜链加 `setpts=N/FRAME_RATE/TB`（按**帧序号**重排时间戳），
实测成片首帧 PTS 回到 **0.000000**、接续点帧号从 125 回到 **124**。

### ✅ **坐实的根因：二采（SelfLift）的色档阶跃**

**唯一变量对照**（同模型、同参数、同分辨率、同提示词、同种子，只切二采开关）：

| 组 | 段1 末帧 RGB | 段2 首帧 RGB | RGB 跳变 | 段内量级 | 比值 |
|---|---|---|---|---|---|
| **二采 ON** | [95.55, 95.56, 33.18] | [84.75, 93.82, 26.33] | **19.39** | 0.66 | **29.52x** |
| **二采 OFF** | [102.54, 94.14, 45.10] | [101.19, 92.31, 43.51] | 4.76 | 0.87 | **5.48x** |

**机理（源码级）**：
`comfyui-SelfLift/nodes.py:299-306`

```python
if video:
    low_video = torch.nn.functional.interpolate(
        source_video.float(), size=(t, h, w), mode="trilinear", ...)
```

→ SelfLift 的**低分辨率段把钉住区内容降采样**后当锚点
（`low_anchor = low_video`，nodes.py:321），
抬升再回高分辨率时，新生成区继承了**低分辨率段的色档**
→ 缝头几帧是「低色档过渡区」（实测段2 前 20 帧 RGB ≈ [85-97, 87-102, 24-28]，
而段2[30] 起就回到 [117.93, 106.29, 38.80]）。

**为什么非二采路径没有这个问题**：标准采样路径没有「降采样→抬升」这一往返，
钉住区与新生成区在**同一分辨率**上生成 → 色档天然连续。

## B.4 修复

### 缺陷 1（拼接时间轴）

`server.py` `_concat_chain_video()` 的滤镜链：

```
改动前： scale=…,pad=…,setsar=1,fps=24,format=yuv420p
改动后： scale=…,pad=…,setsar=1,setpts=N/FRAME_RATE/TB,fps=24,format=yuv420p
```

`setpts=N/FRAME_RATE/TB` 按**帧序号**重排时间戳（而不是按原 PTS 插值），
让 `fps=24` 铺出的帧与输入帧一一对应。

> 为什么不直接照抄 nonebot 的 `-c:v copy`：nonebot 的 copy 路径要求
> 各段编码参数**完全一致**（`h3_chain_video.py:_segments_look_compatible`），
> 我们仍需 scale/pad 统一尺寸 + 可能替换音轨 → 保留重编码，只把时间轴修对。

### 缺陷 2（二采色档阶跃）

在「裁重叠」之后加一跳 **`H3RelayPost`**（画质域）：

```python
p["300:post"] = {
    "inputs": {
        "images": ["300:trim", 0],     # 裁后的画面
        "guide":  ["300:trim", 3],     # prev_tail = 钉住区末帧 = 上段末帧
        "match_prev": 0.5,             # 跨段统计匹配强度
        "match_prev_frames": 12,
        "match_prev_gain_max": 1.15,  # 护栏
        "match_prev_offset_max": 0.06,
        "match_prev_stats_frames": 1, # 与单帧 guide 同口径
        "cross_seg_ack": True,         # ← 关键：确认 guide 是真参照
        # 其余画质域项保持 0
    },
    "class_type": "H3RelayPost",
}
```

**为什么用这个节点**（依据节点自己的 tooltip，不是猜的）：
- 「目标：压『成片缝上的亮度阶跃』」
- 「**真正的用武之地是拷贝桥**（那里 prev_tail 才是真·上段末帧）」—— 我们的路径**就是**拷贝桥
- 「不打勾（默认）⇒ match_prev 与 lowfreq_pull **自动弃权**」→ `cross_seg_ack=True` 是必需的总闸
- 「stats_frames=1 = 与单帧 guide 同口径 ⇒ 首帧被拉向 guide 且**不会越过它**；
  0 = 旧口径 ⇒ 首帧被推过 guide、缝上凭空多出阶跃（真渲染实测 ×12.6）」
- **帧数守恒、不动音频、零采样开销**
