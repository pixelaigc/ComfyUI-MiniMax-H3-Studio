## 1. 缺陷根因（现场代码核实，非历史摘要）

用户报告：在「参考生图 / 首尾帧（flf）/ 参考生视频」这类带素材引用的模式里，
已从素材库引用图片、输入提示词、点「增强」，得到的增强提示词**完全没有基于素材**。

现场核实到的三层根因：

| 层 | 事实 | 后果 |
|---|---|---|
| 前端 | `web/enhance-menu.js` 的 `runBasic` / `runRefine` / `runDirector` 构造 `/api/enhance` 请求体时**从不带任何素材字段** | 模型在增强阶段拿不到素材 |
| 后端契约 | `server.py` 的 `api_enhance` 虽有 `images` 参数，但它是「**浏览器本地图片路径列表**」 | 服务端读不到浏览器本地路径 —— 这条参数实际是**死参数**，前端也从未用过 |
| 提示词构造 | `h3studio/enhancer.py` 的 `build_messages()` 没有任何素材上下文入口 | 即使服务端拿到图，也没有「图序语义」告诉模型每张图是什么角色 |

即：**前端不带 + 后端读不到 + 提示词不描述** —— 三处同时缺失，素材等于白引用。

---

## 2. 修法

### 2.1 新增 `h3studio/enhance_assets.py`（素材引用 → 服务端可读图片）

| 素材类型 | 处理方式 | 理由 |
|---|---|---|
| image | 原图直接给多模态模型 | 模型读的就是图片本身 |
| video | ffmpeg 抽帧（每段最多 4 帧，间隔 1s） | LLM 读不了视频；复用 `h3studio/media_probe.extract_frames`（与素材库分析同一套） |
| audio | **明确降级**：素材库分析文本 → 文字上下文；并如实标注「模型无法直接听取音频」 | 本地多模态 LLM 没有音频输入通道。假装模型听到了音频是撒谎 |

硬约束：
- 只接受**素材库里的 asset_id**（不接裸路径），避免任意文件读取；
- 素材不存在 / 已删 / 文件丢失 → **抛 `EnhanceAssetError` 如实报错**，不静默跳过；
- 图片总数硬顶 8 张（多模态请求体是 base64 内联，无上限会撑爆请求体与视觉 token）；
- 解析走 `asyncio.to_thread`（读 SQLite + ffmpeg 子进程都是阻塞操作，直接跑在事件循环上会卡住整个 Studio）。

### 2.2 `server.py` — `api_enhance`

- 新增 `asset_refs` 入参：`[{"asset_id", "slot", "ordinal"}, ...]`；
- 解析出图片后**追加**到 `images`，连同 `describe()` 生成的图序语义
  （`<image1> = 首帧「xxx」`）一起进 `build_messages()`；
- 素材解析抽成独立协程 `_resolve_enhance_assets()`（端点体变短，也标明了「为什么丢线程」）；
- **显式指定了非多模态 Provider 时提前报错**（`code: provider_not_multimodal`）——
  不再等 llm 层抛「无法读图」，更不静默丢素材；
- 响应新增 `assets` 字段（素材回显）→ 前端可显示「这次带了几张素材图」。

### 2.3 `h3studio/enhancer.py` — `build_messages()`

新增可选参数 `asset_context`（默认 `""`）：

- **只有非空素材上下文才注入** → 无素材面板（文生图 / 文生视频）的提示词与改动前**逐字一致**；
- 素材上下文排在原文**前面**（与已有的跨段历史处理一致）：模型先把「图里是什么」读完，
  再读原文，最后输出。

### 2.4 `web/enhance-menu.js` — 前端

- 新增 `collectPanelAssetRefs()`：收集**当前面板**已引用的素材；
  - `state.assetRefs`（视频面板的首帧/尾帧/参考图/参考视频/参考音乐槽位）；
  - `window.QwenRefs`（图片编辑模式的参考图，自成模块，不在 `state.assetRefs` 里）；
  - **按当前模式过滤槽位**（复用 `app.js` 的 `MODE_ALLOWED_SLOT_KEYS` 唯一真源）——
    不提交「界面上看不见却带上去」的幽灵引用；
  - 槽位→语义映射与出图链路**同一套**（`first→first_frame` / `last→last_frame` /
    `ref\d+→ref_image` / `refvid\d+→ref_video` / `refaud\d+→ref_audio`）。
- 三条走 `/api/enhance` 的路径全部带上 `asset_refs`：
  **普通增强 / 二次增强 / 视频导演提示词**。
- 无素材 → 空数组 → 服务端走「无素材」既有路径。

### 2.5 `web/providers.js` — 可见回显

`buildEnhanceMeta()` 增加「素材上下文」行：带了几张图、音频是否以文字提供、
哪些素材**未参与**及原因。让用户能确认素材到底参没参与 ——
这正是本次缺陷的核心（素材被静默丢弃，用户毫无察觉）。

### 2.6 `web/index.html`

`enhance-menu.js` / `providers.js` 的 `?v=` 升到 `enhassets1`（否则老用户拿不到修复）。

## 6. 遗留问题 / 已知边界

1. **音频以文字形式参与增强**，不是真的「模型听到了音频」。
   本地多模态 LLM（llama.cpp / vLLM）没有音频输入通道。若 Provider 支持
   OpenAI `audio_url` content 类型，将来可再接一条真音频通道。当前行为是
   **明确标注的降级**，不是静默忽略。

2. **视频素材按抽帧参与**（每段最多 4 帧、间隔 1s），不是完整时序理解。
   与素材库「深度分析」是同一套抽帧口径。

3. **图片上限 8 张**（`enhance_assets.MAX_IMAGES`）。超出部分进 `skipped`
   并在界面回显「未参与：xxx（超过单次增强的图片上限）」，不会静默丢。

4. **并发闸门用例改过**：原来取「`api_enhance` 往后 6000 个字符」这个任意长度
   窗口，端点体一变长就会**假失败**。已改为按**函数边界**切 —— 窗口长度与
   被测行为无关。已变异自证仍能抓住真缺陷。

5. **4 条 console 0 报错用例**在「6 个测试文件同时跑 + 机器 load average 20」
   的高压下会偶发失败（`[视频面板] 载入清单失败: Failed to fetch` —— 是
   `/api/video-options` 的 fetch 在高负载下超时；该接口本机实测要 6.5s）。

   **归因已用对照实验钉死**：把**基线 b2c382d（不含本次改动）** checkout 到
   一个独立 worktree，用**完全相同**的 6 文件批次跑一遍：

   | | 结果 |
   |---|---|
   | 本次改动（b39924f） | 4 failed, 155 passed —— 挂的是这 4 条，报错文本相同 |
   | **基线 b2c382d** | **4 failed, 134 passed —— 挂的是完全相同的 4 条，报错文本相同** |

   单独跑这 4 条（不带其它文件抢资源）：**4 passed in 34.10s**。

   -> 判定为**环境负载导致的既有 flake，与本次改动无关**。
   本次改动**没有触碰** `web/video-panel.js` / `h3studio/video_models.py`
   （`git diff b2c382d..HEAD -- web/video-panel.js h3studio/video_models.py` 为空）。

6. **未覆盖的模式**：`t2i` / `t2v` / `t2i_moss` / `t2i_qwen` 本来就没有素材槽位，
   `asset_refs` 恒为空数组 → 服务端行为与改动前逐字一致（有用例锁住）。
   `i2i_qwen` / `i2i_h3image`（图片编辑）的参考图走 `window.QwenRefs`，
   已覆盖收集逻辑（静态用例），但**未做线上浏览器实测**——
   因为那两条走 `/api/qwen-pe/expand`（官方 PE checkpoint），不是本次改的
   `/api/enhance` 链路，其素材处理是**既有能力**（`_upload_ref_images`）。
