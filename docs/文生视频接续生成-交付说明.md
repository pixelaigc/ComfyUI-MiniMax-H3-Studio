## 0. 一句话

文生视频（minimax H3）现在支持「接续生成」：上一段的**潜空间**落盘，
下一段读回来零重编码地接上，媒体库里得到**完整视频**（上一段 + 本段），
并且可以对完整视频**再次接续**，实现无限接续。

同时修掉了 D1 调研报告列出的全部五项缺陷 —— 其中两项是本轮复核时
**新发现**的（同属「落盘坐标 / 静默错误内容」类别）。

---

## 1. 它是什么（技术口径）

接续 = 把上一段生成的 **AV latent（潜空间）**落盘，下一段生成时读回来，
把它的尾部**逐 token 拷贝**进本段初始 latent 的开头，并用 ComfyUI 原生的
`minimax_keyframes` 协议把同一段内容钉成条件行 —— 模型读到的是**真实的
上一段运动**，不是「猜」出来的相似画面。

**不是像素续接**（上一段 mp4 → 解码 → VAE 重编码 → 当锚图）。重编码会在
每一段接缝处掉一次画质、偏一次色档；潜空间桥不碰像素。

底层用的是本机已装的 **ComfyUI-H3-Relay-Kit** 的零重编码 latent 桥
（`H3RelayLatentSave` / `H3RelayLatentLoad` / `H3RelayCopyBridge` /
`H3RelayTrimAV`）—— 我们**没有重新实现**这些节点。

### 工作流接线

```
MiniMaxH3ImageToVideo ──┬─→ H3RelayCopyBridge ─┬─[0]→ SamplerCustomAdvanced.latent_image
  (latent)              │   (300:bridge)        ├─[2]→ trim_frames
                        │                       ├─[3]→ BasicGuider.conditioning
                        └─[0]← H3RelayLatentLoad ──[0] (上游潜空间, explicit_path)
                                  ↑
SamplerCustomAdvanced ─[0]→ H3RelayLatentSave (落盘下一段接力棒)
                  ↑
VAEDecode ─[0]→ H3RelayTrimAV ─[0]→ CreateVideo.images
VAEDecodeAudio ─[0]→ H3RelayTrimAV ─[1]→ CreateVideo.audio
```

要点：
* 拷贝桥接在 **latent 与采样器之间**（不是采样器之后）；
* `conditioning` 走拷贝桥第 4 路（钉帧后的条件，管取景/构图）；
* 裁重叠在 **decode 之后**，且**音画同裁**（否则画面裁了音频没裁 → A/V 不同步）；
* `mask_mode="hard"`（钉住区零重绘）。

### 3.1 已在前序提交修掉的三项

| D1 项 | 根因 | 修法 | 位置 |

### 3.2 本轮复核**新发现**的两项（本轮修）

#### 缺口 A：重试/重跑沿用源任务的落盘目录 → **覆盖原任务的潜空间**

**这是 D1 落盘坐标缺陷的同一类** —— 落盘坐标必须与「产出它的那一段」
一一对应，不能由「参数里恰好带了什么」决定。

**根因**：`create_job_record` 里写落盘目录用的是 `setdefault`：

```python
info.setdefault("latent_run_id", cont.segment_run_id(job_id))   # 旧
```

`setdefault` 只在**字段缺失**时才写。而 Agent 的 `retry_job` 工具会把源
任务的 params **整份拷贝**过来 —— 新任务就沿用**源任务**的目录名 →
写同一个 `stage_00000.safetensors` → **原任务的潜空间被覆盖**。

**实测复现**（`tests/test_continuation_retry.py`）：

```
A 的 latent_run_id = h3studio_sA
重试出来的新任务 latent_run_id = h3studio_sA    ← 与 A 相同（碰撞）
应为                = h3studio_s2dfd0d9d662f
```

**修法**：强制由**本段自己的任务 id** 派生，不再 `setdefault`。

```python
info["latent_run_id"] = cont.segment_run_id(job_id)   # 新
info["latent_stage"] = 0
```

#### 缺口 B：没有内容指纹 → ComfyUI 节点缓存拿回旧 latent

**根因**（ComfyUI 源码级确认）：ComfyUI 的节点缓存 key = 节点**输入**的
哈希（`comfy_execution/caching.py` 的 `get_immediate_node_signature`），
对每个 input 取「链路 or 字面值」—— **文件路径只是普通字符串**，
缓存**不看输入指向的文件内容变没变**。

于是「上一段潜空间被重跑替换」之后，新一段的 `H3RelayLatentLoad`
（`run_id` / `stage_index` / `explicit_path` 三项一字未变）→ **命中缓存**
→ 节点**压根不被调用**（日志里连「已读 stage N」那一行都没有）→
返回**老 latent** → 新一段实际接的是**上一版**的画面，
**且不报错、界面全程显示成功**。

> nonebot 咏唱 h3 在 `h3_chain_video.py::_latent_fingerprint` 踩过同一个坑
> （9/30 报告：重跑段 1 后跑段 2，段 2 开头出现**老段 1**的场景），
> 解法就是**内容指纹**。

**修法（借鉴 nonebot 的内容指纹机制）**：把内容指纹编进**读回用的文件路径**。

```
落盘（Relay-Kit 节点自己算路径，改不了）:
  relay_kit/h3studio_s<job_id>/stage_00000.safetensors

读回（我们算路径）:
  relay_kit/h3studio_s<job_id>/stage_00000_<8位md5指纹>.safetensors
```

内容变 → 指纹变 → 路径变 → `explicit_path` 这个**节点输入**必然变 →
缓存 key 必然变 → 节点必然重跑。

* 指纹口径与 nonebot 同一套：文件**大小**进指纹 + 头 8MB + 尾 8MB
  （不必整份读完 —— 一份约 4.8MB，读全量也没问题但口径对齐更好）；
* 副本用**硬链接**（零拷贝，同文件系统）；跨设备/失败退回复制；
* **本段重跑后**自动清掉同坐标的旧指纹副本（防死副本堆积）。

**真实链路验证**（`tests/verify_fingerprint_cache_break.py`，真实 ComfyUI 生成）：

```
read_path_1 = .../h3studio_s07e4f3e1fae9/stage_00000_988d3126.safetensors
（把 A 的潜空间换成另一份合法 safetensors，模拟「A 被重跑替换」）
read_path_2 = .../h3studio_s07e4f3e1fae9/stage_00000_41aa057b.safetensors
path_changed_after_content_change = True

接续段 C 真实生成：
  ComfyUI 日志：[H3 Relay] 已读 stage 0 ← .../stage_00000_41aa057b.safetensors
  relay_load_node_actually_ran = True      ← Load 节点真跑了（没命中缓存）
  seg_frames = 102 / full_frames = 226
```

**独立佐证**（前一轮真实接续的 ComfyUI 日志）：

```
[2026-11-13 11:20:34] [H3 Relay] 已读 stage 0 ← .../h3studio_s10b2aa1590ca/stage_00000_06514d21.safetensors
[2026-11-13 11:22:48] [H3 Relay] 已读 stage 0 ← .../h3studio_sd93c6dc42964/stage_00000_5ae7eafb.safetensors
```

日志里读的是**带指纹的路径** —— 机制在真实运行中确实生效。

### 3.3 D1 报告的「方案 A / 方案 C」

报告建议「方案 A（落盘 run_id 按 job_id 派生 uuid4().hex[:12] +
显式传 ref_anchor_latent）」与「方案 C（落盘前检查目标 stage 占用）」
择一或并用。

**本实现取方案 A，并额外做了 C 的等价保障**：

* 方案 A 的落地形式：`segment_run_id(job_id)` = `h3studio_s<job_id>`。
  本项目的 `job_id` 本身就是 `uuid.uuid4().hex[:12]`（12 位十六进制），
  所以「按 job_id 派生 uuid4」与「按 job_id 派生目录名」在本项目里
  **是同一件事** —— 不需要再额外套一层 uuid。
* 方案 C 的等价保障：落盘坐标**结构上**每段唯一（目录名由段任务 id
  派生），所以「目标 stage 被占用」这件事**不可能发生** —— 比「检查
  后拒绝」更强：它不是运行时检查，而是类型层面的不变量。

> 为什么不额外套 uuid4：job_id 已经是 `uuid4().hex[:12]`，再套一层
> 只是多一次随机，没有增加任何不变量强度，反而让「目录 ↔ 任务」的
> 对应关系变间接（不利于排查）。**可追溯性 > 随机性**。

## 8. 已知限制

1. **只支持文生视频（t2v）**。首尾帧生成（flf）/ 参考生视频（r2v）走
   `workflows.py` 里的旧工作流路径，那两条路**还没接桥**。
   硬说它们可接续会导致「点了之后静默退化成普通生成」—— 那是最坏的
   失败，所以现在明确不支持。补上桥后把 `continuation.CONTINUABLE_MODES`
   加进去即可（前端无需改）。

2. **二采（selflift）产物不可接续**。二采走 `SelfLiftH3Sampler`：
   低分辨率一采 → 抬升 → 高分辨率二采，节点内部做了 `seed+1` 重新加噪，
   潜空间相位与标准采样路径**不同源**。按钮不出现 + 服务端明确拒绝。

3. **接续窗口固定 22 帧**（≈0.92s 钉住）。没做成可调 —— 窗口越大，
   钉住区越长、可生成的新内容越少。

4. **接续要求本段与上一段分辨率完全一致**。三道闸拦下不一致：
   点「复用参数」清接续上下文 / 提交前比对面板尺寸 / 服务端提交时校验。
   不一致时给出中文原因并**不建任务**（不占 GPU）。
   ⚠ 「接续后改分辨率」这条路走不通 —— 要改分辨率就用「复用参数」独立生成。

5. **完整视频用 ffmpeg concat 重新编码**（CRF 18）。分段视频各自音画同裁，
   拼接不会累积 A/V 偏移；但完整视频经过一次重编码，画质比分段略低。

6. **潜空间文件不自动清理**。每个 5s 段约 4.8 MB（+ 一份硬链接副本，
   硬链接不额外占盘）；链越长占用越大。删除任务时**不会**自动删潜空间
   （避免误删还在用的链）。分叉后每一段都是独立目录，占用按**分支数**增长。

7. **外观锚缺失时静默降级为「无锚」**（不报错）。锚是防长程漂移的加分项，
   不是接续正确性的必要条件。

8. **只接续上一段**，不做「多段历史锚」。

9. **测试实例与线上共用同一个 ComfyUI**（8188）。真实生成会占用 GPU
   （本次验证期间 4090D 显存占用约 47GB/49GB）。

10. **内容指纹是 8 位 md5**（非安全哈希，只当缓存键用）。碰撞概率对本用途
    完全够用。
