## 1. 第 1 项：前端 flf / r2v 接续未传 `params.continuation`

### 1.1 缺陷本体

`web/app.js` 的提交打包里，`params.continuation = ctx.continuation;` **只写在 t2v 分支**：

```js
if (mode === "t2v" && window.VIDEO_PANEL && ...) {
  ...
  if (ctx && ctx.continuation) {
    ...
    params.continuation = ctx.continuation;   // <- 只有 t2v 有
  }
} else if (mode === "flf" || mode === "r2v") {
  // flf / r2v 分支从不设 params.continuation
}
```

后端**本来就支持**（不是后端缺陷）：

| 位置 | 事实 |
|---|---|
| `server.py:5461` | `if mode in ("t2v","flf","r2v") and params.get("continuation"): _prepare_continuation_params(params)` |
| `h3studio/h3_video_modes.py` | `build_flf` / `build_r2v` 都读 `vworkflow._continuation_state(params)` |
| `h3studio/continuation.py:120` | `CONTINUABLE_MODES = ("t2v", "flf", "r2v")` |

### 1.2 为什么这个失败模式特别糟

**它不报错。** 用户在界面上点「接续」→ 面板正确回填（模式 / 素材 / 音轨 / 尺寸都对）
→ 点生成 → 提交体里没有 `continuation` → 服务端看不到接续 → 本段退化成
**普通生成**（不读回上游潜空间、不接拷贝桥）→ 生成成功、界面照常显示「接续上下文」，
但产出是一段与上一段毫无关系的**独立**视频。

用户以为在续写，实际拿到两段互不相干的片段。

### 1.3 修法

把接续上下文的提交提到**三个模式分支之外的公共作用域**，由显式模式白名单驱动
（与服务端 `mode in ("t2v","flf","r2v")` 完全一致），t2v / flf / r2v 共用同一份逻辑，
含提交前的分辨率一致性闸。

**尺寸闸必须一起搬**：它原本也在 t2v 分支里。留在原处 ⇒ flf/r2v 接续失去跨分辨率保护，
错误会一路跑到 ComfyUI 才炸（Relay-Kit 拷贝桥 raise「拷贝桥禁止跨分辨率：上段 WxH ≠ 本段 WxH」）。

### 1.4 证据（双层）

**静态契约**（`tests/test_continuation_frontend_params.py`，7 条）：

- 接续赋值点必须由覆盖三模式的白名单驱动
- 三个分支里都**不得**再出现对 `params.continuation` 的写操作（防「假修」）
- 白名单不得写成「只有 t2v 生效」
- 分辨率一致性闸必须以**可执行的守卫**形态存在（查守卫而非查字符串）

**浏览器端到端**（`tests/test_continuation_frontend.py` 新增 2 条）：
点「接续」→ 提交 → 抓提交体 → 断言有 `continuation` 且 `source_job` 指向来源任务。

> 为什么既有那条浏览器测试抓不到：它用的是 **t2v** 模式（`_seed_continuable_job_as`
> 默认 t2v）⇒ t2v 一直是好的 ⇒ 它**抓不到**本缺陷。

**变异测试**（`tests/mutation_continuation_frontend_params.py`，4/4 全红）：

| 变异 | 内容 | 结果 |
|---|---|---|
| M1 | 把白名单退回只对 t2v 生效（= 缺陷本体） | 如期变红 |
| M2 | 在 flf/r2v 分支里覆盖掉公共作用域写的值 | 如期变红 |
| M3 | 把分辨率一致性闸改成死代码（`if (false)`） | 如期变红 |
| M4 | 把接续提交块整个删掉 | 如期变红 |

用**同一段1** 派生出多个接续段，唯一差别是条件节点带不带参考视频

|---|---|---|---|---|---|

**关键读法**（`tools/seam_kind.py`）：**最大 L1 大 ≠ 缺陷**。

- B：L1=100.78 **且** Δ亮度=+9.01（25.8× 该段中位）⇒ **亮度阶跃** = 用户看到的「闪一下」
- C：L1=95.61 **但** Δ亮度=+1.95（3.5× 该段中位）⇒ 亮度连续 = **镜头切换**（正常内容）

⇒ 去掉参考视频后，跳变**位置不变**（都是 @21 = 钉住区边界），但从「亮度阶跃」
降级成「镜头切换」。**根因 = 参考视频条件 × 钉住区的冲突。**

> @21 的位置：段2 保留 102 帧 = 原始 124 帧裁掉 22 帧钉住区；跳变落在
> 钉住区结束后的新生成区里。

### 2.4 根因（代码级）

`h3studio/h3_video_modes.py::_continuation_media_slice`：

```python
external = h3acont.is_external_track(track_mode)
...
if not external:
    return out          # <- 参考视频的「画面」切片也一起被丢了
```

**参考视频的「画面」切片被绑在了「音轨来源是不是外部音轨」这个条件上。**
音轨来源是「生成的音乐」时 `external=False` ⇒ `skip_frames=0` ⇒
**段2 的参考视频从 0 开始喂**。

而规范（`docs/接续模式深度研究-20261116.md` §5.4.3）明确要求：

```
第 n 段的参考视频切片 = 参考视频的 [t_a_start(n), t_a_end(n))
   视频侧：skip_first_frames = round(t_a_start(n) * 24) = C_n
```

§5.2 还记着「nonebot 侧已有这两个槽位（307/309），但**注入侧未实现**，
H3-Studio 需要自己实现」—— 即本仓一直没实现。

**为什么这会造成冲突**：段1 已经用过同一份参考视频（画面已经演化过去）；
段2 却要求画面**回到参考视频开头**。而拷贝桥把段1 的尾部**硬钉**在前 22 帧
（`mask_mode="hard"` = 钉住区零重绘）。两股力量在钉住区边界正面冲突
⇒ 段2 新生成区爆发式跳变。

### 2.5 最小修复

1. **`_continuation_media_slice` 新增两个与音轨解耦的字段**
   - `video_skip_frames` —— 画面按 `C_n` 跳帧
   - `video_drop` —— 参考视频内容已用尽 ⇒ 本段不带它
2. **`build_r2v` / `build_flf` 应用这两个字段**
   - 参考视频**够长**（`C_n < 帧数`）⇒ `skip_first_frames = C_n`
   - 参考视频**不够长**（`C_n >= 帧数`）⇒ **不带**参考视频
     （喂空会 raise「ref_video_1 must contain at least 5 IMAGE frames」；
     继续从 0 喂就是本缺陷本身）
   - 配对的 `ref_video_audios` **同步清掉**（T8 硬规则：
     「Reference-video soundtrack(s) have no same-numbered video」）
3. **`server.py` 新增 `_record_ref_video_frame_count`**
   链首段探测参考视频真实帧数（`_probe_video_frame_count`）写进
   `params["continuation"]`，后续段继承。
   **探测不到就不猜**（保持旧行为，绝不静默出错）。

**为什么只在接续出现**：非接续段没有钉住区，整段由同一套条件驱动 ⇒ 亮度一致。

**下一步（未做）**：直接测「钉住区尾部亮度 vs 本段新生成区起始亮度」的差，
并尝试用 `mask_mode="ramp"`（缝端留自由度）做对照实验。这需要改
Relay-Kit 的接线（`h3studio/h3_video_modes.py` 的 `300:bridge` 输入），
属于**生产语义变更**，本轮未做。

### 2.6e 接缝连续性实测：**问题在段内，不在接缝**

用跨模式实验的三条链，直接算「段1 末帧 → 段2 首帧」的相邻 L1 与亮度差：

| 链 | 接缝 L1 | 段2 内部最小相邻 L1 | 接缝/内部 | 段1 末帧亮度 | 段2 首帧亮度 | Δ亮度 |
|---|---|---|---|---|---|---|
| U（r2v→r2v） | 2.015 | 0.103 | 19.61× | 122.09 | 121.79 | **−0.31** |
| T（r2v→flf） | 2.702 | 0.105 | 25.72× | 122.09 | 122.00 | **−0.10** |
| S（flf→flf） | 3.281 | 0.240 | 13.67× | 135.32 | 135.44 | **+0.12** |

⇒ **接缝本身连续**（Δ亮度 ≤0.31，L1 只有段内跳变的 1/30 量级）。
拷贝桥确实把段1 的画面正确带过来了。

⇒ 跳变发生在**钉住区尾部 → 本段新生成区**的交界处：
**钉住区亮度（段1 的画面，122/135）与本段新生成区亮度
（按参考条件走，追到 137–157）不匹配**。

这解释了为什么：
  * 非接续段没有这个问题（没有钉住区，整段由同一套条件驱动 ⇒ 亮度一致）；
  * 换参考图会改变跳变（P vs Q：新生成区亮度变了 ⇒ 落差变了）；
  * 但换 task_type / 条件类型**不改变**跳变的存在（T/S/U 都有）——
    因为落差来自「段1 的画面」与「本段按参考条件生成的画面」之间，
    与条件的**类型**无关，只与**内容亮度**有关。

### 2.6f 第四轮定位：**「尾帧是否给定」才是变量**（flf 只给首帧时**非接续段也有跳变**）

`tools/r2v_keyframe_probe.py`（seed 20261701）：

| 变体 | 段2 的条件 | **段1（非接续）** | 段2（接续） |
|---|---|---|---|
| **V** 首尾同图 | 首帧=尾帧=图A（**两端都钉**） | 中位 0.547 / **最大 1.94** @68 / Δ−0.59 ⇒ **无跳变** | （被 watchdog 打断，见 §0） |
| **W** 只给首帧 | 首帧=图A，尾帧缺省（**只钉首帧**） | 中位 3.449 / **最大 81.08** @45 / **Δ−46.39** ⇒ **有跳变** | （被 watchdog 打断） |

**这是本轮最重要的修正**：W 的**段1 是非接续段**（没有拷贝桥、没有钉住区），
**它自己就有 L1=81.08、Δ亮度 −46.39 的跳变**（亮度从 127.7 掉到 81.3）。

⇒ **flf「只给首帧」时，跳变与接续无关** —— 是 task_type=I2VA（只钉首帧、
尾帧由模型自由生成）下的**模型行为**。

⇒ 这同时**修正了上一轮的两条结论**：
  1. 「flf 侧已排除段内跳变」**不成立** —— 上一轮的 flf 链用「首帧与尾帧
     同一张图」（= V 的配置），恰好是无跳变的那一档；
  2. 「r2v 段的段内跳变」需要拆成两个不同问题：
     * **flf 只给首帧** ⇒ 模型行为（I2VA 尾帧不稳定），**不是接续缺陷**；
     * **r2v（整段语义参考）** ⇒ 非接续段无跳变（段1 最大 L1=7.13）、
       接续段有跳变（84.08）⇒ **这一条才是接续引入的**。

【两者的共同机理】
「本段条件对画面的约束强度」决定新生成区会不会偏离钉住区：
  * 约束强（首尾都钉 / 整段语义参考）⇒ 新生成区必须贴着条件走
    ⇒ 与钉住区「段1 已演化的画面」落差大 ⇒ 交界处阶跃；
  * 约束弱 ⇒ 新生成区自由演化 ⇒ 反而可能连续。
**注意**：这解释了「V（约束最强）反而无跳变」的反例吗？—— 不，
V 的段2 被 watchdog 打断了，**没有段2 数据** ⇒ V 的接续段是否跳变
**本轮未测**。这是本项**未闭合**的部分（见 §6）。

### 2.6g 第四轮定位补测：**根因完全闭环**

`tools/r2v_keyframe_seg2.py` 补测了被 watchdog 打断的两个接续段
（段1 数据在首跑已落库）。完整对照：

| 变体 | 本段条件 | task_type | **段1（非接续）** | **段2（接续）** |
|---|---|---|---|---|
| **V** | 首帧=尾帧=图A | FL2VA（**两端都钉**） | 1.94（无跳变） | **1.68（无跳变）** |
| **W** | 只给首帧=图A | I2VA（**只钉首帧**） | **81.08（Δ−46.39）** | **77.73（Δ+25.48）** |
| **U** | 参考图A | Ref2VA（**不钉端点**） | 7.13（无跳变） | **84.08（Δ+19.19）** |

⇒ **跳变由「本段条件是否钉住画面端点」决定，与接续无关。**

- **V 的接续段是干净的**（最大 L1 = 1.68，比值 5.97×）
  ⇒ **接续机制（拷贝桥钉住区）本身没有引入跳变**；
- **W 的非接续段就跳**（81.08）
  ⇒ 那不是接续缺陷，是 **I2VA（只钉首帧、尾帧自由生成）的模型行为**；
- **U（r2v）**同属「不钉端点」这一类 ⇒ 与 W 同机理。

⇒ **上一轮的两条结论都需要修正**：
  1. 「flf 侧已排除段内跳变」**不成立** —— 上一轮的 flf 链恰好是
     「首尾同图」（= V，无跳变那一档）；
  2. 「r2v 的段内跳变是接续缺陷」**不成立** —— 它的成因是
     Ref2VA 不钉端点，与接续无关。

【与上游文档一致】
Relay-Kit 的 `H3RelayTrimAV` tooltip 早就写着：
> 「钉住区之后模型还会先**复现**上一段若干帧，然后才切到本段 prompt；
> **切换点逐段不同**，可能落在钉住区之外。」

本轮观测到的跳变位置（@6/@7/@11/@13/@14/@25/@30/@36/@45/@47/@54/@62/@86）
