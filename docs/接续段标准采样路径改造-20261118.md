## 一、根因：为什么「面板勾了二采」

### 1.1 前端默认值确实是 false

`web/video-panel.js:100-118`：

```js
twopass: {
  enabled: false,
  transition_step: 3,
  lowres_scale: 0.5,
  ...
```

### 1.2 但服务端持久化把它恢复了

`web/video-panel.js:1871-1876`（页面加载时）：

```js
const cfgResp = await fetch("/api/video-config", { cache: "no-store" });
if (cfgResp.ok) {
  const saved = await cfgResp.json();
  applyConfig(saved);          // ← 这里把 twopass.enabled=true 恢复回来
```

`/api/video-config`（`server.py:7570`）把面板配置存在 `model_provider_prefs` 表的
`video_panel_config` 键里，**局域网共用**。

**线上实测（2026-11-18 复核）**：

```
GET http://127.0.0.1:8190/api/video-config
  mode_configs.t2v.twopass.enabled = true   transition_step=4  lowres_scale=0.7
  mode_configs.flf.twopass.enabled = true   transition_step=6  lowres_scale=0.75
  mode_configs.r2v.twopass.enabled = true   transition_step=6  lowres_scale=0.7
```

这三组值**不是**任何一方的默认值（前端默认 ts=3/lrs=0.5；
服务端 `VIDEO_TWOPASS` 默认 ts=3/lrs=0.5）⇒ 只能是**用户历史上勾过**。

### 1.3 当日全部视频作业都被开了二采

```
11:13 r2v  tp.enabled=True ts=4 lrs=0.7   stage=0
11:23 t2v  tp.enabled=True ts=4 lrs=0.7   stage=0
11:44 t2v  tp.enabled=True ts=4 lrs=0.7   stage=1   ← 用户报的那条
...
11:55 r2v  tp.enabled=True ts=4 lrs=0.7   stage=0
```

**全部**视频作业的 `twopass.enabled=true` —— 与「持久化恢复」完全吻合。

### 1.4 结论

> **「二采默认开」不是前端 bug，是「服务端持久化的用户偏好」被当成了默认值。**
> 所以修复**必须落在服务端归一化层**：任何未显式开二采的入参，
> 落到工作流里都必须是标准采样节点。

**生产代码实际行为改动只有 3 处**：
① 新增策略模块；② `server.py` 归一层；③ 两个工作流构建函数里的 `use_twopass` 判定。

### 2.2 策略的三态

`h3studio/twopass_policy.py`：

```python
CONTINUATION_TWOPASS_POLICY = "deny"   # 接续段：默认禁用二采
PLAIN_TWOPASS_POLICY       = "allow"   # 普通段 / 首段：用户勾了就允许
```

`resolve_effective_twopass(params) -> (use_twopass, disposition)`：

| disposition | 含义 |
|---|---|
| `allow` | 走标准采样；是否走二采取决于入参（首段/普通段） |
| `deny` | **强制**走标准采样（二采被关掉），留中文留痕 |
| `warn` | 走二采，但**必须**留警告留痕（显式放行时） |

**判据**：`params["continuation"]["source_job"]` 非空 = 续接段。
这与 `h3studio/continuation.py` 的 `_continuation_state()` 的 `has_source`
判据**完全一致** —— 两处同口径，不允许分裂。

### 2.3 为什么两层都要有（归一层 + 工作流层）

- **归一层**（`server.normalize_t2v_params`）是**策略**：把入参改写成「不启用二采」，
  并留痕。用户在任务详情里能看到「面板勾了二采但没生效」的中文说明。
- **工作流层**（`build_t2v_panel` / `build_flf` / `build_r2v`）是**不变量**：
  无论谁调用、无论是否绕过归一层，接续段产出的**必须**是标准采样节点。

两层调**同一个函数** `resolve_effective_twopass()` —— 否则会出现
「归一层放行、工作流层禁用」或反过来的分裂。

### 2.4 显式放行口子

```json
{"continuation": {"source_job": "...", "allow_twopass": true}}
```

必须是**严格的 `True`**（字符串 `"true"`、`1` 都不算）⇒ 杜绝「悄悄开着」。

### 2.5 为什么接续段默认禁用二采（取舍）

**数据**（`full_census.py` 重跑，13 条链；原始脚本有 numpy float32 序列化 bug
导致归档的 `census.json` 被截断，本轮已修，见 §2.6）：

| 组 | 条数 | 段2 头断点比（中位/最大） | 3 帧亮度降（中位/最大） |
|---|---|---|---|
| 二采 **ON** | 2 | **3.56x / 4.54x** | **+5.947 / +7.212** |
| 二采 **OFF** | 11 | **0.93x / 1.58x** | **−0.110 / +0.260** |

**无重叠、无反例**。突变精确落在**段 2 内部 frame0→1**，不在拼接帧。

**取舍**：接续段默认禁用二采 = 用户在高分辨率档位失去二采的提速收益。
但这是**每条二采接续链都会发生**的可见缺陷（肉眼「第 5 秒那一下」），
所以默认路径必须是无缺陷的那条。首段**不禁用**（没有上游、没有钉住区，
降采样-抬升路径不涉及跨段色档对齐）—— 实测首段走二采没有段头掉档。

### 2.6 顺带修掉的取证脚本 bug（不属主任务，但影响证据可信度）

`full_census.py` 的 `json.dump` 直接 dump numpy float32 ⇒ `TypeError` ⇒
归档的 `census.json` **被截断**（上一轮 `census.json` 只有 1.5KB 且 JSON 解析失败）。
本轮修好后重跑，数据完整（13 条链）。

### 2.7 标准采样可行性的依据（外层已核实，本轮采信并实测验证）

ComfyUI 的标准 `SamplerCustomAdvanced` **会**读 latent 里的 `noise_mask`
并作为 `denoise_mask` 传给采样器
（`comfy/comfy_extras/nodes_custom_sampler.py:1047-1055`：

```python
if "noise_mask" in latent:
    noise_mask = latent["noise_mask"]
...
guider.sample(..., denoise_mask=noise_mask, ...)
```

⇒ 拷贝桥的钉住区（noise_mask）在标准采样路径上**照常生效**，
不存在「换回标准采样就失去钉帧」的问题。**线上实测验证**：接续段走标准采样后，
成片拼接点 L1 = 1.5982（flf）/ 2.8305（r2v），与二采 OFF 历史链同档
（对照 3.0379），钉帧仍在起作用。

⇒ **断点比**：两条链都达标（1.27x / 0.82x），与二采 OFF 组同档。
⇒ **亮度降**：r2v 达标（−0.085）；**flf 是 +0.717，超标**。

### 4.5 flf 的 +0.717 亮度降：是真实超标还是口径问题？

**如实分析**（不粉饰）：

- flf 段2 的**头断点比只有 1.27x**，段内中位 L1 = 0.4737，
  头断点 L1 = 0.6026 ⇒ **绝对幅度也很小**（0.60 vs 中位 0.47）。
- 亮度降 +0.717 是「头帧亮度 − 第 3 帧亮度」，**绝对值只有 0.72 灰阶**
  （头帧 126.60 → 第 3 帧 125.88）—— 肉眼几乎不可见。
- 对照组二采 OFF 的历史链是 **+0.168**，二采 ON 是 **+7.212**。
  +0.717 落在两者之间，但**离 +7.212 差一个数量级**。

**结论**：flf 的 +0.717 **不构成「段头色调突变」**：
突变是「亮度掉 7 格 + 饱和度掉档 + 硬切」（二采 ON 组特征）；
flf 这里是「0.72 灰阶的缓慢漂移 + 0.13 的 L1 增量」。
**但它确实超过了任务给的 ≤+0.3 门槛，本轮如实记录为「未完全达标」**，
不把它说成达标。原因是**单样本**（一条链）—— 需要更多样本才能判断
+0.717 是这个素材的特性还是普遍现象。
