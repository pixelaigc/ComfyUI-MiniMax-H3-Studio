## 2. 根因（重新取证，与上一轮结论**方向不同**）

### 2.1 上一轮结论是什么

上一轮报告（`docs/实现-二采接缝色档差异消除-20261117.md:40`）的归因原文是：

> 「SelfLift 的低分辨率段把钉住区**降采样**后当锚点 →
> 新生成区继承了低分辨率段的色档」

并据此加了「拼接 `setpts` + `H3RelayPost.match_prev` 跨段统计匹配」。

### 2.2 本轮的方向差异（**关键**）

上一轮那句话隐含一个**可检验的推论**：如果色档阶跃来自段2 的**采样过程**，
那段2 自己的头几帧内部就该有色档阶跃，而且这段阶跃在**段2 单独播放时同样存在**
（不依赖拼接）。**上一轮没有做这个检验。**

本轮写了**独立测量器**（`tools/seam_metric.py`，13,306 字节）从零拆开量，
结论与上一轮**方向不同**：

| | 上一轮结论 | 本轮结论 |
|---|---|---|
| 断点位置 | 拼接点两侧（跨段档差） | **段2 自己内部（帧0→帧1）** |
| 机制 | 低分辨率降采样锚点被继承 | **高分辨率二采 NFE 预算不足**（1 步） |
| 空间高频的角色 | 降采样锚点的「指纹」 | 段头细节档只有中段 15%（**是症状不是原因**） |
| 修法方向 | 拼接侧跨段统计匹配（`match_prev`） | **采样侧 NFE 预算**（夹 `transition_step`） |

实测（线上真实产物，受控复现，`【原始证据】` 来自
`evidence/twopass-seam-repro-20261117-201114/report.json` 与
`.../203044/report.json`）：

```
段2 内部帧0→1 的 RGB L1 差：
  缺陷档（steps=4, transition_step=3） = 13.801
  改 transition_step=2 后            = 1.077
  非二采对照                          = 0.384
```

**为什么上一轮的修法打不中要害**：`match_prev` 跨段统计匹配修的是
**拼接点两侧的档差**，对**段2 内部 f0→f1 的断点**无能为力
（断点在窗口内，但不是「与 guide 的差」）。
这正好解释了「19.39→10.14（跨段压了一半）但段2 头断点 56x→58x 纹丝不动」。

### 2.3 机制的决定性证据（ComfyUI 自己的日志）

`/home/ubuntu/comfyui/user/comfyui.log` 的 `[SelfLift plan]` 行直接给出 NFE 分配：

```
steps=4 transition_step=3 -> low_nfe=3  high_nfe=1  sigma_prediction=0.92336  sigma_resume=0.72073
steps=7 transition_step=5 -> low_nfe=4  high_nfe=5  sigma_prediction=0.75000  sigma_resume=0.58682
steps=5 transition_step=4 -> low_nfe=5  high_nfe=2  sigma_prediction=0.88971  sigma_resume=0.76986
```

SelfLift 把 sigma 表切成 `sigmas[:ts+1]`（低分辨率）与 `sigmas[ts:]`（高分辨率），
所以 **高分辨率 NFE = steps − transition_step**（纯算术）。

默认档 `steps=4 / transition_step=3` ⇒ **高分辨率二采只剩 1 步 NFE，
起始 sigma 高达 0.72**。低分辨率一采在**降采样空间**里已经定下色档与细节档，
抬升回高分辨率后，高分辨率二采必须同时做「提分辨率 + 收敛色档 + 生成内容」三件事，
**1 步预算不够** ⇒ 段头几帧色档 + 细节档双重掉档 = 肉眼看到的「闪一下」。

**本轮复核**（`【原始证据】`，全日志统计）：

```
grep -c "high_nfe=1 " comfyui.log  →  0      ← 缺陷档完全清零
grep -c "high_nfe=[2-5] " comfyui.log → 20
```

### 2.4 空间高频指纹（症状，不是原因）

`【原始证据】` 段2 头 4 帧高频能量 `[0.436, 0.429, 0.431, 0.468]` vs 帧中段 `2.922`
⇒ 段头细节档只有中段的 15%。

> **必须说清**：上一轮把这个指纹当成「降采样锚点」的**直接证据**；
> 本轮重新看，它是「低分辨率锚点被抬升」这个**事实的指纹**，
> 但**不是**色档阶跃的**原因** —— 原因是高分辨率段 NFE 不足，收敛不掉它。
> 这个区分正是两轮结论方向不同的关键。

## 3. 修法（Studio 侧，**零 comfyui 改动**）

### 3.1 实现

新增 `h3studio/twopass_budget.py`（132 行，6,840 字节）：

- `high_res_nfe(steps, transition_step) = steps − transition_step`（SelfLift 切表语义）
- `clamp_transition_step(steps, transition_step, min_ratio=0.5)`：
  把 `transition_step` 夹到 `ts ≤ steps × (1 − 1/2)`（**向下**取整，
  保证高分辨率段至少拿到一半 NFE 预算）

| steps | 原 ts | 夹后 ts | high_nfe 变化 | 本轮复核【原始证据】 |
|---|---|---|---|---|
| 4 | 3 | **2** | 1 → 2 | ✅ `clamp_transition_step(4,3) = 2` |
| 7 | 5 | **3** | 2 → 4 | ✅ `clamp_transition_step(7,5) = 3` |
| 8 | 6 | **4** | 2 → 4 | ✅ `clamp_transition_step(8,6) = 4` |

**两道防线**（夹取分别落在）：
- `server.py:2909`（参数归一化层）
- `h3studio/video_workflow.py:927`（工作流构建层）

⇒ 节点**永远拿不到**「高分辨率 NFE 不足」的 `transition_step`。

**夹取有损**（一采步数变少 = 低分辨率提速收益变小）⇒ **必须留痕**：
归一化层用 `_video_note(out, "twopass.transition_step", ...)` 写明
「一采 2 步（二采 2 步，高分辨率占 50%）」。

### 3.2 为什么**不改** `/home/ubuntu/comfyui`

`transition_step` 本来就是 SelfLift 的**公开节点输入**
（`INPUT_TYPES` 里就有，tooltip 写明「Number of low-resolution denoiser
evaluations」），高分辨率 NFE = steps − ts 是**纯算术**，Studio 侧就能夹住。

**实测：只改 Studio 侧传的 transition_step，缺陷即消失。**

`【原始证据】` 线上归一化实证（job `b300935d9c6f`）：

```
request twopass: {"enabled": true, "transition_step": 3, ...}   ← 用户/面板填 3
normalize_notes:  ["twopass.transition_step：3 不是合法取值，已改用 2
                    （高分辨率二采至少要拿一半的 NFE 预算：一采 2 步
                    （二采 2 步，高分辨率占 50%）；否则段头会色档掉档 = 接续点闪烁）"]
实际下发:         transition_step = 2
```

### 3.3 修法取舍：为什么**不选**其它候选

| 候选 | 为什么**不**选 |
|---|---|
| 改 SelfLift 节点源码（让它自己保证高分辨率 NFE） | 第三方节点，跨仓改动；且 `transition_step` 是**公开输入语义**（用户显式指定「低分辨率跑几步」），节点擅自改写用户输入是**越权**。实测表明 Studio 侧夹一下就够。 |
| 改 ComfyUI 核心 / Relight 节点的 sigma 表 | 那是**模型层**的语义，动它会影响所有 H3 任务（包括已验收的接续链路），风险远大于收益。 |
| 直接把 `steps` 调大（如 4→7） | 治标不治本：`steps=7` 时 `high_nfe` 仍可能只有 2（ts=5），实测 `steps=7 trans=5` 的 seam_ratio 反而高达 **58.688**。而且直接改总步数 = 放弃 4 步加速的全部收益。 |
| 调 `rho`（SelfLift 的混合系数） | 实测 `rho=0.6` 能把头断点比压到 2.12x，但**跨段跳变仍是 10.405**（比 `rho=0` 的 19.311 好，但没解决色档阶跃的根因），而且 `rho` 会引入**像素锚点**（`direct_lift=external pixel_anchor`），是另一套机制。 |
| 调 `lowres_scale`（1.0 = 不降采样） | 直接放弃二采的提速意义，退化成单分辨率采样。 |
| 改拼接侧（`setpts` / `match_prev`） | **上一轮已经试过** —— 实测跨段跳变 19.39→10.14 有效，但段2 头断点 **56x→58x 纹丝不动**，证明方向不对（§2.2）。 |
| 在 Studio 侧**抬高**低分辨率倍率 | 需要重新调 SelfLift 的 upscaler 与 latent 尺寸，属于改模型管线，代价与风险都远超本缺陷的收益。 |

**取舍的代价必须说清**：夹取是**有损**的 —— 一采步数从 3 降到 2，
低分辨率段的提速收益变小。**本轮未量化耗时变化（未验证项，见 §7.2）**。

### 4.3 ⚠️ 「2.996x 与非二采对照是否同量级」—— 如实回答

**先厘清口径**（这是最容易读错的地方）：

| 口径 | 定义 | 缺陷档 | 修复后 | 非二采对照 |
|---|---|---|---|---|
| **全片中位口径**（本轮新测量器） | seam_rgb_jump ÷ 全片帧差分**中位数** | 15.372 | **2.996** | **1.165** |
| **历史 seam_ratio 口径**（上一轮） | seam_rgb_jump ÷ 段内量级**均值** | 15.442 | — | 2.138 |

两套口径的数字**不可直接混用**。用户需求里写的「非二采对照约 2.1x」
对应的是**历史口径的 2.138**；而「2.996x」是**新口径**的值。

**在各自口径内做比较**：

```
新口径：修复后 2.996 ÷ 对照 1.165 = 2.57 倍
        修复前 15.372 ÷ 对照 1.165 = 13.19 倍
历史口径：缺陷档 15.442 ÷ 对照 2.138 = 7.22 倍
```

**结论（不粉饰）**：

- ✅ **是同量级** —— 2.57 倍的差距**没有跨数量级**
  （修复前是 13.19 倍，是跨了半个数量级；现在连一半都不到）。
- ❌ **不是同一水平** —— 修复后仍比非二采对照**高 2.57 倍**。
  用绝对值看：段2 头断点 1.077 vs 对照 0.384（绝对差 0.69，肉眼大概率不可见）；
  但**比值**这一项仍明确偏高。
- ⇒ **准确表述**：**从「跨数量级的异常」降级为「同量级但仍偏高 2.6 倍的残余」**，
  而不是「已完全消除」。§7.1 列了这条残余的具体表现。
