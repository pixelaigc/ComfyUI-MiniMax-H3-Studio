## 2. 第 1 步：HTML 本体被缓存？—— **实测不成立**

### 2.1 线上实际响应头

```
$ curl -D- http://127.0.0.1:8190/
HTTP/1.1 200 OK
Cache-Control: no-cache, must-revalidate
Content-Type: text/html
Etag: "18ea02e39b4d5796-192f2"
Last-Modified: Sat, 21 Nov 2026 08:42:59 GMT
Content-Length: 103154
```

⇒ `index.html` **已经**有 `no-cache, must-revalidate`。
`no-cache` 的语义是「每次使用前必须向源站验证」——
**不是**「不缓存」。

### 2.2 条件请求行为（200 vs 304）

```
带 If-None-Match: "18ea02e39b4d5796-192f2"
  → HTTP/1.1 304 Not Modified
    Cache-Control: no-cache, must-revalidate

带 If-Modified-Since: Sat, 21 Nov 2026 08:42:59 GMT
  → HTTP/1.1 304 Not Modified
```

⇒ 304 **只在内容真的没变时**返回。
服务端改了 `index.html` ⇒ ETag 变 ⇒ 304 不成立 ⇒ 浏览器必须拿新的。

### 2.3 这个 `no-cache` 是什么时候加的

```
git log -S 'no-cache, must-revalidate' -- server.py
  d46dd9f 11-08 16:41  feat(ui): 默认面板切到 Z-IMAGE 文生图 + 修复默认筛选历史列表空白

git show 241889a:server.py   # 11-04 的版本
  async def index_handler(request):
      return web.FileResponse(BASE / "web" / "index.html")   ← 当时**没有** Cache-Control
```

⇒ **`index.html` 从 2026-11-08 16:54 起就有 `no-cache, must-revalidate`**，
已经覆盖了本次故障窗口（11-21）。

### 2.4 静态资源的缓存（这里才是真风险）

```
$ curl -D- http://127.0.0.1:8190/static/style.css?v=navfix20261121a
HTTP/1.1 200 OK
Content-Type: text/css
Etag: "18e9eae969bbc528-23bbb"
Last-Modified: Sat, 21 Nov 2026 01:23:35 GMT
Content-Length: 146363
                    ← **没有 Cache-Control**
```

⇒ `/static/*` 靠 **`?v=` 版本号**破缓存（浏览器启发式缓存按 URL 区分）。
这正是既有契约 `test_server_static_has_no_cache_control_is_known_risk` 存在的原因。

### 2.5 缓存假设的实测排除

```
SCEN1 修前实例读到:              {"drawerHead": false, "respCss": false}
SCEN1 同 context 访问修后实例:   {"drawerHead": true,  "respCss": true}   ← 拿到新版
SCEN2 全新 context 访问修后实例:  {"drawerHead": true,  "respCss": true}
```

⇒ 因为 `?v=` 变了（URL 变了），缓存**不可能**命中。

**结论**：**「HTML 本体被缓存」这条不成立**（`index.html` 自 11-08 起就是 `no-cache, must-revalidate`，
且 304 只在内容未变时返回）。**「静态资源被缓存」才是理论风险点**，但 `?v=` 机制已经挡住了它。

⇒ 这**不是缺陷**（用户本来就要滚），但判据必须是「**滚动后**能点到」。

#### F3（12 次）：横屏 932×430 是**平板档**，侧栏常驻、没有汉堡

## 5. 第 4 步：处置 —— 修掉真问题 + 给用户自查能力

### 5.1 真问题 A：顶栏空间被 `.brand` 抢光（产品缺陷，本轮修）

**现象**：为解决「用户无法确认自己跑的是哪一版」，我把版本号加进顶栏。
第一次放在 `.brand-name` 内 ⇒ 320px 下被挤成 **w=0**（完全看不见）。
第二次放在 `.brand` 的兄弟节点 ⇒ **与 `v1.00` 视觉重叠 213px²**
（`vision_analyze` 复核截图明确看到重叠）。

**根因**：窄屏下 `.brand` 是 `flex: 1 1 auto`（会抢满剩余空间），
而它内部的 `strong` / `.brand-version` 都是 `white-space: nowrap`（不肯缩）
⇒ 内容溢出 `.brand` 的盒子，视觉上压到别人身上。

**修法**（`web/favorites.css`，**只写在 ≤700px 断点里**，桌面端零影响）：
```css
@media (max-width: 700px) {
  .topbar .brand { flex: 0 1 auto; overflow: hidden; }
  .topbar .brand-name { flex: 0 1 auto; overflow: hidden; }
  .topbar .brand-name strong { overflow: hidden; text-overflow: ellipsis; min-width: 0; }
}
```
⇒ 空间不够时**品牌区自己先收**（品牌名被截断），把位置让给版本号。

**复测（5 档宽度）**：
```
320x568  重叠: 与v1.00=0 与状态灯=0 与汉堡=0   在视口内=True
360x640  重叠: 与v1.00=0 与状态灯=0 与汉堡=0   在视口内=True
375x667  重叠: 与v1.00=0 与状态灯=0 与汉堡=0   在视口内=True
390x844  重叠: 与v1.00=0 与状态灯=0 与汉堡=0   在视口内=True
430x932  重叠: 与v1.00=0 与状态灯=0 与汉堡=0   在视口内=True
```
`vision_analyze` 复核 320px 截图：**「非常清晰…没有任何视觉上的重叠」**。

### 5.2 真问题 B：指纹算法取 max 版本号（产品缺陷，本轮修）

第一版 `assets_fingerprint` 取所有 `?v=` 里**字典序最大**的：
```
assets_id = "vparams7"     ← 一个 2026-07 的老版本号，毫无指示意义
```
版本号是人工命名的（`mobnav20261121a` / `vparams7` / `refctx1`），
字典序大小跟新旧**毫无关系**。

⇒ 改成对「文件名=版本号」清单（排序后）取 **SHA-256 前 8 位**：
```
assets_id = "1db03c9c"
```
性质：任何 `?v=` 变了 ⇒ 指纹必变；同一 commit ⇒ 同一指纹；长度固定适合一行小字。

### 5.3 交付给用户的能力：可见的构建版本标识

**这才是本轮对「用户仍报现象」最实际的处置** ——
让用户**下一次反馈能直接对照**，不必再猜。

**接口** `GET /api/version`（服务端 `h3studio/build_info.py`）：
```json
{
  "commit": "2954ade",
  "assets": {"style.css": "mobnav20261121a", "app.js": "mobnav20261121a", ...},
  "assets_id": "1db03c9c",
  "built_at": 1795252637,
  "served_from": "/root/projects/h3studio-live",
  "server_time": 1795252700
}
```
- `commit` 来自**部署目录的真实 git**（`git rev-parse --short HEAD`），**不是硬编码**
- `assets` / `assets_id` 是**前端实际请求的** `?v=`（现场解析 index.html）
- `built_at` 能看出服务是不是刚重启过
- `served_from` 能看出是不是跑在 live worktree

**UI 两处**（**不新增任何导航分组**，左侧仍是 7 个顶层分组）：
1. **顶栏**：commit 短哈希（7 字符）—— 320px 下也放得下（37px 宽）
2. **系统页「构建版本」卡片**：完整明细（commit / 静态资源指纹 / 服务启动时间 / 部署目录）

**为什么顶栏只放 commit**：320px 下顶栏富余仅 ~33px（实测），
放两段会被压到 0 宽。完整信息去系统页。

**用户端可执行的确认步骤**（写进交付报告）：
1. 手机打开 `http://<host>:8190/`，看**顶栏**的短哈希
2. 与「系统 → 硬件参数 → 构建版本」卡片里的 commit 对照
3. 若顶栏**没有**版本号 ⇒ 手机上是**旧版页面** ⇒ 硬刷新 / 无痕窗口
4. 若哈希与线上不一致 ⇒ 手机上缓存了旧资源 ⇒ 硬刷新

## 6. 未复现项 —— 证据性解释

**用户为什么还会看到这个现象** —— 可验证的三条：

### 解释 1：用户的手机页面不是当前这一版（**最可能**，且现在可以自证）

### 解释 2：某条路径仍有问题，但**不在我测的维度里**

- 浏览器「返回」手势 / bfcache
- 用户的具体操作序列（我按最典型的路径走）

⇒ 若顶栏哈希是对的、但现象仍在，**请录屏**。有了版本号 + 录屏，可以直接定位。

### 解释 3：静态资源缓存（**实测已排除**，但机制仍在）

- `index.html` 自 11-08 起就有 `no-cache, must-revalidate` ⇒ **HTML 缓存不成立**
- `/static/*` 靠 `?v=` 破缓存；版本号变了 URL 就变 ⇒ 缓存命中不了
- **但**：`/static/*` 没有 `Cache-Control`（仓库既有契约 `test_server_static_has_no_cache_control_is_known_risk` 明确记载这是「已知风险」）
  ⇒ 若某个资源**内容改了但 `?v=` 忘了升**，老用户会拿到旧文件
  ⇒ 本轮的 `test_frontend_assets_hygiene.py` 就是守这个的（顺手修掉了它的一个**隐藏重复条目**）

## 8. 未做到的项与已知限制（如实）

1. **没有在真机上验证** —— 全部是 Playwright Chromium + WebKit（headless / Xvfb headed）模拟。
   iOS Safari 的地址栏收放、PWA standalone、返回手势、bfcache **未覆盖**。

2. **WebKit 是 WebKit 26.4（Linux 构建）**，不是 iOS Safari 的 WebKit ——
   渲染/手势行为有差异（尤其 `<video>` 的手势）。

3. **本机 WebKit 需要手工打补丁**（`scripts/setup_webkit_on_this_host.sh`）——
   改了 `~/.cache/ms-playwright/webkit-2272/pw_run.sh`（headless 走 GTK）
   并补了老 soname 库。**这些改动在本机 Playwright 缓存目录里，重装 Playwright 会丢**。

4. **视频卡长按右键菜单仍然唤不出来** —— `<video>` 原生手势吞 touch 事件。
   已提供不依赖右键的入口（卡片底部「☆ 收藏」按钮）。**这一条仍成立**。

5. **长按阈值 550ms 是经验值** —— 可能与个别用户预期有出入。

6. **版本标识只显示 commit 短哈希**（顶栏空间限制）——
   完整信息需进「系统 → 硬件参数」页。**如果用户不知道这个入口**，
   顶栏那一串哈希仍够用来跟线上对照。

7. **`/static/*` 仍没有 `Cache-Control`** —— 仓库既有契约明确记载这是「已知风险」，
   依赖 `?v=` 破缓存。本轮未改这个契约（改了会让
   `test_server_static_has_no_cache_control_is_known_risk` 变红）。

8. **额度快照已滞后 2 天** —— 本轮未刷新（不新建探针任务）。
   由于本轮**未产生任何 GPU 生成作业**，风险为零。
