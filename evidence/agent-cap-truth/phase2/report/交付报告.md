## 2. 目标 1｜flf / r2v 默认参数（用户实测反馈，确实还没修）

### 2.1 事实定位

| 环节 | 真实位置 |
|---|---|
| **存储** | SQLite `model_provider_prefs` 表 / key=`agent_settings` / 字段 `gen_defaults`（线上库：`/root/projects/comfyui-minimax-h3-studio/data/jobs.db`） |
| **下发接口** | `GET/PUT /api/agent/settings` → `gen_defaults`（当前生效值）+ `gen_defaults_spec`（字段规格） |
| **面板渲染** | `web/agent-manage.js::renderGenDefaults()` —— **完全由 spec 驱动**，前端不硬编码任何取值 |
| **消费路径 A（面板提交）** | `POST /api/jobs` → `server.prepare_job_params` → `h3_video_size.apply_size` |
| **消费路径 B（Agent 自建）** | `POST /api/agent/chat` → `agent.py::_tool_create_job` → `gen_defaults.merge_into_params` → `server.prepare_agent_t2v_params` |

### 2.2 修正前基线（线上实测抓取）

`gen_defaults.flf`（修正前）：
```json
{"aspect":"16:9","resolution":"768p","duration":5.0,"lora":"ckpt850",
 "lora_strength":1.0,"precision":"int8","steps":4,"sampler":"euler",
 "scheduler":"beta","shift_video":12.0,"shift_audio":3.0}
```
`gen_defaults_spec.flf` 的 `resolution` 字段（修正前）：
```json
{"name":"resolution","label":"分辨率档位","type":"enum",
 "options":[{"value":"544p","label":"544p"},{"value":"768p","label":"768p"}],
 "default":"768p","note":"544p = 0.4MP / 768p = 0.8MP"}
```

→ **两个写死的旧档位**（544p/768p）、**写死的旧 MP 口径**（note）、**没有 MP 预算字段、没有百分比字段**。

### 2.3 根因

`gen_defaults._video_legacy_fields()` 用 `wf.RES_MP.keys()`（`{"544p":0.4,"768p":0.8}`）——
那是**旧界面 `#resSeg` 的两档遗留**，不是生成侧的能力上限。

真实约束（`video_models.VIDEO_MODE_SIZE_POLICY`，实时派生）：
flf / r2v 面积上限 **2.0 MP**（与 t2v 同，2026-11-17 放宽，对齐 nonebot seg1/seg2 的
`ResolutionSelector(megapixels=2)`），`multiple=32`，单边 32~16384，`custom_size=True`。

### 2.4 修法

1. **分辨率选项改为按各 mode 真实上限派生**（`size_presets_for_aspect` 并集）→ **28 档**（288p…1440p），不是 2 档。
2. **note 改为真实上限**：`按该模式的真实面积上限（2.0 MP）派生；也可以直接填下面的 MP 预算 × 百分比`。
3. **新增 MP 预算 + 百分比字段**（见目标 2）。
4. **补底模字段**（`model_key`）—— 见 2.6。

### 2.5 存量迁移

新增 `gen_defaults.migrate_size_expression()`：**读取时**迁移（幂等），任何来源的存量数据
都自动变成新表达。

迁移按**旧口径**（`workflows.RES_MP`）反查 —— 因为历史上「768p」有两个**互不相同**的含义：

| 口径 | 768p 的含义 | 16:9 下像素 |
|---|---|---|
| 旧（`workflows.RES_MP`） | 0.8 MP | **1216×672** |
| 新（短边档位） | 短边 768 | 1344×768（0.984 MP） |

按旧口径才能保证用户**已配好的像素不变**。

线上实测迁移结果：
```
flf 存储值 resolution="768p" -> 读出 megapixels=0.8, resolution_percent=100.0
     -> 落库 1216×672（0.779 MP）  ← 像素与修正前完全一致
```

### 2.6 顺带修掉的真缺陷：r2v 线上 400

**线上实测复现**：r2v 提交直接 400 ——
「模型『MiniMax-H3 FL2VA · 剪枝 int8（默认）』不支持参考生成（Ref2VA）通道」。

**根因**：flf/r2v 的字段表**没有底模** → `normalize_t2v_params` 取 `params["model_key"]` 落空
→ 回落 `VIDEO_DEFAULT_MODEL`（FL2VA 权重）→ 校验失败。

**这不是「配了不生效」的假控件**：`h3_video_modes.build_flf / build_r2v` **确实读**
`params["model_key"]`（`model_for_mode(mode, params.get("model_key"))`）。

**修法**：`_video_legacy_fields(mode)` 按 mode 参数化，底模选项按 mode 过滤
（flf 只列 FL2VA 系 4 个、r2v 只列支持 Ref2VA 的 3 个），全部取自 `video_models.VIDEO_MODELS`
真实注册表。

### 2.7 修正后（线上接口实测）

"flf": {"model_key":"fl2va_pruned_int8","aspect":"16:9","resolution":"768p",
        "megapixels":0.8,"resolution_percent":100.0,"duration":5.0,
        "lora":"ckpt850","lora_strength":1.0,"precision":"int8","steps":4,
        "sampler":"euler","scheduler":"beta","shift_video":12.0,"shift_audio":3.0},
"r2v": {"model_key":"ref2va_pruned_int8", ...同上}

`spec.flf.resolution`：`options` 28 档、`note` 为真实上限说明；
新增 `model_key` / `megapixels` / `resolution_percent` 三个字段。

## 3. 目标 2｜分辨率统一为「MP 预算 × 百分比」

### 3.1 新增单一真源 `h3studio/size_spec.py`

```
MP 预算 = 该 mode 真实面积上限（实时派生，非导入期快照）
实际 MP = 预算 × 百分比
宽高    = video_models.video_dimensions(aspect, mp)   ← 与 ComfyUI ResolutionSelector 同源公式，天然对齐 32
超上限  → video_models.normalize_video_size 按比例缩放 + 给出原因
调整原因 → 写进既有 params["size_adjust_reasons"]
```

**复用既有公式，不另造一套**（`video_dimensions` 已逐格复现官方模板 Note 的十四档）。

### 3.2 各 mode 的真实边界（现场核实，非沿用旧文档）

| mode | 真实上限 | 32 对齐 | 单边 | 自定义宽高 | 依据 |
|---|---|---|---|---|---|
| t2v | 2.0 MP | 32 | 32~16384 | ✅ | `VIDEO_MODE_SIZE_POLICY` |
| flf | 2.0 MP | 32 | 32~16384 | ✅ | 同上（2026-11-17 放宽） |
| r2v | 2.0 MP | 32 | 32~16384 | ✅ | 同上 |
| t2i | 8.3 MP | 32 | 32~16384 | ✅ | `Z_IMAGE_RES_TIERS` |
| t2i_qwen / i2i_qwen | 4.0 MP | 32 | 32~16384 | ✅ | `QWEN_IMAGE_RES_TIERS` |
| t2i_moss | 4.0 MP | 32 | 32~16384 | ✅ | `MOSS_IMAGE_RES_TIERS` |
| t2i_h3image / i2i_h3image | 16.0 MP | 32 | 32~16384 | ✅ | `H3_IMAGE_RES_TIERS` |
| **t2a / a2a（音乐）** | **不适用（无画面尺寸概念）** | — | — | — | `music_yue2` 只读时长/采样参数 |

> 音乐模式**不加** MP/百分比字段 —— 不臆造能力。

### 3.3 三处统一

| 位置 | 现状 |
|---|---|
| 默认参数（管理页） | `megapixels` + `resolution_percent` 两个 number 字段，选项/上限/默认值全部派生 |
| 面板展示 | 前端 `renderField` 已支持 number —— **无需改前端**（`web/agent-manage.js` 零改动） |
| Agent 能力自述 | `agent_capability.video_capability_text()` / `list_modes.video_resolution_note` / `agent_schema.mode_schema` 全部改派生 |

### 3.4 线上真实用例（5 个，落库 params 实测）

| 用例 | 原始请求 | 生效宽高 | 生效 MP | 调整原因 |
|---|---|---|---|---|
| **A 合法值原样放行** | `megapixels=0.4` | **864×480** | 0.396 | `flf 尺寸：MP 预算 0.400 MP + 比例 16:9 -> 864×480` |
| **B 需吸附 32 倍数** | `megapixels=0.41` | **864×480** | 0.396 | `flf 尺寸：MP 预算 0.410 MP + 比例 16:9 -> 864×480` |
| **C 超 MP 上限自动下调** | `megapixels=4.0` | **1920×1088** | 1.992 | `总像素 3.984 MP 超过 flf 上限 2.0 MP -> 已缩到 1920×1088` |
| **D 百分比 50%** | `resolution_percent=50` | **1376×768** | 1.008 | `按 50.0% 的 MP 预算换算：2.0 MP × 50.0% = 1.000 MP` |
| **E 百分比 150% 超限** | `resolution_percent=150` | **1920×1088** | 1.992 | `总像素 3.035 MP 超过 flf 上限 2.0 MP -> 已缩到 1920×1088` |

### 3.5 顺带修掉的两个真缺陷

1. **`max_pixels_for_mode` 读导入期快照**
   `video_models.VIDEO_MODE_SIZE_POLICY` 是模块导入时构造的字面量字典，
   `max_pixels_for_mode` 直接读它 → 改 `VIDEO_MAX_CANVAS_PIXELS` 后
   `size_policy_for_mode`（已实时派生）报新值、它仍报旧值 —— **同一真源两套行为**。
   实测：改上限后 `size_policy_for_mode` = 1.0 MP、`max_pixels_for_mode` = 2.0 MP。
   → 改为复用 `size_policy_for_mode`。

2. **显式宽高不吸附到 32 的倍数**
   实测：提交 `width=1900, height=1000` → 原样跑 1900×1000（`width%32=12`）。
   H3 的 `CANVAS_MULTIPLE=32`、节点 schema `step=32`、latent 网格 `width//16`
   —— 非 32 倍数会得到不对齐的 latent 网格。
   → `size_spec.plan_size` 与 `h3_video_size.resolve_size` 都做吸附 + 说明
   （实测 1900×1000 → 1888×992，原因回传）。

## 4. 目标 1 第 4 条｜默认参数对**两条路径**都生效

### 4.1 定位到的真实缺口

**面板提交路径根本不套 `gen_defaults`**：
`gen_defaults` 只被 Agent 路径消费（`agent.py` 的 `merge_into_params`），
`POST /api/jobs` 完全不套 —— 用户在管理页配的默认时长 / MP 预算 / 采样参数，
对面板点「生成」**没有任何作用**。

### 4.2 修法

新增 `server.apply_gen_defaults_and_size(mode, params)`：
1. 套管理页默认参数（t2v 走既有 `_merge_t2v_defaults` 专用路径）；
2. 解析尺寸（`size_spec.plan_size`）。

在**两个时机**调用（同一份实现、幂等）：
- `api_create` 里 `normalize_t2v_params` **之前**；
- `prepare_job_params` 里（所有建任务路径的公共点：面板提交 / Agent create_job / retry_job）。

### 4.3 顺带修掉的真缺陷：提交前不解析尺寸 → 400

`normalize_t2v_params` 第一件事就是校验 `width/height`，没有宽高直接 400
（「宽高无效：宽高必须数字」）。而 flf/r2v 的宽高是**后面**的
`prepare_job_params` → `h3_video_size.apply_size` 才算出来的。
→ 「只传 resolution / megapixels、不传像素」的提交（内置 Agent 自建 job、
旧客户端、只有档位没有像素的调用方）**在建任务之前**就被 400 挡掉。
→ 现在提交前先解析尺寸。

### 4.4 两条路径的实际验证

**路径 A（面板提交，真实 HTTP → 真实 SQLite）**
```
POST /api/jobs  mode=flf  params={"prompt":"...","asset_id":"asset_…"}
落库 params: width=864 height=480 megapixels=0.396 duration=6.0
             lora=ckpt850 precision=int8
```
（`duration=6.0` / `lora=ckpt850` / `precision=int8` 全部来自管理页保存的默认值，
提交时**没带**这些字段 —— 证明是默认参数被套上的，不是碰巧。）

**路径 B（Agent 自建 job）**
`_user_gen_defaults(ctx)` → `ctx.server.agent_settings_snapshot()` → 真实库读出
`gen_defaults.flf` → `merge_into_params` 套进 params。端到端测试用**真读数据库**
的 server 替身（不是手写常量）验证。

**线上实测**：flf 与 r2v 各一条真实落库 job，参数一致
（`1216×672 / MP=0.779 / dur=5.0`），证明存量迁移在两条路径都生效。

### 4.5 顺带修掉的真缺陷：显式百分比被默认 MP 预算盖掉

**线上实测复现**：提交 `resolution_percent=50`，落库却是 `1216×672`
（= 管理页默认的 0.8 MP），而不是 50%×2.0MP = 1.0 MP 的 `1376×768` ——
**用户的百分比被无视了**。

**根因**：「MP 预算」与「MP 预算百分比」是同一件事的两种写法，
而 `plan_size` 的优先级是 `megapixels > percent`；`merge_into_params` 把管理页默认的
`megapixels` 也套了进来 → 两个都在 → `megapixels` 胜出。

**修法**：用户显式给了哪一个，就**只保留那一个**
（显式 percent → 不填默认 megapixels；显式 megapixels → 不填默认 percent）。
