## 0. 一句话结论

Agent 的能力自述原来硬编码在三处（系统提示词 / `list_modes` 返回 / `create_job` schema）且各写一份；

## 3. 目标 C：补齐媒体后处理

### 3.1 新增 4 个 ffmpeg 工具（真实调用，产物入库可被后续引用）

| 工具 | 能力 | 关键实现 |
|---|---|---|
| `media_extract_audio` | 从视频**抽取音轨**成独立音频素材 | `-vn` 丢视频流；输出 m4a/mp3/wav/flac/opus；可选起止 |
| `media_trim` | **时长裁剪 / 截取片段** | 输出侧 `-ss`（精确裁剪，不丢帧不偏移）+ `-t`；重编码保证帧精确；超出素材长度时截到末尾并标 `clipped_to_source` |
| `media_normalize_audio` | **响度归一**（EBU R128） | `loudnorm=I=<target>:TP=<peak>:LRA=11`；视频流 `-c:v copy` |
| `media_replace_audio` | **真正替换音轨** | 原声**彻底去掉**（默认）；`keep_original=True` 时两路 `amerge` 并排（先降为单声道，避免 4 声道相位抵消）；`apad` + `-shortest` 对齐长度 |

**为什么需要 `media_replace_audio`**：原来的 `media_mix_audio(replace=True)` 语义是「把原音**也**作为一路送进 amix」—— 原声仍留在成片里。那是「混」不是「替换」。用户说「把这段 BGM 换成那段音频」时要的是原声被去掉。

### 3.2 安全边界（沿用既有设计，未放松）

- 输入只认**素材库 asset_id**（`_resolve_asset_path` 走素材库查库 + 路径内解析），不接受外部文件路径
- 产物走 `asset_service.register_asset` 入库（去重/元数据/预览），**可被后续工具引用**
- ffmpeg 参数全部由代码拼装，模型传的参数只进白名单分支，不做 shell 拼接
- 失败抛 `MediaToolError(code=...)`，原因回传给模型

### 3.3 设计参考

`/home/ubuntu/nonebotqq/plugins/nonebot_plugin_novelai` 的咏唱实现（`h3_audio_video_merge.py` / `h3_audio_edit.py` / `h3_chain_video.py` / `h3_yue2_remix.py`）：

- **已移植**：先 ffprobe 再拼命令；concat 前统一 time刻度；音轨不齐补等长静音；混音前统一采样率/声道/布局；`amix` 用 `normalize=0` 保留各路原始响度关系；失败不留半成品；临时文件清理
- **未移植（nonebot 特有耦合）**：事件对象 / 会话状态机 / QQ 文件下载 / 用户交互菜单 / 触发词
- **本项目额外补强**：产物 size>0 校验、`apad` 补齐、`amerge` 先降单声道（本机 ffmpeg 7.1.1 的 `amerge` **没有** `duration` 选项 —— 实测报 `Option not found`）

## 4. 目标 D：让多步请求一气呵成

### 4.1 三处编排缺陷与修法

| 缺陷 | 修法 |
|---|---|
| **D1 提示词强制反问** | 删除「关键参数缺失…不要瞎猜，也不要硬着头皮做」整节，改成「多步请求：一次做完，不要中途停下等用户催」，并明确只有三种情况才提问（素材根本不存在 / 解读互相冲突 / 需要用户凭证）。同时把「工具调用预算是 8 次」改成 `{MAX_TOOL_CALLS}` 的真实值并注明「这是**上限**不是配额」 |
| **D5 respond 无条件收尾** | 澄清式 respond（`needs_clarification=true`）**不再收尾**：编排层继续执行剩余工具调用，并给模型一条 nudge「先把能做完的做完，缺的那个参数按最贴近用户表述的合法值处理，并在最终结论里说明你替他做了什么」。结论性 respond 仍收尾。收尾态判定：有实质进展 → `completed`（澄清问题降级为「附带确认项」）；无实质进展 → `needs_clarification` |
| **D4 无进展检测缺失** | 新增 `_progress_fingerprint()` + `NO_PROGRESS_LIMIT = 6`：算每次工具调用的「事实指纹」（search_assets → 命中的 asset_id 集合；describe_asset → 描述哈希；create_job → job_id；媒体工具 → 产物 asset_id；配置类工具 → 工具名**+参数**）。连续 6 步指纹不变 → 先纠偏提示，再收尾 |
| **D6 工具结果 JSON 被裁坏** | `_clip` 从「头尾拼接」改为**结构化裁剪**：合法 JSON dict → 逐轮缩短长字符串值直到塞进上限（JSON 始终合法）；塞不进 → 退化裁剪并附上原结果的键清单 |

### 4.2 保留的护栏

- `MAX_STEPS = 50`（已是 50，本轮确认无需调整；`agent_settings.MAX_STEPS_HARD_CAP = 50`，线上配置 `max_steps: 50`）
- `MAX_TOOL_CALLS = 120`
- `TOTAL_TIMEOUT = 2400`（可配范围 `[60, 14400]`，线上走管理页配置）
- `REPEAT_LIMIT = 3`（同名同参）
- **新增** `NO_PROGRESS_LIMIT = 6`、`CLARIFY_LIMIT = 2`（防止澄清式 respond 变成死循环）

### 4.3 端到端单测

`test_clarification_does_not_stop_the_chain`：模拟模型第 1 轮先澄清式 respond、第 2 轮 search、第 3 轮 media_merge_av、第 4 轮给结论 → 断言 `status == completed` 且 `media_merge_av` **被调用**（旧行为下澄清即收尾，合并根本不会发生）。

### 6.5 部署脚本的加固（自查发现并已修）

部署脚本用 `git diff --name-only LIVE_BEFORE MERGE_COMMIT` 算改动清单，再 `git checkout MERGE_COMMIT -- <清单>`。
**风险**：`git checkout <commit> -- <path>` 对一个在 `<commit>` 里**不存在**的路径会**真的删掉** live 工作区里的那个文件；
而上面的差异清单会把「live 有、合并后没有」的路径也列进来 —— 那是**删除类**变更。

**自查结论**：本轮线上**没有文件被误删** ——
`docs/参考素材右键移除-交付说明-20261120.md` 在 live HEAD（`c028691`）里**存在**（6541 字节，tracked，工作区与 HEAD 一致）。
原因：它是 live 分支比 `local/maintainer` 基线**多出来**的文档，合并时被正常保留；
我最初在主仓库用 `HEAD:` 查它时查错了引用（主仓库 HEAD 指向的是另一个分支的 `b21a9e6`，不是 maintainer），
导致误判为「被删除」。已用 `git cat-file -e HEAD:<path>` 在 live worktree 里复核确认。

**加固（已提交并部署）**：部署脚本把清单拆成「新增/修改」（checkout）与「删除」（**只在日志里报告、不 checkout**，
live 保留原文件由人工确认），完整性自检也只核对新增/修改那一批。

### 9.1 追加修正 1：Agent 传的 resolution 档位被静默丢弃（真缺陷，已修）

**审计发现**：服务端审计实测 `server._merge_t2v_defaults` 在缺 width/height 时
只读 `defaults["megapixels"]`，**从不看用户传的 `resolution`**：

| 请求 | 修复前实际 | 修复后实际 |
|---|---|---|
| `resolution="480p"` | **1376×768** | **864×480** ✅ |
| `resolution="768p"` | **1376×768** | **1344×768** ✅ |
| `resolution="1088p"` | **1376×768** | **1920×1088** ✅ |
| `resolution="480p"` + 9:16 | **1376×768** | **480×864** ✅ |
| 什么都不传 | 1376×768 | 864×480（默认） |

**为什么这是缺陷而不是「无害的默认值」**：用户明确说了「要 480p」，
服务端却跑 1.0MP —— 界面显示的和产物不是一回事。
**与用户报的原话是同一个家族**（「请求 480p 实际按 768p 生成」，方向相反）。

**修法**（`server.py`）：
- 新增 `_resolution_tier_megapixels(tier, aspect)`：按**用户指定的比例**
  在真实预设（`video_models.size_presets_for_aspect`）里反查该短边档位；
- 档位合法 → 原样换算；
- **该比例下没有这个档位 → 明确报错**并给出该比例的真实档位集。
  不跨比例兜底 —— 那会让「768p + 4:3」静默变成 864p（实测）。

**关键事实（实测）**：档位集合**按比例不同**：
- 4:3 的预设：384p/480p/576p/640p/672p/736p/800p/832p/864p/896p/960p/1088p/1184p/1248p（**没有 768p**）
- 21:9 的预设：288p…896p（**没有 1440p**）
- 同一短边在不同比例下对应不同 MP（480p：16:9→0.4MP、4:3→0.3MP、21:9→0.5MP）

**面板路径不受影响**（面板总是提交 width/height，实测 864×480 照旧）。

**线上端到端复验**（`logs/case1_480p_generate_final.json`）：

### 9.2 追加修正 2：合并音视频时音轨短于视频 → 尾部断音（真缺陷，已修）

**审计发现**（咏唱实现调研）：咏唱用 `-af apad` + `-shortest` 处理短音轨。
本项目 `op_merge_av` / `op_replace_audio` **只有 `-shortest`**。

**实测**：4 秒视频 + 2 秒音频 → 产物视频 4 秒、音频仅 2 秒 ——
**尾部 2 秒画面在播、音轨已断**。

**修法**：补 `-af apad`。实测四种组合：

| 组合 | video | audio |
|---|---|---|
| 无 apad（修复前） | 4.000s | **2.000s** ❌ |
| **apad + shortest（修复后）** | 4.000s | **3.994s** ✅ |
| apad + whole_dur | 4.000s | 4.000s |
| apad + -t | 4.000s | 4.000s |

> 注：`-af apad` + `-t` **无效** —— `-t` 是输出总时长限制，而视频流是
> `-c:v copy`（不可延长），实测仍按原始流结束。

### 9.3 追加修正 3：Agent 描述合并结果时**说错了**（真缺陷，已修）

**实测**：Agent 合并「6 秒视频 + 2 秒音频」后在结论里说
