## 一、缺陷（线上实测复现，非推测）

### 1.1 利用链

```
POST /api/jobs -F mode=flf -F params={"first_frame":"/etc/hostname",...}
  → HTTP 200，任务建成
  → worker: lp = UPLOAD_DIR / up   （Path.__truediv__ 遇绝对路径丢弃左侧）
  → comfy_upload_image(session, lp)  ← 文件被复制进 ComfyUI input
  → GET http://127.0.0.1:8188/view?filename=hostname&subfolder=h3studio&type=input
  → HTTP 200，响应体 = /etc/hostname 原文
```

8190 与 8188 **均监听 `0.0.0.0`**（主机 LAN 地址 `192.168.3.78`），ComfyUI `/view` **无鉴权** ⇒ 局域网内任意主机可回读任意本地文件。

**修复前实测回读原文**：

```
$ curl -s "http://127.0.0.1:8188/view?filename=hostname&subfolder=h3studio&type=input"
ubuntu            ← 这就是 /etc/hostname 的内容
```

**ComfyUI input 目录前后对比（修复前）**：新增 `hostname` —— 即 `/etc/hostname` 的副本被落地。

### 1.3 根因

`h3studio/asset_ref_guard.py` 只覆盖两条通道：

| 通道 | 守卫 | 状态 |
|---|---|---|
| multipart 直传（`saved_files`） | `reject_external_media()` | ✅ 已拦 |
| `asset_refs`（`asset_id`） | `check_asset_refs()` 查库 | ✅ 已拦 |
| **`params` JSON 通道** | —— | ❌ **无人管** |

而 worker 会把 `params["first_frame"]` 当成「uploads 目录下的相对文件名」拼路径（`server.py:1837-1845`），于是外部路径被当成本地文件读入并上传到 ComfyUI。

### 2.2 接入点：唯一公共点

`server.prepare_job_params` 是**所有**建任务路径的公共点：

- 面板提交 `POST /api/jobs`
- 内置 Agent `create_job` 工具
- Agent `retry_job` 工具

一处接入 ⇒ 三条链路同时生效，不会各写一份必然漂移。

### 2.3 判定口径

params 里的媒体引用**只允许两种形态**：

1. **素材库引用** —— 走 `asset_refs` 通道（`check_asset_refs` 查库）；
2. **i2i 的 `ref_images` 元数据** —— `[{asset_id, description}]`，dict 形态，由查库那条通道负责。

其余（绝对路径 / `..` 穿越 / 符号链接 / ComfyUI input 直引 / 任意相对路径）**一律明确拒绝**，并给可执行的中文原因：

```
首帧不能直接引用外部文件路径（收到：/etc/hostname）。请先在「素材库」页上传并入库，再从素材库选择首帧。
```

错误码：`code=media_must_come_from_library`。

覆盖的媒体键（8 个，缺一个就是一个旁路）：
`first_frame` / `last_frame` / `ref_videos` / `ref_audios` / `ref_images` / `ref_video_audios` / `ref_audio` / `segment_audio_file`

**为什么按「值的形状」判而不是按「路径在不在白名单目录」判**：「resolve() 后必须落在 UPLOAD_DIR 内」这种写法有两个致命问题 —— 符号链接（UPLOAD_DIR 里的软链指向 `/etc/shadow` 时 resolve 后已出界）、以及 TOCTOU（判定通过后、worker 读文件前文件可被替换）。按形状判**根本不给外部路径进入的机会**：不存在「路径解析」这一步，也就没有符号链接与竞态窗口。

### 2.4 顺带修好的既有缺陷：媒体任务的重试

**实测发现（修复前线上）**：媒体任务的重试**今天本来就是坏的**。

```
重放一条已完成 flf 任务的 params（= Agent retry_job 的语义）
  → HTTP 200 建任务 → failed
  「找不到上传文件: h3studio/685e6b9292ca0ec9__e2e-sample-4079691-93314.png」
```

根因：worker 上传素材后把 ComfyUI 文件名**写回 params** 并整份回写进 jobs 表；重试把这份 params 整份拷来，而 `UPLOAD_DIR / "h3studio/<name>"` 指向一个**并不存在**的文件（实测线上 53 个这样的值**没有一个**能解析到真实文件），worker 的 flf 分支**先**执行 `lp = UPLOAD_DIR / up` 就报错，走不到后面的 `_apply_asset_refs`。

修法：`_drop_stale_worker_media_params()` 在校验**之前**清掉「asset_refs 已覆盖的槽位」上的过期残留，让 worker 改走素材库那条路。

**安全底线**：只删「形状上不可能是外部路径」的值（无 `/` 开头、无 `..`、无盘符、只有一层子目录）。`/etc/hostname` **不被删** → 留给闸门**明确报错**。否则攻击者只要同时带上覆盖同一槽位的 `asset_refs`，就能让自己的外部路径被静默丢弃 —— 那等于把「明确拒绝」降级成「悄悄忽略」，与需求相悖。

**修复后线上实测**（同一条任务、同一份 params）：

| | 任务 | 结果 |
|---|---|---|
| 修复前 | `c77213295171` | **failed**「找不到上传文件: h3studio/685e6b9292ca0ec9__...png」 |
| 修复后 | `b62932b406e3` | **done**（正常出片） |

## 七、执行过程中的失误与处理（如实记录）

**在全量 pytest 时污染了线上 `jobs.db`。** 原因：`config.json` 的 `data_dir` 指向**线上共用的** data 目录，而 `server.DB_PATH = <data_dir>/jobs.db` —— 任何调用 `create_job_record` 的用例都会往线上 jobs 表写任务，线上 worker 随后把这些测试任务当真实任务跑（占 GPU、产出视频）。

- 实测污染：24 条测试任务（`prompt` 为 `x` / `next`），其中 5 条被线上 worker 真的跑完出了视频。
- 处理：备份 `/tmp/jobs.db.precleanup-1795131816` 后，**只删** `prompt ∈ {x, next}` 的测试产物，**11 条真实用户任务全部保留**（含 `18830486d451` / `ce7247b905a8` / `974f5dcd0823` 等用户任务与 `a8fa98b7d91f`）。
- 根治：新增 `scripts/compare_suite_isolated.sh`，**强制**用独立的 `H3STUDIO_DATA_DIR`（/tmp），测试产物不再落线上。已验证：重跑期间线上 jobs.db 只剩真实任务与本次探针任务。

**其它取证副作用清理**：

- 探针产生的 `/home/ubuntu/comfyui/input/h3studio/hostname` **已删除**（仅本轮探针产物，未触碰任何线上业务数据）
- 探针临时目录 `/tmp/params-probe-*` 随脚本退出自动清理
- **未删除任何线上业务数据**；未改动任何他人未提交文件（`/root/projects/h3studio-cont-seam-hires` 的 118 项未提交改动经核对与本次改动文件无冲突，合并走 `git update-ref` 未触碰其工作区）
